# 第 1 轮 · AI 对话产品（2.5 / 5）

## Q1 · Prefill 和 Decode 混批会发生什么？

**原题**：LLM 推理分 Prefill（算 prompt，吃算力）和 Decode（逐 token 生成，吃带宽）。新请求的 Prefill 和一堆老请求的 Decode 混在同一个 batch，会发生什么？如果你是调度器怎么处理？

**你的回答**：先处理 Decode，Prefill 等待。→ 被追问「你的首字延迟 <1 秒目标还守得住吗」后改答：将 Prefill 切片和 Decode 一起推理。

**完整答案**：这就是矛盾核心——保护 Decode 则新用户干等（TTFT 崩），保护 Prefill 则老用户吐字卡顿。正解是 **chunked prefill**：把大 Prefill 切成小块，与 decode 步混排在同一个 batch，两边都不饿死。你第二轮自己推出了正确答案。

**要点**：✅ 过（先错后对）

**📌 复盘总结**
- **缺口本质**：第一反应只盯住一头目标（保 Decode 流畅），没意识到 TTFT 同样是硬指标——两个目标抢同一块资源时，「让一方排队」永远不是答案
- **补全链路**：识别两类任务（prefill 吃算力 / decode 吃带宽）→ 确认双方都有延迟 SLA → 把大任务切碎混排 → 两边都不饿死
- **记忆钩子**：「两类任务抢同一资源、谁都等不起 → 切碎混排」。磁盘 IO 混合、数据库读写混布同理

## Q2 · 显存满了，踢谁的 KV 缓存？

**原题**：显存满了，新会话要分配 KV 缓存。现有：A 一个 10 分钟没动静的会话、B 正在生成中的请求、C 几百个会话共享的系统提示前缀缓存。驱逐优先级是什么？被踢的 A 若 5 分钟后回来会怎样？

**你的回答**：先答 C→A→B（先踢公共前缀）→ 被追问「你确定要第一个踢掉一份成本、几百倍收益的东西？」后改答 A→C→B。

**完整答案**：**A（不活跃）→ C（公共前缀）→ B（生成中）**。判据不是「活跃度」，是「**重建成本 vs 占用空间**」的性价比：
- C 被踢 → 几百个会话每次都要重算公共前缀 → prefix caching 这个最大省钱杠杆当场作废
- B 永远最后——踢了正在生成的等于白烧已算过的 GPU
- 加分项：被踢的 A 不必真删，可 **offload 到 CPU 内存**，用户回来换回显存，比从头重算便宜

**错误要点**：❌ 「先踢公共前缀」是典型错误——共享缓存的性价比被会话数摊薄放大，是最不该先踢的。

**📌 复盘总结**
- **缺口本质**：直觉用「活跃度」（LRU 思维）当驱逐依据，没算重建成本的杠杆——共享前缀空间小、重建收益被几百个会话分摊放大
- **补全链路**：驱逐顺序 = 重建成本 × 重建概率 ÷ 占用空间 → 共享缓存性价比最高放最后 → 正在生成的重建成本无穷大（已烧的 GPU 白费）永远最后
- **记忆钩子**：「驱逐看重建性价比，不看活跃度」。加分项：被踢的可 offload 到 CPU，不必真删

## Q3 · 70B 模型 4 张卡，按层拆还是每层切开？

**原题**：A）按层拆（流水线并行 PP）B）每层矩阵横切（张量并行 TP）。各要传什么数据、传输量谁大？哪种对卡间网络要求高？4 张卡跨机器走以太网选哪种？

**你的回答**：「肯定是张量并行，卡之间不需要传递太多信息，只需要最后组合答案」——**答反了**。追问后纠正：跨机以太网选流水线并行。

**完整答案**：

| | 张量并行 TP | 流水线并行 PP |
|---|---|---|
| 通信频率 | **每层都要 all-reduce（80 层 = 每个 token 80+ 次集合通信）** | 只在层边界传激活值（4 卡只传 3 次） |
| 网络要求 | NVLink 级超高带宽，**只能单机内** | 以太网也能忍 |
| 代价 | 通信开销 | 流水线气泡（卡空转） |

你的错误根源：以为 TP「只需最后组合答案」。错——**第 2 层需要第 1 层的完整输出**，所以每层算完都必须立刻合并才能进下一层。TP 是通信**最重**的方案。大规模集群的混合部署：**机内 TP + 机间 PP**。

**错误要点**：❌ 这是最经典的认知错误，模板里已标为「❗ 最常见的认知错误」。

**📌 复盘总结**
- **缺口本质**：把 TP 想象成「分工后最后合并」，没看到层间数据依赖——每一层的输入都是上一层的**完整**输出，切了就必须每层同步
- **补全链路**：先画数据依赖 → 数通信：TP 每层 all-reduce（80+ 次/token）、PP 只在层边界传激活（3 次）→ 通信量决定网络要求 → 决定部署边界
- **记忆钩子**：「通信模式决定部署边界」。任何分布式拆分前先算「传几次、传多少」

## Q4 · 模型路由悖论：谁判断问题难不难？

**原题**：简单问题给小模型省钱，但「谁来判断难度」？用大模型判断=多花钱，用小模型判断=学渣不知题超纲，用规则判断=「证明黎曼猜想」只有 12 字。怎么设计路由器？

**你的回答**：两步走，都答对了——
1. 「不对问题路由，对**任务**路由：大模型形成任务列表，按难度路由」（Agent 场景）
2. 追问单轮请求（占 C 端 80%）后：「小模型先答，特定小模型判断是否好，不好再升级重答」

**完整答案**：
- **任务级路由**：大模型反正要做规划（这笔钱省不了），难度判断搭规划的便车，零额外成本
- **级联路由（cascade）**：小模型先答 → Judge 评质量 → 不合格才升级。关键洞察：**判断「答得好不好」比预判「难不难」容易得多**
- 你没说的代价：级联升级时用户等了「小模型 + Judge + 大模型重来」三段时间，**尾延迟翻倍**——级联省的是钱，付的是最慢那批请求的体验

**要点**：✅ 本轮最漂亮的一题（把「问题路由」重框为「任务路由」是有实践经验的人才会有的反应）

**📌 复盘总结（强项固化）**
- **为什么答对**：有 agent 实践，会重新框定问题（对问题路由 → 对任务路由），被提示后能自己推出级联
- **还差一步**：级联的代价要主动说——尾延迟翻倍（最慢那批请求为省钱买单）
- **记忆钩子**：「判断答得好不好，比预判难不难容易得多」

## Q5 · 用户流式对话到一半关掉浏览器，GPU 在干什么？

**原题**：流式输出到 300 字时用户关浏览器。① GPU 知道用户走了吗？会算完剩下 700 字吗？② 烧掉的算力谁付钱？③ 怎么设计让 GPU 尽快知道「人走了」？

**你的回答**：「继续计算，生成后保存结果，通知用户」❌；补救机会时答「应该有停止按钮」❌。

**完整答案**：
- **cancellation 沿链路传播**：SSE 连接断开 → 网关检测到 → 通知编排层 → 推理引擎**立刻把请求踢出 batch、释放 KV 缓存槽位**（vLLM 有 abort 接口）
- 三重代价：① 纯烧钱零收益 ② 占 batch 槽位拖累真实用户首字延迟 ③ 占 KV 缓存。规模化后取消请求可能占 10%+
- 第二个 abort 场景：**同一会话用户没等答完就发新消息** → 旧答案已经不要了，应自动 abort（会话级串行化）
- 「停止按钮」解决不了：关浏览器/断网/锁屏用户都不会主动通知；且按钮点下去之后还是走同一条 abort 链路

**错误要点**：❌ 未答出。暴露「成本意识不彻底」——嘴上说 token 都是钱，遇到具体场景第一反应是「贴心地算完」。纪律：**这一秒 GPU 在为谁工作？这个人还要这个结果吗？**

**📌 复盘总结**
- **缺口本质**：「服务要完整」的惯性——把用户当成必须服务到底的对象，没想「这个请求还有没有主人」；还想用产品补丁（停止按钮）代替架构保证
- **补全链路**：资源在服务谁 → 人走了/不要了 → 立刻 abort 释放槽位+KV → 沿链路传播（SSE 断→网关→编排层→推理引擎）；两个场景：断连、同会话新消息进来
- **记忆钩子**：「这一秒 GPU 在为谁工作？他还要这个结果吗？」架构不能假设用户守规矩

# 第 2 轮 · 短链接服务（3 / 5）

## Q1 · 6 位短码空间多久用完？用完那天发生什么？

**原题**：Base62 六位 ≈ 568 亿空间，每天新增 1000 万条。① 多久用完？② 用完那天发生什么？③ 上线前该做什么设计？

**你的回答**：① 5680 天 ✅ ② 「短码会重复」❌ ③ VARCHAR、正则 `{6,}`、按最长位数预留 ✅

**完整答案**：
- 568 亿 ÷ 1000 万 = 5680 天 ≈ 15.5 年
- **不会重复**——自增 ID 唯一，ID = 62⁶ 时 Base62 编码出来是 **7 位**。真正发生的是**位数悄无声息从 6 变 7**：没有报错、没有冲突，某天新链接就是 7 位了。你以为「会重复」会去设计冲突检测，但实际问题需要的是**变长兼容**——完全不同的防御
- 上线前三件事：`VARCHAR` 变长 / 正则写 `{6,}` 不锁死上限 / 全链路（前端、SDK、二维码）不假设固定长度。**上线前就不假设固定长度，比那天再改便宜一万倍**
- 补刀：短码位数不该产品说了算，是架构用「日增量 × 预期寿命」反推出来的

**错误要点**：❌ 「会重复」导致设计错防御方向

**📌 复盘总结**
- **缺口本质**：把「空间耗尽」想成「碰撞」，没推演自增 ID 的唯一性——真正发生的是编码位数静默增长，而炸点是全链路所有「假设 6 位」的地方
- **补全链路**：自增 ID 唯一 → 编码也唯一 → 变的是位数 → 扫全链路长度假设（定长字段/正则/前端/二维码）→ 上线前预留变长
- **记忆钩子**：「固定容量资源，上线前就用日增量×寿命算耗尽日；全链路不假设长度」

## Q2 · 热点 key TTL 到期瞬间，50 万请求涌入

**原题**：千万粉大 V 转发的短链 10 秒 50 万点击，TTL 正好此刻到期。① 发生什么？② 数据库承受几次查询？③ 怎么设计不打死数据库？

**你的回答**：缓存击穿 ✅、50 万次 ✅、加锁只放一个回源 ✅。追问「499,999 个请求等锁会不会打死应用服务器」时答「双份缓存」❌。

**完整答案**（三种做法从轻到重）：

| 做法 | 机制 | 代价 |
|------|------|------|
| **热点 key 永不过期** | 短链映射本来就不可变，直接不设 TTL | 冷数据占内存（LRU 兜底） |
| **逻辑过期** | 缓存存 `{value, expire_at}` 永不物理过期；读到逻辑过期返回旧值 + 后台异步刷新 | 短时返回旧值（对不可变映射零风险） |
| **TTL 随机抖动** | TTL = 基础值 + random(0~10%) | 只防雪崩，不防单个热点击穿 |

关键洞察：**你自己说过「短链映射是不可变的」——那为什么要给它设 TTL？** 给不变的数据设过期时间，是把「缓存一致性」的思维惯性套用到不需要一致性维护的场景。

**错误要点**：❌ 这是裂缝②（有结论不主动调用）的**第一次出现**：教练模式说对了「不可变」，实战场景没把它用上。

**📌 复盘总结**
- **缺口本质**：把「缓存需要维护一致性」的思维惯性套到不可变数据上；「不可变」的结论停在记忆里，没变成设计红利
- **补全链路**：数据不可变 → 缓存永远不会旧 → 不需要 TTL → 不会过期 → 击穿不存在。不是解决击穿，是让击穿没有发生条件
- **记忆钩子**：「与其解决问题，不如让问题没有条件发生」——与消解扇出同源。设 TTL 前先问：这数据不可变吗？

## Q3 · 自定义短码和自增短码会撞车吗？

**原题**：企业客户可指定 `sho.rt/spring-sale`。① 和自增生成的短码在同一命名空间，会撞车吗？举个场景。② 怎么设计不打架？

**你的回答**：「做一个映射，自定义码映射为 Base62 字符串」❌ → 被驳后改答「自定义后标记为使用，自增 ID 到了跳过」△

**完整答案**：
- 你的第一版是致命漏洞：访问 `spring-sale` 时系统得先查到它映射的 `aB3xY`——需要一张以 `spring-sale` 为 key 的表，**一次查找变两次，撞车一点没解决**
- 真实撞车场景：客户抢先注册自定义码 `aB3xY` → 三个月后自增 ID 编码正好等于 `aB3xY` → 客户印在物料上的链接指向了别人的网站

| 方案 | 机制 |
|------|------|
| 长度隔离 | 自定义码强制 ≥8 位，自增生成永远 ≤7 位 |
| 字符集隔离 | 自定义码必须含 `-` 或 `_`（Base62 里没有） |
| 路径隔离 | 自定义走 `sho.rt/c/xxx` |

**📌 复盘总结**
- **缺口本质**：第一反应是「加一道检查」（再映射/查重跳过），没想「改结构让冲突数学上不可能」
- **补全链路**：问「能不能让两个命名空间不相交」→ 长度≥8 / 必含- / 路径隔离 → 零检查成本 → 唯一约束只做最后保险
- **记忆钩子**：「结构能保证的，绝不用检查保证」——复式记账、客户端生成 ID+唯一约束、幂等键唯一索引，全是同一思想

## Q2 · 朋友圈式信息流估算

**原题**：日活 1000 万，人均日发 1 条，人均日刷 20 次每次 10 条。① 写 QPS ② 读 QPS、读写比 ③ 峰值读 QPS（×3）④ 就这三个数字，能得出什么架构结论？

- **第 4 问正解不是读写分离，是「什么都不用做」**：6000 QPS 峰值，一台 8 核机器 + Redis 就能扛。**信封背面估算最重要的用途，不是告诉你「要上什么方案」，而是证明你「不需要上什么方案」**——这个规模单体 + 一个数据库 + 一层缓存就够了，不要微服务、不要分库分表、不要读写分离

**📌 复盘总结**
- **缺口本质**：把估算的用途用反了——算出数字先想「该优化什么」，而估算的第一用途是证伪复杂度；且 QPS 只算请求数，漏了写放大

- **记忆钩子**：「架构师最有价值的输出常是『不需要做』」；「算 QPS，再算扇出，再算数据总量」

- **还差一步**：D 识别出了模式但没喊族名（限量发放族）——认出模式还要归族
- **记忆钩子**：「有因果的必须保序，并发的随意」；「在真正需要顺序的最小范围内保序」

## Q4 · 「立刻看到已发送」和「一条不能丢」怎么同时满足？

**原题**：用户希望 <100ms 看到「已发送」，但消息必须可靠送达一条不丢。① 为什么冲突 ② IM 有没有别的系统没有的资源让两者都满足 ③ 「绝对不丢」靠客户端做什么+服务端做什么

**你的回答**：① 对 ② 把 Q2 答案套过来 ❌，提示后答「缓存」❌ ③ 「客户端还要写其他人的信息」❌——记未答出

**完整答案**：
- 冲突机制：要立刻显示「已发送」就不能等服务端持久化确认（几十~上百 ms）；要绝对不丢就必须等确认才敢说成功——**延迟 vs 持久性**的冲突
- IM 独有的资源不是「缓存」，是——**客户端本身就是一个持久副本**：

| | 缓存 | 持久副本 |
|---|------|---------|
| 目的 | 加速 | 保障可靠性 |
| 丢了 | 没事，回源重取 | 不能丢，它就是数据本身 |
| 在 IM 里 | 内存里的最近消息 | 本地 SQLite + 待发队列 |

- 状态分级的架构意义 = **把一条时间线拆成两条**：发送中（转圈，客户端本地落库，**0ms** ← 满足立刻反馈）/ 已发送（单勾，服务端持久化并 ack，几十 ms ← 满足绝对不丢）/ 已送达 / 已读。**这就是消解，不是妥协。微信的双勾号不是产品设计，是架构决策的 UI 投影**
- 客户端只存两样：自己收到的 + 自己待发的。别人的消息由别人的客户端存——副本边界是「我自己的会话视图」
- 连线（你没连上的）：消息 ID 客户端生成 → 超时重传时服务端靠唯一约束分辨新消息/重传 → **重传 100 次也只存一条**。这是「用结构保证而非检查保证」的又一次出现

**错误要点**：❌ 暴露心智模型缺失：把客户端当「展示层/缓存」而不是「参与可靠性保障的副本节点」——这促成了下一轮专项训练

**📌 复盘总结**
- **缺口本质**：这是心智模型缺口，不是知识点缺口——客户端被当成「缓存/展示层」，所以「立刻反馈」和「绝对不丢」在你眼里无解，只能二选一
- **补全链路**：两要求抢同一个返回时刻 → 拆成两条时间线（状态分级）：客户端本地 0ms 满足「立刻」、服务端 ack 满足「不丢」→ 各走各的时间线，两个都拿到
- **记忆钩子**：「微信双勾号是架构决策的 UI 投影」；「客户端可以是仓库」——本地 DB 不是缓存

# 第 5 轮 · 专项训练：客户端/边缘作为副本（3.5 / 4）

## Q1 · 飞机上记 5 笔账、删 1 笔，落地开网后怎么同步？

**原题**：记账 App，完全无网时记了 5 笔、删了 1 笔。① 存在哪里？存的是最终状态还是别的？② 开网时客户端发什么、服务端提供什么接口（和普通 CRUD 有何不同）？③ 网页端也记了 3 笔，客户端怎么知道「服务端有哪些我还没有的变更」？

**你的回答**：① 存本地、**存操作日志而非最终状态** ✅（视角已建立）② 发操作序列 ✅ ③ 「通过操作日志」❌（没答出机制）；提示「你昨天自己说过」仍没接上 ❌。删除问题答「本地标记、同步到服务端真实删除」——前半对后半错 ❌

**完整答案**：
- ③ 的答案是**同步游标（sync cursor）**：服务端给每个变更分配单调递增 seq；客户端记住 `last_synced_seq = 1042`；开网时①上传 `POST /changes`（本地未同步的操作，每条带客户端生成的操作 ID）②下载 `GET /changes?since=1042`（只返回之后的变更）③更新游标。**全量比对不可行**（十年账目每次开网都比一遍？），游标的意义是**只传增量**。同步接口和普通 CRUD 的差别：普通是「给我第 N 条」，同步是「**给我第 X 号之后发生的所有事**」。（你昨天在群聊题自己说出的「每人存一个读到哪的游标」就是它——**一个模式三个场景**：群聊已读、离线同步、短链日志补算）
- 删除的正解：**墓碑（tombstone），而且服务端也不能物理删**。你答「服务端真实删除」会出事故：手机删了这笔账 → 服务端物理删 → 平板一周后联网，`GET /changes?since=X` 里没有任何删除痕迹 → 平板把本地那条**又传回去** → 删除的账目**复活**。墓碑要保留一段时间（所有设备确认同步过，或固定 30 天）再 GC
- 🔑 **分布式同步里最难的操作是删除**——「不存在」这个状态没法传播，只能用「一条说明它不存在的记录」来传播它

**错误要点**：❌ 同步游标是裂缝②第三次出现（明确提示仍没调用）；墓碑后半错

**📌 复盘总结**
- **缺口本质**：「读游标」没被跨场景检索到（提示了仍没接住）；墓碑只想客户端侧，没想到服务端物理删会让删除复活
- **补全链路**：同步靠游标（只传增量：GET /changes?since=X）→ 删除靠墓碑（用「一条说明不存在的记录」传播）→ 两端都不能物理删 → 墓碑保留期后 GC
- **记忆钩子**：「一个模式三个场景：群聊读游标/离线同步游标/短链日志补算」；「同步里最难的是删除」

## Q2 · 手机改 100、网页改 200，都离线——LWW 丢了什么？

**原题**：① Last-Write-Wins 丢了什么、用户后果？② 更隐蔽的坑：时间戳是谁的时钟？③ 什么数据绝对不能用 LWW？为什么？

**你的回答**：① 静默丢失 ✅ ② 客户端时钟不可信 ✅ ③ 例子对（余额）但理由错（「必须串行处理」❌）。追问后三问全对，且**把两题串起来** ✅✅

**完整答案**：
- LWW 三个坑：① **静默丢失**——手机上明明改成 100，同步后变 200，没有任何提示 ② **客户端时钟不可信**（可手动改、时区漂移）③ **服务端时间也不完美**——离线三小时后上传的操作打上更晚时间戳，反而赢过期间在线的修改，真实因果顺序丢了。严格解法是**版本向量/逻辑时钟**
- 「必须串行」是实现手段不是原因，且和「离线可用」直接冲突。真正原因藏在数据性质里：手机记「+100」、网页记「+200」是**两笔不同的账**，LWW 结果余额 200，应该是 300——**累加型数据每个操作都携带信息，丢一个就错一个**
- 你把两题串起来了：**存操作日志而非最终状态，冲突自动消解**——「+100」和「+200」是两个独立操作，都保留都执行，自然是 300，**根本不需要问「谁赢」**。这就是 **CRDT** 的核心思想：让数据结构本身具备「无论以什么顺序合并都得到相同结果」的性质

| 数据性质 | 例子 | 能 LWW 吗 |
|---------|------|----------|
| 累加/集合型 | 余额、计数、标签、待办 | ❌ 必须合并操作 |
| 覆盖型 | 备注、标题、设置项 | ✅ 后写覆盖符合语义 |

- **记忆钩子**：「两种访问形态 → 两套存储」；「不为 1% 的查询毁掉 99% 的主路径」

## Q1 · 爆款最后 100 件，10 万请求秒杀

## Q2 · 2PC 最干净，为什么要用 Saga？

**原题**：下单跨库存/订单/支付三服务，同事主张两阶段提交。① 2PC 为什么扛不住（至少两条机制理由）② Saga 换来什么、失去什么 ③ 用了最终一致必须补建什么？为什么「最终」可能永远到不了？

**你的回答**：① 理由混乱（「超卖需要回退」说反了）❌ ② **「我不知道 Saga 是什么」**——知识盲区 ❌❌ ③ **主动说出对账系统** ✅

**完整答案**：
- 2PC 三条死因：① **锁的时间太长**——prepare 阶段所有参与者锁住资源等最慢者，高并发吞吐崩塌 ② **一个卡住、全体卡住**——银行响应要几秒几分钟，整个事务挂起，其它事务全被堵 ③ **外部系统根本无法参与**（最致命）——银行没有 prepare 阶段，你没法让银行「先冻结、听命令提交或回滚」。2PC 只适用于你完全掌控的参与者，而支付必然涉及外部渠道
- **Saga** = 把跨服务长流程拆成一个个本地事务步骤，每步在各自服务内快速提交（不锁别人），为每步预写**补偿操作**，第 N 步失败时按相反顺序执行补偿：

```
① 预扣库存 → ② 建订单（待支付）→ ③ 调支付（异步）
   ├─ 成功 → 订单已支付，预扣转正式扣减，触发履约
   └─ 失败/超时 → 补偿：订单取消 + 回补库存
```

- 换来：高吞吐（无跨服务长锁）、每步可独立重试、可异步。失去：**不一致窗口**（订单建了钱没付，外人看是脏数据）、每步都要写补偿逻辑、必须靠对账兜底
- 一句话：大事务是「全局锁一次搞定」，Saga 是「每步快进快出、错了再倒着退」——**用短暂的不一致+对账，换吞吐**
- 「最终」必须有主动核对兑现：对账系统逐笔核对（订单 vs 支付 vs 账务），能修的自动修、修不了的报警人工。**没有对账，「最终」可能永远到不了**——最终一致承诺必须配对账机制，就像「先落库」必须配 ack+重试

**📌 复盘总结**
- **缺口本质**：不知道 Saga（知识盲区——模板里写着但没吃透）；2PC 理由还答反了（2PC 恰恰靠锁防超卖）
- **补全链路**：2PC 三死因（长锁/一卡全卡/外部系统无 prepare）→ Saga = 本地事务序列 + 反向补偿，每步快进快出 → 代价：不一致窗口 + 补偿复杂度 + 必须配对账
- **记忆钩子**：「大事务 = 全局锁一次搞定；Saga = 每步快进快出、错了倒着退」；「『最终』要有对账兑现」

## Q3 · 5 次提交同一笔订单，幂等怎么做？

**原题**：网络抖动前端自动重试 3 次 + 用户手抖多点 2 次。① 不做幂等会出哪两个事故 ② 幂等键怎么设计（谁生成、放哪、靠什么去重）？「先查重再执行」为什么有坑 ③ 支付幂等和下单幂等是同一件事吗？各自的键长什么样？

**你的回答**：① ✅（重复订单+重复扣款/超卖）② 「**服务端生成版本号**」❌❌（致命错误）「先查重」没说出唯一约束 ❌ ③ 「不是同一件事」✓ 但「key 是金额/库存数量」❌❌

**完整答案**：
- ① 重复创建订单、重复扣款/超卖
- ② 三要素：
  - **谁生成：调用方（客户端）生成**，一次业务动作一个键，重试复用同一个键。**服务端生成的话 5 次重试 = 5 个不同的键，永远无法去重**
  - **怎么去重：数据库唯一约束**（键上建唯一索引），重复插入直接失败返回首次结果。「先查重再执行」有竞态——查与写不原子，两个并发请求同时查到「不存在」→ 都执行 → 照样重复
  - **键的语义：「这一次动作的身份证」**（下单请求号、订单号+支付单号），不是金额/库存——**两笔 100 元的支付是两笔**，金额相同不能互相去重
- ③ 本质是**同一纪律**：一切会被重试的写操作的安全带（重试在分布式是常态——超时不知道成没成，只能重发）。差别只在键的形态

**📌 复盘总结**
- **缺口本质**：两处致命：键由服务端生成（每次重试都是新键，永远去不重）；把键当业务量（金额/库存）——键是身份不是量
- **补全链路**：三要素：调用方签发（重试复用同一键）→ 唯一约束验票（先查后写有竞态，两并发会同时查不到同时执行）→ 语义是「这一次动作的身份证」（下单请求号/订单号+支付单号）
- **记忆钩子**：「两笔 100 元的支付是两笔——金额不是身份」

## Q4 · 支付请求银行一直不回，超时了

**原题**：100 元支付发给银行，30 秒、1 分钟不回。① 直接判失败最坏发生什么 ② 正确做法：归到哪个状态、靠哪两个机制收敛 ③ 「失败」和「未知」的本质区别？

**你的回答**：① ✅（扣钱订单不成立）② 查询补偿 ✓、漏「未知」状态定义和对账第二层 ❌ ③ 「确定性」抓到边但没讲透 △

**完整答案**：
- ① 银行侧实际已扣款成功，系统却记失败 → **钱消失**：用户没拿到订单、钱也没了；更糟的是重试会再扣一次（双重扣款）
- ② 第一步：**状态置为「未知」**（不是直接去查）；然后两层收敛：**主动查询补偿**（定时/退避地问银行这笔成没成）+ **对账兜底**（拿不到准话时，当天对账以银行流水为准）
- ③ **「失败」= 系统确定知道结果；「未知」= 系统不知道结果（可能成功、也可能失败）**。归入失败 → 钱消失；归入成功 → 实际没扣款却照常发货 → 钱收不到。两边都是真金白银。**超时 ≠ 失败**——承认信息不足，用机制把不确定收敛成确定，而不是假装它不存在

**错误要点**：❌ 对账第二层漏了——**而你在上一题 Q2 里刚主动说过对账系统**。同一个知识换个场景就没调用，裂缝②最隐蔽的变体：知识没绑定触发场景

**📌 复盘总结**
- **缺口本质**：漏了两层：「未知」的状态定义（一等公民，不是直接去查）；对账第二层——而对账上一题刚说过，换场景就忘（知识没绑触发场景）
- **补全链路**：超时 → 状态置「未知」→ 查询补偿（主动问银行）→ 仍拿不准 → 对账兜底（以银行流水为准）。失败 = 确定；未知 = 信息不足
- **记忆钩子**：「超时 ≠ 失败」；把知识绑场景：「任何最终一致承诺 → 必有对账兑现」

**原题**：① 传递层为什么做不到恰好一次，两种选择各换什么保证 ② 效果上恰好一次的组合公式 ③ GitHub 案例：都按规则执行为什么还是灾难、头号整改措施

**你的回答**：① 原因对；重传=不丢 ✅；「等待避免重复」❌（应是「不重发=至多一次：不重但可能丢」）② 只说「幂等」，缺「至少一次+消费端」③ 忘了

**完整答案**：① 没收到 ack 就无法确认对方收没收到；重发=至少一次（不丢可能重）/ 不重发=至多一次（不重可能丢）② **至少一次投递 + 消费端幂等 = 效果上的恰好一次**——正确性下沉到消费端（幂等键+去重表）③ 规则的前提错了：Orchestrator 为单节点故障设计，面对区域分区把「失联」误判为「主库不可用」（灰色失败），分区另一侧凑齐多数派按规则切主 → 两岸都接收过写入，数据分叉，只能人工修复；头号整改：**禁止跨区域提升主库**。教训：**自动化越强，越要想清楚它在极端情况下会做出什么决定**

## Q1 · 双写难题 → Outbox（3/4）

**原题**：改库+发 Kafka 两件事无共同事务。① 先写库再发消息崩了会怎样 ② 先发消息再写库呢 ③ 重试为什么补不上 ④ 正解叫什么、最狡猾的一步

**你的回答**：①② 只说了事件没说后果；③ 摸到「不知道是否成功」但没打中结构原因；④ Outbox + 同一事务包住 ✅

**完整答案**：先写库再发消息 = **丢消息**（库里订单已建，下游永远收不到）；先发消息再写库 = **幽灵消息**（下游收到通知但库里没有）。重试补不上：**失败窗口来自「两步没有共同事务」这个结构，重试只是把不确定性挪位置**——重试解决「单次调用可能失败」，解决不了「两步必须同生共死」。Outbox 狡猾之处：把「发消息」降级成「写 outbox 表一行」，与业务数据同一本地事务原子提交，真正发送由独立投递员（轮询/CDC）事后完成

**📌 复盘总结**
- **缺口本质**：后果的两个名字（丢消息/幽灵消息）没出口；重试失效的结构原因没想透
- **记忆钩子**：「丢消息 vs 幽灵消息」；Outbox = IM 模板「先落库、再投递」的工程化标准形态

## Q2 · 补偿 ≠ 回滚（2.75/3）

# 第 12 轮 · 第 13 章规模化力学检验（11.05 / 15 ≈ 74%）

## Q1 · 垂直 vs 水平 / 无状态好扩（2.4/3）

**原题**：① 垂直/水平优缺点 + 垂直在做什么 ② 水平的代价 ③ 先问哪句 + 为什么两层成本天差地别

**你的回答**：① ✅（「拿金钱换时间」很接近）② 「从管一台到管一群」✅ ③ 「加的是哪一层？」✅ 原因偏薄

**完整答案**：垂直是在「**买时间**」（且不解决单点）；水平的代价是从管一台到管一群——互相通信、同步，一致性、分片、再平衡全来了。有状态层贵的原因：它「记得」东西（余额/库存/会话），加一台意味着**两份「记忆」怎么对上**。**加机器从来不是一个均匀的动作**：无状态层加 10 台是配置改一行；有状态层加 1 台是重新分片+TB 级搬迁

**📌 复盘总结**
- **缺口本质**：垂直的「不解决单点」漏了；有状态「两份记忆对不上」的画面没说
- **记忆钩子**：「有人说加机器就行，先问：加的是哪一层？」

## Q2 · 分片与一致性哈希（1.85/3）

**原题**：① 范围/哈希优缺点+判据 ② 朴素哈希致命缺陷 ③ 一致性哈希一句话价值 + vnode 好处

**你的回答**：① 范围的缺点说成「容易雪崩」❌（是易热点；雪崩是缓存词）② 说了结果没说机制 ③ 「只搬 1/N」✅，vnode 只答一个好处

**完整答案**：范围 ✓ 范围查询高效 ✗ 易热点（新数据总往最后一段挤）；哈希 ✓ 均匀 ✗ 范围查询废；判据 = 查询形态。朴素哈希：**N 写死进了公式**，%4→%5 时 N 一变余数全乱，几乎每个 key 归属都变，加一台搬 ~80% 数据。一致性哈希：加减节点只搬 1/N（只影响环上相邻段）。vnode 还有两个好处：**一台挂了负载被「打散」分给所有节点**（不全压一个邻居）；异构机器好处理（猛的多放 vnode）

**📌 复盘总结**
- **缺口本质**：术语配错位（雪崩 vs 热点）；机制没说到根（N 写死）
- **记忆钩子**：「朴素哈希把 N 写死——一变全集群地震；一致性哈希只搬 1/N」

## Q3 · 热点与 Bieber 问题（2.3/3）

**原题**：① 负载遵循什么分布 + 分片为何失效 ② 一句话思路 + 四手段配场景 ③ Bieber 问题与解法

**你的回答**：① 幂律 ✅、路由到同一节点 ✅ ② 「把一个点变成一片」✅、四名字全但没配场景 ③ ✅ 写推改读拉

**完整答案**：幂律 = 少数 key 占绝大多数流量；分片失效 = 加再多机器流量还是全压持有热 key 的那一台。四手段配场景：**加盐→写热点（计数器）、本地缓存→读热点（配置/热门内容）、只读副本→读多写少、请求合并→读击穿**。Bieber：发一条推 = 几千万次写入；**混合策略**：普通用户仍写扇出，超级大 V 读时拉取——「对热点，把写时打散到千万处换成读时从一处拉取」

**📌 复盘总结**
- **缺口本质**：四手段没配场景——用的时候关键是「什么热点用什么招」
- **记忆钩子**：「写热点加盐、读热点缓本地、读多写少上副本、读击穿做合并」

## Q4 · 尾延迟（1.75/3，本轮最大问题）

**原题**：① 平均数为何骗人 ② 36.6% 含义 + 最反直觉结论 ③ 对冲请求

**你的回答**：① 答成「等最慢的」❌（那是扇出，串台）② 前半 ✅ 后半答「利用率高变慢」❌（那是排队论，又串台）③ ✅ 等 p95 补发 + 2~5% 负载

**📌 复盘总结**

## Q5 · 排队与 USL（2.75/3，本轮最佳）

**原题**：① 95% 利用率为何爆炸 + 闲着 30% 是浪费吗 ② Little 定律一句话 + 票务类怎么预留 ③ USL 为何递减 + 好的规模化设计本质

**你的回答**：① 直觉 ✅、留余量 ✅、爆炸形状没透 ② ✅ 一字不差（L=λW）、按峰值 ✅ ③ ✅ 协调开销 + 「加进来的机器不需要通信」

**完整答案**：排队时间 ∝ 1/(1−ρ)：ρ=90% 因子 10、**99% 因子 100**——到达随机、没余量消化波峰，波峰一来排队，队列拖慢后面的（正反馈），直到延迟趋于无穷。Little 定律：排队人数 = 到达速度 × 平均停留时间；开售即洪峰的系统**按峰值而非均值预留**。USL：厨师太多抢灶台，协调开销吃穿收益甚至变负。收束：**好的规模化设计，本质是让加进来的机器尽量不需要互相说话**

**📌 复盘总结（强项固化）**
- **为什么答对**：排队论直觉扎实，收束句命中主线
- **还差一步**：爆炸的形状是 1/(1−ρ) 因子从 10 到 100，不是线性上升

# 第 16 轮 · 第 15 章组织即架构检验（9.75 / 18 ≈ 54%）

> 进阶篇第 6 章检验，首次采用「逐题出题、逐题判分」节奏（用户要求分开问）；用户自评状态「比较着急」。主干概念（买造尺子、逆康威、平台收外在负荷、拆分信号）已立住；丢分集中在一处：**只复述了结论句，机制段落缺席**——54% 是「背结论 vs 懂机制」的差价。

## Q1 · 解不干净的耦合（1.5/3）

**原题**：支付/风控两个服务缠死，两轮代码解耦都失败；组织里两边 KPI 绑定、每周三次联合作战会。① 用康威定律解释为何注定失败（机制层）② 下一步动作

**你的回答**：① 「沟通频繁→耦合度高、没有明确契约」（只有相关性，没有机制与「注定」的动态）② 「确立清晰契约→组织就不用频繁开会」（因果倒置：把契约当降低沟通成本的开关）

**完整答案**：① 机制：接口是沟通的**化石**——沟通便宜（随时能问），没人有动力把接口一次谈死，随手直读库最省事→边界必然模糊；且是**动态注定**：重构出干净边界，下周两边一商量「直接读你的库最快」又被捅穿——只要「随时能改」的组织便利在，代码边界会被日常协作一次次压回耦合形状 ② 先改组织：拆开 KPI、降会议频率、明确 ownership——沟通成本升上来接口才自然变硬，**这时**的代码重构才立得住；或反向诚实判断：KPI 深绑+实时依赖=业务上本是一体，合并成一个团队/服务（「边界不该存在」也是合法答案）

**📌 复盘总结**
- **缺口本质**：① 相关性≠机制，没答「化石」与动态回压；② 因果倒置——契约是沟通成本高的**产物**，不是让沟通停下的**开关**（与「补偿前先确认」同构的顺序病第三例）
- **记忆钩子**：「契约是化石不是开关——先改沟通，化石才变硬；化石硬不硬，别怪雕刻刀」

## Q2 · 逆康威 + 四词复测（2/3）

**原题**：六年单体+职能分团队（前端/后端/DBA），要改成按业务能力独立部署。① 传统顺序直接拆会长出什么系统、为什么 ② 逆康威第一步 ③ 「订单查询」先切 10% 流量观察再放量是哪招（点名先归位四词再指认）

**你的回答**：① 「一个功能三个组才能上线，效率低下」（答的是现状问题，不是拆后形态）② 按业务能力拆团队 ✅ ③ 「逐步切是绞杀者」（主干对；四词归位没输出，漏了灰度叠加）

**完整答案**：① **分布式单体**：组织还是职能竖井，康威不管架构图怎么画，系统镜像的是沟通结构——服务边界对不齐业务边界，函数调用全变网络调用，发布照样联合排期+平添分布式全部苦头：耦合没消失，升级成跨网络的耦合 ② 按业务能力垂直切**全栈小队**（自带前后端+数据），服务边界=团队边界 ③ 主干=绞杀者（整块功能从旧实现逐块迁流），叠加=灰度（10% 起步观察再放量）；双写=数据过渡、expand-contract=结构演进，本题不涉及

**📌 复盘总结**
- **缺口本质**：①「分布式单体」这个投影结论不在默认词库里；③ 点名要四词归位仍没输出——知道但不在默认动作里（上轮完全混淆→本轮主干认对，部分改善）
- **记忆钩子**：「职能竖井+拆服务=分布式单体（函数调用升级成网络调用的耦合）」

## Q3 · 溢出的桶（2.5/4）

**原题**：8 人团队管 12 个服务，四种症状：①说不清整体②30% 工时耗在自建 CI/K8s③上午支付下午搜索④疲于救火。① ②③分别是哪种负荷、①④说明什么 ② 至少两类 Team Topologies 干预

**你的回答**：① ②外在 ✅、③内在 ❌（是切换负荷）、①④「需要拆分组织架构」（方向对但粗）② 平台工程去外在 ✅、「拆分组织简化内在」（内在是分摊不是简化）

**完整答案**：① ②外在负荷（偶然复杂度，平台该收走）③**切换负荷**（上下文横跳，边界没切好的代价；内在负荷=业务领域本身的复杂度，省不掉）①④=桶已溢出的信号（疲于救火、没人说得清整体；8 人管 12 服务本身就是超载形态）② 平台团队收走外在负荷；按业务线切流式对齐团队（支付/搜索/通知各一队）——内在负荷**分摊**到更多桶、切换负荷随之消失；灵魂顺序：**先问哪个桶爆了，再决定拆什么**

**📌 复盘总结**
- **缺口本质**：三种负荷的定义边界没吃透（横跳≠领域复杂度）；「拆分简化内在」——内在省不掉，只能分摊到更多桶
- **记忆钩子**：「内在省不掉、外在该收走、切换说明缝切歪了；先问哪个桶爆了再拆」

## Q4 · 十二个人的微服务冲动（1.25/4）⚠️ 审题纪律回潮

**原题**：12 人（后端 3）单发布线运行良好。CTO 三论点：①单体丑该拆显得先进②早晚要拆不如现在拆③AI 扛得住。逐条回应（对在哪错在哪）+ 什么信号才真该拆

**你的回答**：「都在用同一条发布线所以可以拆分，但需要按组织拆分」+「调试发布需要多团队协调同步」（第一句方向反了：一条发布线恰是**不拆**的理由——没有互相阻塞；三论点未逐条回应；信号方向对）

**完整答案**：① 错在拿审美当尺子——架构依据是质量属性与约束，「丑」不是质量属性；一条发布线=没有互相阻塞，单体是正确形态不是将就 ② 对一半：30 人时大概率要拆；错一半：预支复杂度——现在拆换不到任何自治收益，且 30 人时业务边界长什么样现在不知道，现在画的边界大概率是错的；正解=先做**模块化单体**零成本把缝划对、被真实业务捶打 ③ 对一半：AI 确实撑大了认知负荷的桶（代劳偶然复杂度）；错一半：判断式没变——`团队互相阻塞的痛 > 分布式复杂度的痛`，现在左边是零，零不参与比较；AI 扛得动写代码，扛不掉部分失败排查、可观测性建设这些分布式**固有苦头**（不是知识量问题，是架构复杂度本身）。真该拆的信号：①团队多到互相阻塞（发布排同一条队、联调会议挤占开发）②认知负荷爆桶（疲于救火）——看信号不看日期

**📌 复盘总结**
- **缺口本质**：题目点名「三个论点逐条」只交两句——审题纪律第三轮回潮；且「一条发布线」信号读反（它是没有阻塞的证据，不是可以拆的证据）
- **记忆钩子**：「拆分的理由不在代码里，在日历上——看发布排期排多长、联调会议开到几点」

## Q5 · 买还是造 + 契约边界（2.5/4）

**原题**：直播电商。A 视频转码 / B 实时推荐算法（GMV 命脉），CFO 全自建、CTO 全买。① 各自该自建还是买、尺子是什么 ② 对买的那个：稳定契约接进来的纪律；供应商旧 API 六个月后下线怎么撑

**你的回答**：① A 买 B 自建 ✅（尺子名字没报出来）② 「买的接口不能修改，做一个中转层/对阶层，后续绞杀者或灰度」（中转层摸到 ACL 但名字没出；「不能修改」因果反了；绞杀者/灰度用词错位——那是对自家旧系统的手法）

**完整答案**：① 尺子=**是不是差异化核心**（本质：这块认知负荷值不值得占用团队的脑容量）；A 转码是成熟商品能力→买；B 推荐是 GMV 命脉→自建+养团队 ② 纪律=选契约严肃的供应商（版本化/向后兼容/废弃走流程）+自己这侧架**防腐层（ACL）**做翻译+隔离，绝不深度耦合；六个月下线：变化关在防腐层内——系统只依赖自定义的稳定接口，供应商换版本只改层内翻译逻辑（层后并新 API 适配器验完切换，抽象分支在层内小规模重演）

**📌 复盘总结**
- **缺口本质**：判断全对但概念名词挂不上（中转层→防腐层）；手法适用域混淆（绞杀者用于自家旧系统迁移，不用于接外部供应商）
- **记忆钩子**：「外部供应商的变，关在防腐层里；换版本只动层内翻译」

# 缺口补全自查卡：看到 X，立刻想 Y

> ✅ 本卡已提升为技能正式附录并补全进阶篇（10–12 章）反射条目：[references/appendix-reflexes.md](references/appendix-reflexes.md)。日常使用以附录版为准；以下为十轮拷问收官时的历史快照。

把全部缺口压缩成条件反射。日常做架构决策前扫一遍：

| 触发场景 | 条件反射 |
|---------|---------|
| 算出 QPS/容量数字 | 先问「这真的是问题吗」（证伪复杂度），再算扇出、再算数据总量 |
| 看到「一对多」业务关系 | 算写放大：推/拉/推拉结合；长连接系统扩容指标是连接数不是 QPS |
| 看到数字（QPS/写量） | 先问「读还是写」——同数字不同性质，结论相反 |
| 看到「剩余 N 个」 | 限量发放族 → 强一致+原子扣减（库存/券/名额/预订全同族） |
| 判一致性 | 三把尺子依次过：①赔钱吗 ②能自愈吗 ③是 hint 还是判定；同一数据不同用途分档 |
| 需要对账的数据 | = 错了不会自愈 = 强一致 |
| 写瓶颈 | 复制和缓存直接出局；分片前先消解：「为什么有这么多写」 |
| 任何最终一致承诺 | 必配兑现机制：对账 / ack+重试；「最终」不会自己到达 |
| 超时 | ≠ 失败；置「未知」，查询收敛，对账兜底 |
| 会被重试的写操作 | 幂等三要素：调用方签发键、唯一约束验票、键是动作身份证；**查重和写入必须原子——用唯一约束，不用先查后写** |
| 既改库又发消息 | 双写陷阱：先写谁都漏窗口（丢消息/幽灵消息）→ Outbox 同一本地事务，重试补不上结构缺口 |
| 客户端先写的请求 | 两把尺子：决定权在谁？涉钱涉权限吗？客户端可以是仓库，不能是法官 |
| 多端/离线同步 | 操作日志 + 游标（只传增量）+ 墓碑（两端不物理删） |
| 并发写冲突 | 先问能不能存操作而非状态（冲突自动消解）；累加型禁用 LWW |
| 要防碰撞/防重复 | 先想结构不相交（命名空间隔离/唯一约束），别做先查后写 |
| 给缓存设 TTL | 先问：数据不可变吗？不可变→永不过期；可变→逻辑过期/抖动 |
| 两个需求冲突 | 先问能不能消解（正交通道/状态分级/客户端副本），消解不了再给带价签选项 |
| 给老板/业务方出方案 | 菜单不是报价：方案/他得到/他付出/成本，至少三条路；绝不说「做不到」 |
| 画图框超 9 个 | 拆论证不是合并框；一张图一个结论，箭头标方向和含义 |
| 两个模块解耦不干净 | 先看人：owner 是谁、沟通多紧密；逆康威先组团队再拆系统 |
| 想照搬成熟架构 | 先比约束：团队/流量/成本/生命线；「不加会死吗」问到系统还需不需要存在 |
| 打散/分片/分段 | 第二层账单：倾斜+再平衡是出厂配套 |
| 两种访问形态冲突 | 两套存储（CQRS）；不为 1% 查询毁 99% 主路径 |
| 重要决策落地 | 写 ADR：「放弃了什么」是独有价值；技术债三件事：借、记账、排期还 |
| 昂贵资源在运转 | 问：这一秒它在为谁工作？那个人还要这个结果吗？（不要则 abort） |
| 拆分/并行方案 | 先数通信：传几次、传多少；通信模式决定部署边界 |
