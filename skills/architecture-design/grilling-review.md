# 第 1 轮 · AI 对话产品（2.5 / 5）

> 知识本体：[templates/02-ai-chat-product.md](templates/02-ai-chat-product.md)（决策 2/3/6/7/8）；各题「完整答案」已删知识重述，只留结论 + 指针。

## Q1 · Prefill 和 Decode 混批会发生什么？

**原题**：LLM 推理分 Prefill（算 prompt，吃算力）和 Decode（逐 token 生成，吃带宽）。新请求的 Prefill 和一堆老请求的 Decode 混在同一个 batch，会发生什么？如果你是调度器怎么处理？

**你的回答**：先处理 Decode，Prefill 等待。→ 被追问「你的首字延迟 <1 秒目标还守得住吗」后改答：将 Prefill 切片和 Decode 一起推理。

**答案**：保 Decode→TTFT 崩、保 Prefill→吐字卡顿 → **chunked prefill**（大切块与 decode 混排，两边不饿死）。〔02 模板·决策 2〕

**要点**：✅ 过（先错后对）

**📌 复盘总结**
- **缺口本质**：第一反应只盯住一头目标（保 Decode 流畅），没意识到 TTFT 同样是硬指标——两个目标抢同一块资源时，「让一方排队」永远不是答案
- **补全链路**：识别两类任务（prefill 吃算力 / decode 吃带宽）→ 确认双方都有延迟 SLA → 把大任务切碎混排 → 两边都不饿死
- **记忆钩子**：「两类任务抢同一资源、谁都等不起 → 切碎混排」。磁盘 IO 混合、数据库读写混布同理

## Q2 · 显存满了，踢谁的 KV 缓存？

**原题**：显存满了，新会话要分配 KV 缓存。现有：A 一个 10 分钟没动静的会话、B 正在生成中的请求、C 几百个会话共享的系统提示前缀缓存。驱逐优先级是什么？被踢的 A 若 5 分钟后回来会怎样？

**你的回答**：先答 C→A→B（先踢公共前缀）→ 被追问「你确定要第一个踢掉一份成本、几百倍收益的东西？」后改答 A→C→B。

**答案**：驱逐序 A 不活跃→C 公共前缀→B 生成中；判据=重建成本÷占用空间（非活跃度）；A 可 offload 到 CPU 不必真删。〔02 模板·决策 3〕

**错误要点**：❌ 「先踢公共前缀」是典型错误——共享缓存的性价比被会话数摊薄放大，是最不该先踢的。

**📌 复盘总结**
- **缺口本质**：直觉用「活跃度」（LRU 思维）当驱逐依据，没算重建成本的杠杆——共享前缀空间小、重建收益被几百个会话分摊放大
- **补全链路**：驱逐顺序 = 重建成本 × 重建概率 ÷ 占用空间 → 共享缓存性价比最高放最后 → 正在生成的重建成本无穷大（已烧的 GPU 白费）永远最后
- **记忆钩子**：「驱逐看重建性价比，不看活跃度」。加分项：被踢的可 offload 到 CPU，不必真删

## Q3 · 70B 模型 4 张卡，按层拆还是每层切开？

**原题**：A）按层拆（流水线并行 PP）B）每层矩阵横切（张量并行 TP）。各要传什么数据、传输量谁大？哪种对卡间网络要求高？4 张卡跨机器走以太网选哪种？

**你的回答**：「肯定是张量并行，卡之间不需要传递太多信息，只需要最后组合答案」——**答反了**。追问后纠正：跨机以太网选流水线并行。

**答案**：TP 每层 all-reduce（80 层=每 token 80+ 次，NVLink 只能机内，通信最重）；PP 层边界传激活（以太网可忍，代价气泡）；跨机选 PP，大规模机内 TP + 机间 PP。〔02 模板·决策 7〕

**错误要点**：❌ 这是最经典的认知错误，模板里已标为「❗ 最常见的认知错误」。

**📌 复盘总结**
- **缺口本质**：把 TP 想象成「分工后最后合并」，没看到层间数据依赖——每一层的输入都是上一层的**完整**输出，切了就必须每层同步
- **补全链路**：先画数据依赖 → 数通信：TP 每层 all-reduce（80+ 次/token）、PP 只在层边界传激活（3 次）→ 通信量决定网络要求 → 决定部署边界
- **记忆钩子**：「通信模式决定部署边界」。任何分布式拆分前先算「传几次、传多少」

## Q4 · 模型路由悖论：谁判断问题难不难？

**原题**：简单问题给小模型省钱，但「谁来判断难度」？用大模型判断=多花钱，用小模型判断=学渣不知题超纲，用规则判断=「证明黎曼猜想」只有 12 字。怎么设计路由器？

**你的回答**：两步走，都答对了——
1. 「不对问题路由，对**任务**路由：大模型形成任务列表，按难度路由」（Agent 场景）
2. 追问单轮请求（占 C 端 80%）后：「小模型先答，特定小模型判断是否好，不好再升级重答」

**答案**：任务级路由（规划顺带判难度，零成本）+ 级联路由（小模型先答→Judge→不合格才升级）；级联省钱，付的是最慢那批尾延迟翻倍。〔02 模板·决策 6〕

**要点**：✅ 本轮最漂亮的一题（把「问题路由」重框为「任务路由」是有实践经验的人才会有的反应）

**📌 复盘总结（强项固化）**
- **为什么答对**：有 agent 实践，会重新框定问题（对问题路由 → 对任务路由），被提示后能自己推出级联
- **还差一步**：级联的代价要主动说——尾延迟翻倍（最慢那批请求为省钱买单）
- **记忆钩子**：「判断答得好不好，比预判难不难容易得多」

## Q5 · 用户流式对话到一半关掉浏览器，GPU 在干什么？

**原题**：流式输出到 300 字时用户关浏览器。① GPU 知道用户走了吗？会算完剩下 700 字吗？② 烧掉的算力谁付钱？③ 怎么设计让 GPU 尽快知道「人走了」？

**你的回答**：「继续计算，生成后保存结果，通知用户」❌；补救机会时答「应该有停止按钮」❌。

**答案**：cancellation 沿链路传播（SSE 断→网关→编排→引擎踢出 batch+释放 KV）；不 abort 三重代价；两场景=断连/同会话新消息；停止按钮解决不了。〔02 模板·决策 8〕

**错误要点**：❌ 未答出。暴露「成本意识不彻底」——嘴上说 token 都是钱，遇到具体场景第一反应是「贴心地算完」。纪律：**这一秒 GPU 在为谁工作？这个人还要这个结果吗？**

**📌 复盘总结**
- **缺口本质**：「服务要完整」的惯性——把用户当成必须服务到底的对象，没想「这个请求还有没有主人」；还想用产品补丁（停止按钮）代替架构保证
- **补全链路**：资源在服务谁 → 人走了/不要了 → 立刻 abort 释放槽位+KV → 沿链路传播（SSE 断→网关→编排层→推理引擎）；两个场景：断连、同会话新消息进来
- **记忆钩子**：「这一秒 GPU 在为谁工作？他还要这个结果吗？」架构不能假设用户守规矩

# 第 2 轮 · 短链接服务（3 / 5）

> 知识本体：[templates/01-url-shortener.md](templates/01-url-shortener.md)；各题「完整答案」已删知识重述，只留结论 + 指针。

## Q1 · 6 位短码空间多久用完？用完那天发生什么？

**原题**：Base62 六位 ≈ 568 亿空间，每天新增 1000 万条。① 多久用完？② 用完那天发生什么？③ 上线前该做什么设计？

**你的回答**：① 5680 天 ✅ ② 「短码会重复」❌ ③ VARCHAR、正则 `{6,}`、按最长位数预留 ✅

**答案**：568 亿÷1000 万=5680 天≈15.5 年；不会重复，是位数静默 6→7（要变长兼容非冲突检测）；上线前全链路（VARCHAR/正则 {6,}/前端 SDK 二维码）不假设固定长度；位数由「日增量×寿命」反推。〔01 模板·短码位数〕

**错误要点**：❌ 「会重复」导致设计错防御方向

**📌 复盘总结**
- **缺口本质**：把「空间耗尽」想成「碰撞」，没推演自增 ID 的唯一性——真正发生的是编码位数静默增长，而炸点是全链路所有「假设 6 位」的地方
- **补全链路**：自增 ID 唯一 → 编码也唯一 → 变的是位数 → 扫全链路长度假设（定长字段/正则/前端/二维码）→ 上线前预留变长
- **记忆钩子**：「固定容量资源，上线前就用日增量×寿命算耗尽日；全链路不假设长度」

## Q2 · 热点 key TTL 到期瞬间，50 万请求涌入

**原题**：千万粉大 V 转发的短链 10 秒 50 万点击，TTL 正好此刻到期。① 发生什么？② 数据库承受几次查询？③ 怎么设计不打死数据库？

**你的回答**：缓存击穿 ✅、50 万次 ✅、加锁只放一个回源 ✅。追问「499,999 个请求等锁会不会打死应用服务器」时答「双份缓存」❌。

**答案**：三做法——热点 key 永不过期（映射不可变直接不设 TTL）/ 逻辑过期（存 expire_at，读到过期返旧值+后台刷新）/ TTL 随机抖动（只防雪崩）。关键洞察：你说过「短链映射不可变」——那为什么给它设 TTL？把缓存一致性惯性套到了不需一致性的场景。〔01 模板·缓存 + 05 章缓存三难〕

**错误要点**：❌ 这是裂缝②（有结论不主动调用）的**第一次出现**：教练模式说对了「不可变」，实战场景没把它用上。

**📌 复盘总结**
- **缺口本质**：把「缓存需要维护一致性」的思维惯性套到不可变数据上；「不可变」的结论停在记忆里，没变成设计红利
- **补全链路**：数据不可变 → 缓存永远不会旧 → 不需要 TTL → 不会过期 → 击穿不存在。不是解决击穿，是让击穿没有发生条件
- **记忆钩子**：「与其解决问题，不如让问题没有条件发生」——与消解扇出同源。设 TTL 前先问：这数据不可变吗？

## Q3 · 自定义短码和自增短码会撞车吗？

**原题**：企业客户可指定 `sho.rt/spring-sale`。① 和自增生成的短码在同一命名空间，会撞车吗？举个场景。② 怎么设计不打架？

**原题**：用户希望 <100ms 看到「已发送」，但消息必须可靠送达一条不丢。① 为什么冲突 ② IM 有没有别的系统没有的资源让两者都满足 ③ 「绝对不丢」靠客户端做什么+服务端做什么

**你的回答**：① 对 ② 把 Q2 答案套过来 ❌，提示后答「缓存」❌ ③ 「客户端还要写其他人的信息」❌——记未答出

**答案**：延迟 vs 持久性冲突；IM 独有资源=**客户端本身是持久副本**（非缓存：缓存丢了回源、副本丢了数据没了；本地 SQLite+待发队列）；状态分级=把一条时间线拆两条（发送中客户端落库 0ms 满足立刻反馈 / 已发送服务端 ack 满足不丢）——**微信双勾号是架构决策的 UI 投影**；消息 ID 客户端生成+服务端唯一约束→重传 100 次只存一条（结构保证）。〔05 章·客户端持久副本 + 05 模板·IM 状态分级〕

**错误要点**：❌ 暴露心智模型缺失：把客户端当「展示层/缓存」而不是「参与可靠性保障的副本节点」——这促成了下一轮专项训练

**📌 复盘总结**
- **缺口本质**：这是心智模型缺口，不是知识点缺口——客户端被当成「缓存/展示层」，所以「立刻反馈」和「绝对不丢」在你眼里无解，只能二选一
- **补全链路**：两要求抢同一个返回时刻 → 拆成两条时间线（状态分级）：客户端本地 0ms 满足「立刻」、服务端 ack 满足「不丢」→ 各走各的时间线，两个都拿到
- **记忆钩子**：「微信双勾号是架构决策的 UI 投影」；「客户端可以是仓库」——本地 DB 不是缓存

## Q5 · 永久保存 + 全文搜索 + 压成本

**原题**：老板要求聊天记录永久保存、全文搜索秒出、成本压一压。① 哪两个冲突最尖锐 ② 给 3 个带价签的选项 ③ 推荐+理由 ④ 哪个是底线、哪个是优化项

**你的回答**：冲突说「永久保存 vs 成本」❌；选项给的是散文不是表 ❌（又说了一次「难以实现」）；推荐「周期性遗忘+付费订阅」✅（商业解，有产品意识）；「成本是底线」❌。追问后：分层存储 ✅（主动从「多层缓存」联想到——裂缝②首次改善）、底线改答隐私合规 ✅

**答案**：最尖锐冲突=全文搜索 vs 成本（倒排索引是原始 1~3 倍且必须放贵存储）；99% 查询打最近 5% 数据→冷热分层；选项表(A 全量热存极高 / B 冷热分层降 80~90% 推荐 / C 免费3月+付费永久)推荐 B+C；你卡在列「报价」（每条多贵）而非「菜单」（有哪几条路）——**写不出三个方案=没想清楚**；成本是约束不是底线，IM 底线是隐私合规。〔05 模板·IM 冷热分层 + 06 章·报价 vs 菜单〕

**📌 复盘总结**
- **缺口本质**：「难以实现」第二次出口；列的是「每条需求多贵」（报价）不是「有哪几条路」（菜单）；把成本当底线
- **补全链路**：冲突先定位最尖锐的（搜索 vs 成本：索引是 1~3 倍且必须放贵存储）→ 问访问分布（99% 打最近 5%）→ 冷热分层 → 三行带价签表
- **记忆钩子**：「报价是『这事多难』，菜单是『有这几条路，你拍』」；「成本是约束，底线是不可谈判的质量属性」

# 第 5 轮 · 专项训练：客户端/边缘作为副本（3.5 / 4）

> 知识本体：[references/05-data-and-state.md](references/05-data-and-state.md)（客户端作为副本：操作日志/同步游标/墓碑/LWW 边界）；各题「完整答案」已删知识重述，只留结论 + 指针。

## Q1 · 飞机上记 5 笔账、删 1 笔，落地开网后怎么同步？

**原题**：记账 App，完全无网时记了 5 笔、删了 1 笔。① 存在哪里？存的是最终状态还是别的？② 开网时客户端发什么、服务端提供什么接口（和普通 CRUD 有何不同）？③ 网页端也记了 3 笔，客户端怎么知道「服务端有哪些我还没有的变更」？

**你的回答**：① 存本地、**存操作日志而非最终状态** ✅（视角已建立）② 发操作序列 ✅ ③ 「通过操作日志」❌（没答出机制）；提示「你昨天自己说过」仍没接上 ❌。删除问题答「本地标记、同步到服务端真实删除」——前半对后半错 ❌

**答案**：③=同步游标（服务端分配单调递增 seq，客户端记 last_synced_seq，上传 POST /changes + 下载 GET /changes?since=X 只传增量）——一个模式三场景（群聊已读/离线同步/短链日志补算）；删除=墓碑（tombstone），服务端也不能物理删（否则平板联网把删除的账又传回去=复活），保留期后 GC；**分布式同步最难的是删除**（「不存在」没法传播，只能用「一条说明它不存在的记录」传播）。〔05 章·同步游标 + 墓碑〕

**错误要点**：❌ 同步游标是裂缝②第三次出现（明确提示仍没调用）；墓碑后半错

**📌 复盘总结**
- **缺口本质**：「读游标」没被跨场景检索到（提示了仍没接住）；墓碑只想客户端侧，没想到服务端物理删会让删除复活
- **补全链路**：同步靠游标（只传增量：GET /changes?since=X）→ 删除靠墓碑（用「一条说明不存在的记录」传播）→ 两端都不能物理删 → 墓碑保留期后 GC
- **记忆钩子**：「一个模式三个场景：群聊读游标/离线同步游标/短链日志补算」；「同步里最难的是删除」

## Q2 · 手机改 100、网页改 200，都离线——LWW 丢了什么？

**原题**：① Last-Write-Wins 丢了什么、用户后果？② 更隐蔽的坑：时间戳是谁的时钟？③ 什么数据绝对不能用 LWW？为什么？

**你的回答**：① 静默丢失 ✅ ② 客户端时钟不可信 ✅ ③ 例子对（余额）但理由错（「必须串行处理」❌）。追问后三问全对，且**把两题串起来** ✅✅

**答案**：LWW 三坑（静默丢失/客户端时钟不可信/服务端时间也不完美→严格解版本向量）；累加型（余额/计数）每个操作都携带信息、丢一个错一个，禁用 LWW；覆盖型（备注/标题）可 LWW；**存操作日志而非最终状态，冲突自动消解**（+100 和+200 都执行=300，不需问谁赢）=CRDT 核心。〔05 章·LWW 边界 + 存操作而非状态〕

**要点**：✅ 本轮最佳回答

**📌 复盘总结（强项固化）**
- **为什么答对**：LWW 三个坑全对；最漂亮的是自己把两题串起来——存操作而非状态，冲突自动消解
- **还差一步**：第一版理由给的是「串行处理」（那是手段不是原因，且和离线前提矛盾）——原因要到数据性质里找：累加型丢一个就错一个
- **记忆钩子**：「存操作而非状态，冲突自动消解」（op-based CRDT）；累加/集合型不能 LWW，覆盖型可以

## Q3 · 边界题：电商能不能离线先下单？

**原题**：把「客户端副本+离线优先」用到电商：离线下单付款、联网同步。① 离线下单 5 件，联网发现只剩 2 件，操作日志还能无脑重放吗？② 离线点「支付」，本地显示成功页，联网后发生什么？③ 「客户端作为副本」的边界在哪？什么数据可以先写后同步？

**你的回答**：① 不能，拒绝付款 ✅ ② 漏了最致命的一点 ❌ ③ 判据「是否需要强一致」方向对 △

**答案**：②假的成功页=产品灾难（比一开始拒绝糟百倍，制造愤怒用户）；两把尺子——①决定权在谁（用户独占✅可离线先写 / 争抢共享资源❌ / 第三方确认❌）②客户端不可信（本地数据能改，涉钱权限判定不采信，客户端=外部输入）；电商折中=照搬 IM 状态分级但「成功」话语权留服务端（离线显示「已保存待提交」，绝不显示「下单/支付成功」）——**客户端只能盖「我记下了」，不能盖「事情成了」**。〔05 章·离线先写两把尺子〕

**📌 复盘总结**
- **缺口本质**：只想技术不一致，没想用户认知——假的成功页 = 承诺，事后推翻比一开始拒绝糟糕一百倍；判据方向对但没磨锐
- **补全链路**：两把尺子：① 决定权在谁（自己独占✅/争抢❌/第三方❌）② 客户端不可信（涉钱权限判定不采信）→ 状态分级手法可用，但「成功」盖章权在服务端
- **记忆钩子**：「客户端只能盖『我记下了』，不能盖『事情成了』」；每个方案多问一句「用户会看到什么、会误解成什么」

## Q4 · 六项操作分类：哪些能离线先写？

**原题**：A 笔记加标签、B 给朋友动态点赞、C 修改自己的昵称、D 领限量优惠券、E 协同文档编辑一段文字、F 待办打勾。C 和 B 有微妙之处。

**你的回答**：A✓ B✓（理由尤其好：点赞决定权在自己且可撤销）C✗ D✓ E✓ F✓——5/6

**答案**：C 昵称踩坑——昵称是「你自己的数据」，但加了全局唯一约束就变成「争抢共享资源」（甲乙都改「架构师」必有一个失败）；**「用户自己的数据」≠「用户能独立决定」**，判据关键=操作成功是否依赖别人的状态；正确做法=可离线编辑但显示「待生效」，或把唯一 ID 和可重复显示名拆开；与限量发放族同源（唯一性约束把私有数据变争抢资源）。〔05 章·离线先写尺子〕

**📌 复盘总结**
- **缺口本质**：判据停在「数据属于谁」，没问「操作的成功是否依赖别人的状态」
- **补全链路**：看到「自己的数据」再多问一句：有全局唯一约束吗？→ 有就是争抢资源 → 可离线编辑但不能宣布成功（显示「待生效」）
- **记忆钩子**：「唯一性约束把私有数据变成争抢资源」——与限量发放族同源

# 第 6 轮 · IM 模板验证（3.5 / 5）

> 知识本体：[templates/05-group-chat-im.md](templates/05-group-chat-im.md) + [references/05-data-and-state.md](references/05-data-and-state.md) + [references/11-data-consistency-engineering.md](references/11-data-consistency-engineering.md)（CQRS）；各题「完整答案」已删知识重述，只留结论 + 指针。

## Q1 · 网关 C 整台崩了，路由表还写着「U→C」

**原题**：① 投递指令送到已崩的网关 C，消息丢了吗？② U 重连到网关 A，路由表何时更新？③ 窗口期发给 U 的消息去哪了？什么机制兜住？

**你的回答**：三个场景判断都对 ✅；追问「为什么敢转存离线信箱」答「为了不丢失/避免重传」❌（说成结果，不是前提）

**答案**：①不丢（投递失败转存离线信箱）②重连时网关更新路由表③窗口期消息一直在存储里，重连带 last_synced_seq 一拉补齐；因果方向——**「先落库」是让消息在投递前就成为「系统里确定存在的事实」，投递降级为可失败任意多次的尝试**（先投递再落库则网关崩时消息凭空蒸发）；「不丢」是前提带来的结果不是前提本身。〔05 模板·先落库再投递〕

**📌 复盘总结**
- **缺口本质**：背了结果（「不丢」），没说出前提——因果方向反了
- **补全链路**：先落库 → 消息成为「系统里确定存在的事实」→ 投递降级为「可以失败任意多次的尝试」→ 失败可转存/重投/等拉取；窗口期无需特殊处理
- **记忆钩子**：「先让它成为确定的事实，投递才可以失败重来」；「不丢」是结果，「先落库」是前提

## Q2 · presence 最终一致，读到过时状态会怎样？

**原题**：路由表最终一致+TTL。情况甲：说在线实际刚掉线 → 投递到没有这条连接的网关；情况乙：说离线实际刚上线 → 消息转存离线信箱+发了推送。① 甲消息丢了吗？② 乙算 bug 吗？③ presence 可最终一致的边界在哪？

**你的回答**：① 没丢（已落库+无 ack 会转存）✅ ② 不算 bug，「靠 ack 决定是否补推送」✅（实践标准做法）③ 判据「不影响用户体验」❌——尺子太软

**答案**：软尺子「不影响体验」筛不掉东西，用锐尺子（赔钱/自愈）验——甲投递失败转存能自愈、乙多推送只是噪音能自愈；presence 能最终一致的真因=**它不是权威、错了会被兜住**（只是投递路径选择依据，两条错路都通向同一正确结果）；**第三把一致性尺子**：hint（路径提示）✅可最终一致（猜错走慢路有兜底）/ 判定依据❌（猜错就错无兜底，如群成员权限）——同一份数据判定用途强一致、展示用途最终一致。〔05 章·hint vs 判定第三把尺子〕

**📌 复盘总结**
- **缺口本质**：又用软尺子（「影响体验」）——刚学的锐尺子（赔钱/自愈）没调用，裂缝②第五次
- **补全链路**：presence 两条错路都通向同一个正确结果（投失败→落库兜住；多推送只是噪音）→ 它是 hint 不是判定依据 → 可以不准
- **记忆钩子**：「能不准不是因为『用户看不出来』，而是因为『猜错有兜底』」；同一份数据两用途两档（权限强/显示弱）

## Q3 · 被踢出群的用户离线三天后联网同步

**原题**：原则 A「客户端是持久副本」vs 原则 B「客户端永远不可信」。用户被踢出财务群、离线三天，带着 `last_synced_seq=1042` 请求 `GET /changes?since=1042`，这三天群里有 200 条他不该看的消息。① 服务端该返回什么？② 他本地已有的旧消息要不要删？③ 两条原则怎么共存？

**你的回答**：① 不返回（返回即越权）✅ ② 不删（数据当时合法+可能重新加群）✅ ③ 「不冲突」方向对，没提炼辖区 △

**答案**：原则 A 管「数据在哪」（客户端可持有/保存/先写后传，是合法存储介质），原则 B 管「谁说了算」（客户端不能判权限/宣布结果/决定拿什么，判定权在服务端）；场景落地=客户端持有旧消息（A）+ 服务端决定返不返新消息（B）——**客户端可以是仓库，但不能是法官**，两原则分管存储和裁决从不冲突。〔05 章·仓库非法官〕

**📌 复盘总结**
- **缺口本质**：说了「不冲突」但没划辖区——原则共存需要明确的分工边界
- **补全链路**：A 管「数据在哪」（持有、先写、后传），B 管「谁说了算」（判权限、宣布结果、决定拿什么）→ 场景落地：持有旧消息（A）+ 服务端决定返不返新消息（B）
- **记忆钩子**：「客户端可以是仓库，但不能是法官」

## Q4 · 分片键 conversation_id 遇上全局搜索

**原题**：消息表按 conversation_id 分片。用户要全局搜索自己所有消息。① 用户在 200 个群，搜一个词要查多少分片？匹配吗？② 要不要改成按 user_id 分片？③ 正确解法？

**你的回答**：① 200 个分片，不匹配 ✅ ② 不要（理由偏软）✅ ③ 「建索引+近三个月放快缓存」❌——在「索引哪些数据」上打转，没答出「索引放在哪」

**答案**：②改按 user_id 分片会毁主路径（群 50 人一条消息写 50 分片，写放大回来了；拉会话跨分片聚合是 99% 读）——**用 1% 搜索毁 99% 主路径是分片键经典错误**；③正解=独立搜索存储按 user_id 组织（消息存储按 conversation_id 分片是真相源，搜索索引按 user_id 是派生数据，异步同步可重建）=**CQRS 读写不同数据模型**；你混淆了「索引放哪怎么组织」（架构）和「索引多少数据」（成本）两个维度。〔11 章·CQRS + 05 模板·IM 搜索〕

**📌 复盘总结**
- **缺口本质**：两个维度混在一起——「索引放哪、怎么组织」（架构）和「索引多少数据」（成本），在后者上原地打转
- **补全链路**：分片键 vs 查询形态不匹配 → 不改分片键（毁 99% 主路径：50 人写 50 分片+跨片聚合）→ 建独立派生存储按查询形态组织，异步同步可重建（CQRS）
- **记忆钩子**：「两种访问形态 → 两套存储」；「不为 1% 的查询毁掉 99% 的主路径」

## Q5 · 500 人内部工具的通知功能，照搬 IM 架构吗？

**原题**：老板说参考 IM 架构做（长连接、不丢、多端同步）。① 照搬吗？哪些必须、哪些浪费？② 算量级，第一个结论？③ 最小可行方案？

**要点**：✅ 这是「工程师惯性」题型的**第三次尝试首次通过**（前两次：6000 QPS 想削峰、30000 写背教条说单体）——先算量级 → 判断不复杂 → 明确砍组件并给理由。该裂缝判定为**已改善**

**📌 复盘总结（强项固化）**

- **还差一步**：可以更狠一问——「这个系统还需要存在吗」（企微机器人可能就够了）
- **记忆钩子**：「先算量级，再看性质，再判要不要照搬模式」；「不加会死吗」问到最后一层

## Q2 · 2PC 最干净，为什么要用 Saga？

**原题**：下单跨库存/订单/支付三服务，同事主张两阶段提交。① 2PC 为什么扛不住（至少两条机制理由）② Saga 换来什么、失去什么 ③ 用了最终一致必须补建什么？为什么「最终」可能永远到不了？

- **记忆钩子**：「大事务 = 全局锁一次搞定；Saga = 每步快进快出、错了倒着退」；「『最终』要有对账兑现」

## Q1 · 双写难题 → Outbox（3/4）

**原题**：改库+发 Kafka 两件事无共同事务。① 先写库再发消息崩了会怎样 ② 先发消息再写库呢 ③ 重试为什么补不上 ④ 正解叫什么、最狡猾的一步

# 第 11 轮 · 第 12 章韧性工程检验（11.75 / 15 ≈ 78%）

> 进阶篇第 3 章检验，连续三章稳定在高位（65% → 80% → 78%）。常识型章节理解扎实，缺口集中在「意思对、名字/要害没钉死」。章节本体：[12 · 为失败而设计：韧性工程](references/12-resilience-engineering.md)

## Q1 · MTBF→MTTR 思维翻转（2.5/3）

**原题**：① 「让它别坏」为什么走不到头 ② 杠杆压 MTBF 端 vs MTTR 端性价比差在哪 ③ 一句话说核心翻转

**你的回答**：① 故障消灭不了 ✅（偏薄）② 对比意思对 ✅ ③ ✅

**答案**：磁盘会坏/网线被挖断/依赖超时/**人手抖打错命令**——Everything fails all the time（包括人）；MTBF 30→60 天代价指数级且有上限，MTTR 30分→30秒靠可设计可演练的工程手段（自动检测/切换/隔离）；「高可用不是祈祷别出事，而是预设一定会出事」。〔12 章·MTTR 翻转〕

**📌 复盘总结**
- **缺口本质**：「故障消灭不了」的清单薄，没点出「手抖」（三个案例的共同根源）
- **记忆钩子**：「韧性不是从不摔跤，是摔了能立刻爬起来、只蹭破一点皮」

## Q2 · 级联失败与三放大器（2.25/3）

**原题**：① 慢 DB→全站 503 的链条 ② 三个放大器 ③ 慢为什么比宕机致命

**你的回答**：① 主线对，漏了火上浇油的重试一步 ② ✅ 三个名字全对 ③ 答「宕机恢复更快」——停在 MTTR 视角

**答案**：链条=慢 DB→B 线程被占→A 超时线程池耗尽→客户端/网关善意重试请求翻 2-3 倍→全链路池耗尽健康接口也没线程→全站 503；三放大器=资源耗尽/重试风暴/超时堆叠；慢 vs 宕机要害=宕机快速失败立刻释放资源，慢让请求抱着资源一点点死、顺调用链把池吸干一节节传染。〔12 章·级联失败三放大器〕

**📌 复盘总结**
- **缺口本质**：链条漏重试放大器；「宕机释放资源、慢占用资源」这个资源维度没答出
- **记忆钩子**：「宕机是断了，大家绕路；慢是堵着，所有人陪着耗」

## Q3 · 熔断/超时预算/降载（2.25/3）

**原题**：① 熔断三态 + 半开为何是灵魂 ② 每层 30s 为何是反模式 ③ 背压 vs 降载 + 来者不拒为何更糟

**你的回答**：① 意思对、名字不准（「全开/失败」）② ✅ 层层递减 ③ 把降载理解成「停止服务」❌

**答案**：熔断三态=关闭/打开/半开（半开是灵魂：冷却后先放一个探子试水，成功→关闭失败→重开；没半开则恢复瞬间积压流量全放出把刚缓的下游再打死）；超时预算沿链路递减（3s→2.5→1.5→0.8）；**背压和降载都不是停服**（背压=向上游说你慢点发，降载=超出的立刻丢 429/503、放进来的好好服务）——会降载的系统过载时仍部分可用。〔12 章·熔断/超时预算/降载〕

**📌 复盘总结**
- **缺口本质**：三态名字不准；「降载≠停止服务」这个要害没钉死
- **记忆钩子**：「降载不是关闸门，是开着闸门但只放一部分进来」

## Q4 · 舱壁 + 重试四件套（2.5/3）

**原题**：① 共享池错在哪 + 最该隔开哪两者 ② 重试四件套 + 无抖动的后果 ③ 没有幂等为何不敢重试

**你的回答**：① ✅ 全对 ② 四样都在 ✅（「有限重试」学名=重试预算），抖动后果含糊 ③ 金额例子 ✅，关键场景没点名

**答案**：共享池被慢依赖像泡水海绵吸干（健康依赖也没线程），最该隔开核心与非核心；无抖动=一千客户端在 1s/2s/4s 整齐一起重试，同步冲击波把刚恢复的下游反复打死；「超时但其实成功」的请求再执行→重复扣款/发货——**没幂等不敢重试，不敢重试瞬时故障就成永久失败**（at-least-once+幂等=效果恰好一次）。〔12 章·舱壁 + 重试四件套〕

**📌 复盘总结（强项固化）**
- **为什么答对**：舱壁核心/非核心判断、重试与幂等的连线，都一次到位
- **还差一步**：抖动的画面是「同步冲击波」，不是「保持峰值」

## Q5 · 降级/错误预算/混沌工程（2.25/3）

**原题**：① 降级前提+三种形态 ② 0.1% 是什么 + 追 100% 为何错 ③ 混沌悖论 + 护栏前提 + 三案例共同剧本

**你的回答**：① ✅ 全对 ② 概念对但只答「做不到」③ 悖论 ✅；护栏答成「科学假设」（那是方法不是护栏）；剧本太压缩

**答案**：降级前提=「掉了会死/能忍」分级在风平浪静时做完，形态=默认值/功能丰富度/异步；错误预算 0.1%≈每月 43 分钟可挂额度，追 100% 错在即使能做到也不该（永远不敢发布实验、迭代归零，用户感知不到 99.9% vs 100%）；混沌工程护栏三前提=有监控看见影响+有爆炸半径控制止损+能一键中止（没护栏注故障叫事故）；三案例共同剧本=微小局部触发顺资源耗尽/自动化连锁/全局推送放大器炸成全局灾难。〔12 章·降级/错误预算/混沌工程〕

**📌 复盘总结**
- **缺口本质**：错误预算的深理由（留迭代空间）没说；护栏前提与方法混淆
- **记忆钩子**：「错误预算是留给冒险的空间」；「别假设，去证明——但没护栏的注入是事故」

# 第 12 轮 · 第 13 章规模化力学检验（11.05 / 15 ≈ 74%）

> 进阶篇第 4 章检验，连续四章稳定在高位（65%→80%→78%→74%）。排队论直觉扎实，最大缺口是尾延迟「两层串台」。章节本体：[13 · 规模化的力学](references/13-scaling-mechanics.md)

## Q1 · 垂直 vs 水平 / 无状态好扩（2.4/3）

**原题**：① 垂直/水平优缺点 + 垂直在做什么 ② 水平的代价 ③ 先问哪句 + 为什么两层成本天差地别

**你的回答**：① ✅（「拿金钱换时间」很接近）② 「从管一台到管一群」✅ ③ 「加的是哪一层？」✅ 原因偏薄

**答案**：垂直=买时间（且不解决单点）；水平代价=从管一台到管一群（互相通信/同步，一致性/分片/再平衡全来）；有状态层贵因它「记得」东西（余额/库存/会话），加一台=两份记忆怎么对上；**加机器不是均匀动作**（无状态加 10 台改一行配置，有状态加 1 台=重新分片+TB 级搬迁）。〔13 章·垂直 vs 水平/无状态好扩〕

**📌 复盘总结**
- **缺口本质**：垂直的「不解决单点」漏了；有状态「两份记忆对不上」的画面没说
- **记忆钩子**：「有人说加机器就行，先问：加的是哪一层？」

## Q2 · 分片与一致性哈希（1.85/3）

**原题**：① 范围/哈希优缺点+判据 ② 朴素哈希致命缺陷 ③ 一致性哈希一句话价值 + vnode 好处

**你的回答**：① 范围的缺点说成「容易雪崩」❌（是易热点；雪崩是缓存词）② 说了结果没说机制 ③ 「只搬 1/N」✅，vnode 只答一个好处

**答案**：范围分片（✓范围查询高效 ✗易热点新数据挤最后段）vs 哈希（✓均匀 ✗范围查询废），判据=查询形态；朴素哈希 N 写死进公式（%4→%5 余数全乱，加一台搬~80%）；一致性哈希加减节点只搬 1/N（只影响环上相邻段）；vnode 两好处=一台挂了负载打散给所有节点（不全压邻居）+异构机器好处理（猛的多放 vnode）。〔13 章·分片/一致性哈希〕

**📌 复盘总结**
- **缺口本质**：术语配错位（雪崩 vs 热点）；机制没说到根（N 写死）
- **记忆钩子**：「朴素哈希把 N 写死——一变全集群地震；一致性哈希只搬 1/N」

## Q3 · 热点与 Bieber 问题（2.3/3）

**原题**：① 负载遵循什么分布 + 分片为何失效 ② 一句话思路 + 四手段配场景 ③ Bieber 问题与解法

**你的回答**：① 幂律 ✅、路由到同一节点 ✅ ② 「把一个点变成一片」✅、四名字全但没配场景 ③ ✅ 写推改读拉

**答案**：幂律=少数 key 占绝大多数流量，分片失效=加再多机器流量还是全压持有热 key 那台；四手段配场景=加盐→写热点（计数器）/本地缓存→读热点（配置/热门内容）/只读副本→读多写少/请求合并→读击穿；Bieber=发一条推=几千万次写，混合策略（普通用户写扇出、超级大 V 读时拉取）——对热点把写时打散千万处换成读时从一处拉。〔13 章·热点〕

**📌 复盘总结**
- **缺口本质**：四手段没配场景——用的时候关键是「什么热点用什么招」
- **记忆钩子**：「写热点加盐、读热点缓本地、读多写少上副本、读击穿做合并」

## Q4 · 尾延迟（1.75/3，本轮最大问题）

**原题**：① 平均数为何骗人 ② 36.6% 含义 + 最反直觉结论 ③ 对冲请求

**你的回答**：① 答成「等最慢的」❌（那是扇出，串台）② 前半 ✅ 后半答「利用率高变慢」❌（那是排队论，又串台）③ ✅ 等 p95 补发 + 2~5% 负载

**答案**：两层分开——①单请求层（99% 请求 20ms、1% 请求 2000ms，平均≈40ms 达标但每 100 用户 1 个转圈 2 秒，平均数稀释少数极慢）②扇出层（(99%)¹⁰⁰≈36.6%，63% 请求撞至少一个慢子调用，**大扇出系统整体 p99 趋近子调用 p999 甚至 p9999**）；对冲请求=等第一个超 p95 才补发谁先回用谁，~2-5% 负载把 p999 从 1800ms 砍到 74ms。〔13 章·尾延迟两层〕

**📌 复盘总结**
- **缺口本质**：⚠️ 两层串台——「等最慢的」放进了「平均数为何骗人」，排队论两次串进尾延迟题
- **记忆钩子**：「平均骗人看分布，扇出等最慢被放大，排队是另一节」

## Q5 · 排队与 USL（2.75/3，本轮最佳）

**原题**：① 95% 利用率为何爆炸 + 闲着 30% 是浪费吗 ② Little 定律一句话 + 票务类怎么预留 ③ USL 为何递减 + 好的规模化设计本质

**你的回答**：① 直觉 ✅、留余量 ✅、爆炸形状没透 ② ✅ 一字不差（L=λW）、按峰值 ✅ ③ ✅ 协调开销 + 「加进来的机器不需要通信」

**答案**：排队时间∝1/(1−ρ)（ρ=90% 因子 10、99% 因子 100）——到达随机没余量消化波峰，波峰一来排队、队列拖慢后面的（正反馈）直到延迟无穷；Little 定律=排队人数=到达速度×平均停留时间，开售即洪峰按峰值而非均值预留；USL=厨师太多抢灶台协调开销吃穿收益甚至变负；**好的规模化设计=让加进来的机器尽量不需要互相说话**。〔13 章·排队/USL〕

**📌 复盘总结（强项固化）**
- **为什么答对**：排队论直觉扎实，收束句命中主线
- **还差一步**：爆炸的形状是 1/(1−ρ) 因子从 10 到 100，不是线性上升

**📌 复盘总结**

- **记忆钩子**：案例四句诀：「S3=护栏下限、Meta=恢复不依赖被恢复系统、Cloudflare=变更要灰度、GitHub=自动化的前提假设会失效」

## Q4 · 工具箱快判（2.5/5）

# 第 16 轮 · 第 15 章组织即架构检验（9.75 / 18 ≈ 54%）

> 进阶篇第 6 章检验，首次采用「逐题出题、逐题判分」节奏（用户要求分开问）；用户自评状态「比较着急」。主干概念（买造尺子、逆康威、平台收外在负荷、拆分信号）已立住；丢分集中在一处：**只复述了结论句，机制段落缺席**——54% 是「背结论 vs 懂机制」的差价。

## Q1 · 解不干净的耦合（1.5/3）

**原题**：支付/风控两个服务缠死，两轮代码解耦都失败；组织里两边 KPI 绑定、每周三次联合作战会。① 用康威定律解释为何注定失败（机制层）② 下一步动作

**你的回答**：① 「沟通频繁→耦合度高、没有明确契约」（只有相关性，没有机制与「注定」的动态）② 「确立清晰契约→组织就不用频繁开会」（因果倒置：把契约当降低沟通成本的开关）

**答案**：①机制=接口是沟通的化石（沟通便宜没人有动力把接口谈死，随手直读库最省事→边界必然模糊），且动态注定（重构出干净边界，下周一商量「直接读你库最快」又捅穿——只要「随时能改」的组织便利在，代码边界被日常协作压回耦合）；②先改组织（拆 KPI/降会议频率/明确 ownership，沟通成本升上来接口才自然变硬、这时重构才立得住），或反向诚实判断（KPI 深绑+实时依赖=业务本是一体，合并成一个团队/服务，「边界不该存在」也合法）。〔15 章·康威化石机制〕

**📌 复盘总结**
- **缺口本质**：① 相关性≠机制，没答「化石」与动态回压；② 因果倒置——契约是沟通成本高的**产物**，不是让沟通停下的**开关**（与「补偿前先确认」同构的顺序病第三例）
- **记忆钩子**：「契约是化石不是开关——先改沟通，化石才变硬；化石硬不硬，别怪雕刻刀」

## Q2 · 逆康威 + 四词复测（2/3）

**原题**：六年单体+职能分团队（前端/后端/DBA），要改成按业务能力独立部署。① 传统顺序直接拆会长出什么系统、为什么 ② 逆康威第一步 ③ 「订单查询」先切 10% 流量观察再放量是哪招（点名先归位四词再指认）

**你的回答**：① 「一个功能三个组才能上线，效率低下」（答的是现状问题，不是拆后形态）② 按业务能力拆团队 ✅ ③ 「逐步切是绞杀者」（主干对；四词归位没输出，漏了灰度叠加）

# 第 17 轮 · 第 16 章安全与多租户检验（8.5 / 15 ≈ 57%）

> 章节入库后首次检验。三段式梳理（一个公理+三个机制+一条反转+两笔账）后逐题拷问；四个检验点：机制词蹦出 / 审题纪律 / 结构优于检查 / 跨章调用。四题共享同一业务背景（短视频推荐 SaaS 从小到大），实为一条线：Q1 画边界 → Q2 数据维度收缩边界 → Q3 依赖维度管信任 → Q4 时空维度划损失边界。

## Q1 · 信任边界识别（1.5 / 3）

**原题**：短视频 App 推荐链路：客户端 SDK→API 网关→推荐服务→用户画像库（读写）；运营后台（内网部署）直连画像库跑导出报表。① 全链路（含后台）几道信任边界？逐道列。② 网关边界和后台边界各自最该防的 STRIDE 两类为什么不一样？③ 用机制反驳「后台在内网不用设防」。

**你的回答**：① 网关、服务、画像库、后台 ② 网关防冒充+拒服；后台防提权+抵赖 ③ 一旦攻击突破内网，后台会不安全。

**答案**：①四道信任边界（客户端→网关、网关→服务、服务→库、**后台→库**——最阴险是后台绕过应用直连库）②网关=无人称公网入口→防 S 假冒+D 拒服；后台=高权限数据出口（能跑全表导出）→防 I 泄露+E 提权；思维=分析一道边界防什么从「这个入口手里有什么能力」出发 ③机制=横向移动（单点突破后在「可信内网」走廊式收割，单点变全军覆没）+墙已塌（远程办公/上云/东西向流量），「在内网」不构成安全主张；后台直连库+高权限=被横移攻陷炸全量数据（Capital One 同构）。〔16 章·STRIDE/信任边界/横向移动〕

**要点**：边界位置全对（含后台直连库）；S+D 全对；提权对、抵赖错（R 是合规审计要求不是攻击面主线，第二类应为 I——导出报表是天然批量数据出口）；③ 结论对机制零分——横移没蹦出、「一旦突破内网」本身还是城堡思维。

**📌 复盘钩子**：「内网不是边界，是攻击者的走廊；后台的权限就是他的爆炸半径」

## Q2 · 多租户漏点与结构保证（2.25 / 4）

**原题**：行级隔离 SaaS，40 人团队每周上新接口；新增附件功能（URL 自增 ID）、仪表盘缓存（键 dash:board:42）、周日全表批处理。① 租户投诉「看到别家看板数据」「改 URL 数字看到别人合同附件」——列至少四处漏点各配为什么漏 ② 评价「通告开发者自查 tenant_id + CR 重点检查」方案 ③ 缓存键问题与修后长相。

**你的回答**：① 新接口没过滤、附件没租户隔离、自增 id 可猜、遍历全表权限太大 ② 不应该检查而是结构防护，ORM 层过滤 ③ 没租户隔离且 id 可猜。

**答案**：①四处漏点=新接口 SQL 忘带 tenant_id/缓存键没租户前缀（dash:board:42 是看板串扰正主，题面两现象只归因一个）/附件自增 ID 可猜（应不可猜 ID+租户前缀路径或签名 URL）/批处理跑全表（应按租户分组），共性=不报错能跑通单租户自测发现不了；②行级隔离命门=全靠每条 SQL 带对 tenant_id，通告+自查仍把命脉押在人为纪律→结构修复组合拳（ORM/平台层全局过滤+附件不可猜 ID+批处理按租户分组+跨租户读不到的自动化测试）；③缓存键问题=缺租户维度（内部键防撞不防猜、外部 URL 才防猜），修后 dash:tenant:{tenant_id}:board:42 由结构强制。〔16 章·多租户串扰五漏点 + 结构强制〕

**要点**：✅ 本轮最大亮点——「不应该检查而是从结构防护」正面甩出（顽固模式「偏好检查而非结构保证」首次正向应用）；❌ 审题半愈：编号形式有了，「数够没」没执行——「至少四处」实给三处、两个投诉现象只归因一个、「为什么漏」一句没配。

**📌 复盘钩子**：「题面每个投诉现象都要归到一次因；内部键防撞不防猜，外部 ID 防猜」

## Q3 · 供应链与 secrets（2.25 / 4）

**原题**：vibe coding 新服务：AI 推荐 3 个眼生 pip 包直接装；数据库连接串写进 config.py 提交 Git；CI 拉码→构建→自动部署生产无人工确认。① 按优先级排前三大风险并显式写机制词 ② AI 推荐包的具体威胁名+为何比抢注拼写近名更阴险（两词）③ 「删掉 config.py 不就行了」为什么不行+正确结构至少两件 ④ CI 对应哪起案例+把哪个机制推到极致。

**你的回答**：① 密码入 git、pip 不知是否安全、CI 没查依赖 ② slopsquatting、规模化可预测 ③ 不行，密码在 git 历史可能已被拉取；新提交删密码+后续不写+换密钥 ④ xz-utils、供应链攻击。

**答案**：①三大风险排序=secrets 进 Git（违反三铁律+明文即泄露）> 三个 pip 包（slopsquatting+信任是传递的）> CI 无人确认（自动化放大器），机制词显式报；②slopsquatting 阴险在可预测+规模化（同一模型对同类问题稳定幻觉同一批名字，攻击者提前占坑=撒一地钓饵，vs typosquatting 碰运气）；③Git 历史永不可删（删工作区≠删历史，克隆已散出）→正确结构至少两件=密钥进 KMS/Vault 集中保管运行时注入+CI 加 secret 扫描挡在合并前（+轮换已泄露密钥）；④SolarWinds（特征词构建+无人值守自动部署：攻陷构建系统让带签名官方产物从信任链最深处流出，18000 家自动装后门，自动化放大器推到极致）。〔16 章·供应链/secrets 三铁律 + 四案例〕

**要点**：✅ slopsquatting 满分（名字+两词全对）；✅ Git 历史机制抓住；❌ 机制词三处没报（病灶一）、优先级没排；❌ 修复只掏轮换一件（漏集中保管/secret 扫描）；❌ 案例配对错（答 xz）——xz 特征是**人被社会工程腐蚀**，题面特征是构建+自动。

**📌 复盘钩子**：「四案例配对看特征词：xz 看人、Log4Shell 看深度、SolarWinds 看构建+自动、Capital One 看权限+半径」

## Q4 · 合规、爆炸半径与跨章综合（2.5 / 4）

**原题**：C 轮后：两家医疗客户（HIPAA）+一家欧洲客户（数据不出欧盟）；安全报告：全公司共用一个数据库账号+一套 IAM 凭证，配环境变量一年没换。① 两类客户各逼出什么结构决策+与哪章哪个决策同构 ② 共用凭证对应哪起案例+用爆炸半径语言说问题+修复方向 ③ 医疗客户要求数据物理隔离——谱系落位+代价至少两条+公开社区平台怎么变 ④ 「安全做到什么程度算够」用判断式一句话回答。

**你的回答**：① 数据隔离=第五章合规驱动分片 ② Capital One，角色权限过大没最小权限；最小权限+账号/表权限细分 ③ 竖井物理隔离；代价机器成本+聚合统计成本；反向则池化+表隔离 ④ 结构上安全而不是检查。

**答案**：①欧洲客户数据驻留→数据层按法域分区（与 05 章分片、13 章多区域同构）；医疗客户审计留痕（敏感操作不可篡改落日志，与支付模板复式记账同构）+串扰代价极高→隔离往硬处走；②Capital One（✅Q3 刚错立刻修正），爆炸半径语言=一套凭证=全公司一个巨型半径（任一服务任一漏洞被攻破钥匙能开所有门），修复成套=凭证隔离+集中保管 KMS+自动轮换/短时凭证；③竖井+物理级落位对，代价=机器成本+跨租户聚合统计变难+运维随租户数线性涨，公开社区→池化+行级（串扰代价低）；④判断式=安全做不到 100% 不被攻破，「够」=被攻破后最多能碰到什么（爆炸半径缩到一次事故损失可承受），底线（合规/资金）不可谈判其余按事故代价 vs 成本定档。〔16 章·合规即架构/爆炸半径 + 05/13 章同构〕

## Q1 · vibe coding 的分界线与放大机制（1.75 / 3）

**原题**：小王用 AI 写内网工具不审查直接上架；小李用 AI 写退款审批助手（接订单库+支付接口、能自动批退款）不审查直接上生产。① 按 Willison 定义哪个是 vibe coding？线画在哪？② 小李辩解「AI 写得快且 demo 跑得好」——用机制指出错在哪。③ 退款审批助手该问哪些判断问题（至少三个，各挂一章）+ 装什么护栏（套名报出来）。

**你的回答**：① 都是 vibe coding 但小李越界，线是审查和护栏 ② demo 只是乐观路径，没考虑超时重试幂等 ③ 失败怎么办、能否回退、是否安全；评测量化+CI、人工审查。

**答案**：①都是 vibe coding（特指不审查就接受，两人都没审查）；线是两条=审不审查（定义线）×失败代价（适用性线：玩具可 vibe、生产必须判断收口），护栏是修复不是分界；②机制=放大对称（AI 写得快=错得快错得更大债积更猛，速度不是质量证据）+瓶颈转移（生成快≠可以不想）；③判断问题各挂一章=失败会怎样（12）/自动批退款是写操作+涉钱→幂等键三要素（11）/会被提示注入吗+爆炸半径多大（16），护栏=评测三件套+不可逆操作走人工确认（能批真金白银，human-in-the-loop 最重一道闸）。〔17 章·vibe coding/放大对称 + 评测三件套〕

**要点**：✅「都是 vibe coding 但小李越界」精确命中定义（多数人第一反应就错）；✅乐观路径机制名蹦出；❌最对症的放大对称没报；❌「至少三个」仍给两条半（回读残留）；❌章没挂、套名没报、human-in-the-loop 没说出为什么格外要命。

**📌 复盘钩子**：「vibe coding 的线是两条：审不审查 × 失败代价；速度不是质量证据——放大是对称的」

## Q2 · 非确定性与评测驱动（3 / 4，本轮最佳单题）

**原题**：「小退」LLM 客服能自动创建退货单。上线验收=产品经理+测试各试二十轮对话觉得挺好；供应商换新版后没改一行代码，三周后退货批错率上升。① 二十轮验收为什么不够——缺的整套方法叫什么（套名）+至少三件？② 「没改代码却退化」暴露哪个头号新约束？为什么传统软件升依赖不会出这种事？③ 能自动创建退货单——哪条护栏格外要命？两个词。④ 评测集从哪来？进 CI 卡什么？

**你的回答**：① LLM 不确定性，同输入不同输出；缺评测和评分、评测量化、护栏加人工审查、可观察和回退 ② 非确定性，传统软件非对即错且可观测 ③ 可观测与可回退：因为退货退款后无法回滚 ④ 用户真实交互轨迹+AI 生成轨迹；卡质量分布、是否提升或没回归。

**答案**：①机制名非确定性+三件（评测量化/护栏人审/可观测可回退）=评测三件套；②传统软件地基是确定性（输入定输出定，assert 能守没改的部分），LLM 供应链里模型本身就是代码，换版本=隐式改实现却不过你的 CI——「换模型就是换代码，只是不经过你的 CI」；③不可回滚（退货单创建即副作用）→不可逆操作走人工确认；④评测集=线上真实轨迹（人工审+标注）+补充生成（生成用例本身要人工审），CI 卡退化不是提升（换模型/改提示必须过评测集分数掉就拦）。〔17 章·非确定性/评测驱动〕

**要点**：✅ 机制名第一句报出（病灶一击破）；✅不可回滚→人工确认因果链自己推出（第 17 轮欠的补上）；❌CI「卡什么」没接住叙事钩子；❌「是否提升」不严谨——卡退化，持平放行。

**📌 复盘钩子**：「换模型就是换代码，只是不经过你的 CI——评测集是给隐性供应链装的门禁」

## Q3 · 上下文工程与成本三角（1.75 / 4）

**原题**：8 万页 SOP 三个方案：A 全量塞超长上下文；B 切片向量化+检索 Top-50+知识库团队运营；C 全量微调烧进权重。① 三方案在新内存层级各占哪格+死穴？② A 除了贵还有什么性能杀手（机制名）？③ 5% 文档吃掉 90% 检索——13 章见过的一模一样现象叫什么？RAG 上怎么治？④ 给老板甩判据+算账否掉 A。

**你的回答**：① A 窗口层成本大易幻觉；B RAG 层重、需大体量数据库；C 长期记忆：压缩丢失语义 ② 幻觉，上下文长输出漂移，全量放入每次可用 token 少效率低 ③ 热点，一致性哈希加虚拟节点 ④ 更贵，每次全量放入窗口即使命中缓存成本仍大，且易幻觉。

**要点**：✅热点机制名主动蹦出（跨章调用前半步）；❌C 归错格（微调≠长期记忆）连带死穴错；❌迷失在中间没报；❌跨章调用新失败形态：**机制名迁过来，药箱没换成当地的药**；❌判据先行没执行。

**📌 复盘钩子**：「跨章调用别只搬名词——机制名迁过来，药箱也要换成本地的药」+「能装下≠装得起」

**📌 复盘钩子**：「熔断拦不住注入——可用性套件治故障，安全套件治攻击，开方先认科室」+「固定管道用工作流，自主性只买你需要的那点灵活性」

## Q1 · 连环翻车诊断（1.8 / 4）

**原题**：「秒票」大促压轴场次开售 10 分钟连环翻车，五现象：A 单分片 CPU 100% 其余 7 片空闲（有人提议加 8 台机器）；B 超时后自动重试请求翻 3 倍、支付线程池拖干、正常付款也 503；C 2000+ 重复扣款、对账差异巨大；D 订单已建但优惠券没发（下游没收到事件）；E 订单接口校验登录但没校验归属，改 URL 订单号看别人明细。① 逐条挂号+机制名+一句机制，并判 A 的「加 8 台机器」② B、C 各开一套药（套名+逐件）③ 至少两条因果链+跨哪几科。

**你的回答**：1A 规模/热点 key/加机器没用要加盐；2B 可用性/重试风暴/熔断舱壁隔离线程池+幂等重试；3C 一致性/saga 补偿回滚/对账兜底；4D 双写/outbox；5E 安全/权限没细分/先换密钥+最小权限+临时凭证。

**完整答案**：A 规模科·热点（幂律让单分片被打爆，加机器救不了单分片热点；读热点更适合本地缓存/只读副本/请求合并，加盐偏治写热点）✅；B 可用性科·重试风暴+资源耗尽（两个放大器并存）；药=韧性套件（熔断+舱壁+超时预算+重试四件套退避抖动预算幂等+降载）；C 一致性科·**幂等缺失**（重试+不幂等=随机重复扣款机）；药=**幂等三件套**+对账（不是 Saga——Saga 治「做一半」不治「重复」；且「补偿回滚」踩雷：补偿≠回滚）；D 一致性科·双写→Outbox+幂等消费 ✅精准；E 安全科·**IDOR（水平越权）**；药=对象级授权校验+结构强制 owner 过滤（不是 secrets 药——E 没有密钥泄露）。因果链：A 热点(规模)→DB 慢→B 重试风暴+资源耗尽(可用性)→同笔支付被重试→C 幂等缺失下重复扣款(一致性)；E 与 A–D 无因果但同根（大促匆忙上线没做威胁建模）。

**要点**：✅ 五现象科室全挂对；✅ A「加机器没用」顶住工程师惯性；✅ D 极简精准（双写+outbox）；❌ C 套件错配（幂等病开 Saga 药）+「补偿回滚」概念错；❌ E 套件错配（越权病开 secrets 药）；❌ ③因果链整问漏答（回读）。

**📌 复盘钩子**：「科室内要细分症：一致性科——重复→幂等三件套、做一半→Saga、丢失→Outbox、对不上→对账；安全科——越权 IDOR→对象级授权、泄露→secrets 三铁律、串扰→结构强制 tenant 过滤、注入→提示注入套件」

## Q2 · 重构还是拆分（2.25 / 4）

# 缺口补全自查卡：看到 X，立刻想 Y

> ✅ 本卡已提升为技能正式附录并补全进阶篇（10–12 章）反射条目：[references/appendix-reflexes.md](references/appendix-reflexes.md)。日常使用以附录版为准；以下为十轮拷问收官时的历史快照。

把全部缺口压缩成条件反射。日常做架构决策前扫一遍：

| 触发场景 | 条件反射 |
|---------|---------|
| 算出 QPS/容量数字 | 先问「这真的是问题吗」（证伪复杂度），再算扇出、再算数据总量 |
| 看到「一对多」业务关系 | 算写放大：推/拉/推拉结合；长连接系统扩容指标是连接数不是 QPS |
| 看到数字（QPS/写量） | 先问「读还是写」——同数字不同性质，结论相反 |
| 看到「剩余 N 个」 | 限量发放族 → 强一致+原子扣减（库存/券/名额/预订全同族） |
| 判一致性 | 三把尺子依次过：①赔钱吗 ②能自愈吗 ③是 hint 还是判定；同一数据不同用途分档 |
| 需要对账的数据 | = 错了不会自愈 = 强一致 |
| 写瓶颈 | 复制和缓存直接出局；分片前先消解：「为什么有这么多写」 |
| 任何最终一致承诺 | 必配兑现机制：对账 / ack+重试；「最终」不会自己到达 |
| 超时 | ≠ 失败；置「未知」，查询收敛，对账兜底 |
| 会被重试的写操作 | 幂等三要素：调用方签发键、唯一约束验票、键是动作身份证；**查重和写入必须原子——用唯一约束，不用先查后写** |
| 既改库又发消息 | 双写陷阱：先写谁都漏窗口（丢消息/幽灵消息）→ Outbox 同一本地事务，重试补不上结构缺口 |
| 客户端先写的请求 | 两把尺子：决定权在谁？涉钱涉权限吗？客户端可以是仓库，不能是法官 |
| 多端/离线同步 | 操作日志 + 游标（只传增量）+ 墓碑（两端不物理删） |
| 并发写冲突 | 先问能不能存操作而非状态（冲突自动消解）；累加型禁用 LWW |
| 要防碰撞/防重复 | 先想结构不相交（命名空间隔离/唯一约束），别做先查后写 |
| 给缓存设 TTL | 先问：数据不可变吗？不可变→永不过期；可变→逻辑过期/抖动 |
| 两个需求冲突 | 先问能不能消解（正交通道/状态分级/客户端副本），消解不了再给带价签选项 |
| 给老板/业务方出方案 | 菜单不是报价：方案/他得到/他付出/成本，至少三条路；绝不说「做不到」 |
| 画图框超 9 个 | 拆论证不是合并框；一张图一个结论，箭头标方向和含义 |
| 两个模块解耦不干净 | 先看人：owner 是谁、沟通多紧密；逆康威先组团队再拆系统 |
| 想照搬成熟架构 | 先比约束：团队/流量/成本/生命线；「不加会死吗」问到系统还需不需要存在 |
| 打散/分片/分段 | 第二层账单：倾斜+再平衡是出厂配套 |
| 两种访问形态冲突 | 两套存储（CQRS）；不为 1% 查询毁 99% 主路径 |
| 重要决策落地 | 写 ADR：「放弃了什么」是独有价值；技术债三件事：借、记账、排期还 |
| 昂贵资源在运转 | 问：这一秒它在为谁工作？那个人还要这个结果吗？（不要则 abort） |
| 拆分/并行方案 | 先数通信：传几次、传多少；通信模式决定部署边界 |

## 答题前三问（治三条顽疾）

1. **「我手上有没有现成的结论/尺子能用？」** —— 治裂缝②（有结论不主动调用）
2. **「这次的数字/性质和上次一样吗？」** —— 治教条惯性（读/写、可变/不可变、限量/非限量）
3. **「题目要几个点？有什么限定词？」** —— 治审题漏项

## 一句话收尾

> 八轮拷问磨出一件事：**判断你已经有，缺的是把判断变成条件反射。**
> 尺子要主动掏、结论要绑场景、代价要先说、结构优于检查、消解先于硬扛。
