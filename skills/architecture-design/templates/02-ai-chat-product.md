# AI 对话产品架构模板

> 代表产品：Claude、ChatGPT、Gemini、各类「AI 助手」
> 一句话定位：把一个大语言模型（LLM）包装成可对话、能流式输出、能用工具、能联网的产品。

## 1. 一句话定位

一个 AI 对话产品 = 一个昂贵的「推理大脑」（LLM）+ 一圈把它变得好用、安全、能赚钱的「外壳」。

架构上最反直觉的一点：和普通网站最大的不同，不是逻辑复杂，而是**最贵、最稀缺的资源从「数据库/CPU」变成了「GPU 算力」**。整套架构几乎都是围绕「怎么把 GPU 喂饱、用满、用省」转的。

三个支柱：
- **GPU 不能停**：连续批处理、KV 缓存、GPU 利用率是一切的核心
- **token 都是钱**：上下文压缩、模型路由、缓存复用，每个 token 都有成本
- **模型会骗人**：Guard 模型、输入不可信、输出审核、沙箱隔离

## 2. 业务本质

用户要的是随叫随到、什么都懂、能帮干活的助手。取代的是「自己 Google + 自己读 + 自己写」的过程。

**钱从哪来**：
- 订阅（个人/团队按月付费，要稳定体验和额度）
- API 调用（开发者按 token 计费）
- 企业版（数据隔离、合规、私有部署）

**关键事实**：每生成一个字，背后都是真金白银的 GPU 时间。普通网站「多一次请求几乎不要钱」，这里「多生成 1000 字就是实打实的成本」。这一条决定了后面几乎所有架构取舍。

## 3. 核心需求与约束

### 功能性需求

- 多轮对话：记住上下文，连续聊
- 流式输出：像打字机一样逐字蹦出来
- 系统提示/角色设定：给模型设定行为边界
- 工具调用（function calling）：让模型能调计算器、搜索、代码执行、查数据库
- 联网/RAG：让模型回答时能引用外部知识或实时信息
- 多模态：看图、读文件、出图
- 会话历史：保存、检索过去的对话

### 质量属性（架构主战场）

| 质量属性 | 目标 | 为什么重要 |
|---------|------|-----------|
| 首字延迟 TTFT | < 1 秒 | 用户盯着屏幕等，首字越快越「跟得上」 |
| 生成吞吐 | 高 tokens/秒 | 决定回答多快读完，也决定单卡能服务多少人 |
| 成本/每千 token | 越低越好 | 算力即成本，毛利全看这个。和普通系统最大区别 |
| 可用性 | 99.9%+ | 挂了用户立刻就走 |
| 安全性 | 必须 | 不能被诱导输出有害内容、不能被注入攻击 |

### 关键约束（不可逾越的边界）

- **GPU 又贵又缺**：头号约束，整套架构为它服务
- **上下文窗口有限**：模型一次能「看」的内容有上限，塞太多既贵又慢
- **推理是「有状态」计算**：生成下一个字依赖前面所有字的中间结果（KV cache），显存吃得很凶
- **模型本身不可控**：会胡说、会被骗，需要外层兜底

**灵魂部件是推理服务**——其余所有东西（网关、编排、缓存）本质上都是在「保护和喂养这块昂贵的 GPU」。

## 5. 组件职责

| 组件 | 职责 | 为什么需要 |
|------|------|-----------|
| 接入层/API 网关 | 鉴权、限流、配额分配、维持流式长连接 | GPU 太贵，必须在最外层挡住滥用和超额 |
| 编排层 | 组装 prompt、Agent 循环、安全检查、计费 | 模型只会「续写文字」，变成「产品」的智能都在这一层 |
| 推理服务 | 管理 GPU、连续批处理、逐 token 输出 | 单请求喂 GPU 大量空转；批处理是把成本打下来的关键 |
| 会话存储 | 存历史对话，按会话 ID 读取 | 多轮对话要记住上文 |
| 向量检索/RAG | 文档切块→向量化→语义检索 | 让模型基于「你的资料/最新信息」回答 |
| 工具执行沙箱 | 隔离环境执行搜索/代码/函数调用 | 让模型从「只会说」变「能做事」；隔离因有安全风险 |
| 模型权重存储 | 对象存储，GPU 节点启动时加载 | 模型文件几十~上千 GB |
| 安全/内容审核 | 输入拦截恶意请求，输出拦截有害内容 | 模型不可控，需外层兜底 |
| Guard / Judge 模型 | 独立的轻量模型，对输入/输出做安全评估和放行 | 比硬编码规则更智能，能识别语义级攻击（提示注入） |

## 6. 关键数据流

### 场景一：普通流式对话（核心路径）

1. 用户输入 → 网关（鉴权、扣配额、建立 SSE 连接）
2. → 编排层：取会话历史 → 拼装 prompt（系统提示+历史+本轮） → 输入审核
3. → 推理服务：请求入队，与其他用户请求组成 batch
4. → GPU 逐 token 生成，每生成一个立刻回吐：网关 ══SSE══▶ 用户屏幕逐字出现
5. 生成结束 → 输出审核 + 记录 token 数计费 + 写入会话存储

> 字还没生成完，用户已经在读了。流式架构把「十几秒等待」变成「立刻有反应」。

### 场景二：带工具的 Agent 循环

```
用户问「上季度华东区销量多少?」

编排层 → 模型：这个问题要查数据
模型 → 输出「工具调用：查询销量(区域=华东, 季度=Q3)」
编排层 → 工具沙箱执行 → 拿到「华东 Q3:1240 万」
编排层 → 结果拼回 prompt，再喂给模型
模型 → 「华东区上季度销量为 1240 万元，环比……」（流式回答）

⟲ 可能循环多轮，直到模型不再要工具
```

> 工具结果是重新进入模型的文本，**必须当不可信输入对待**（提示注入风险）。

## 7. 数据模型与存储选择

| 数据 | 存储类型 | 为什么 |
|------|---------|-------|
| 用户/订阅/配额 | 关系型 | 要事务、强一致（扣费不能错） |
| 会话历史（消息） | 文档型/追加日志 | 写多读少、按会话 ID 取、结构灵活 |
| 文档向量（RAG） | 向量数据库 | 按语义相似度检索，普通 DB 做不到 |
| 模型权重 | 对象存储 | 文件巨大、不可变、按需加载到 GPU |
| 用量/计费流水 | 时序/列存 | 海量、按时间聚合、用于账单和监控 |
| 热点提示前缀 | 显存 KV 缓存 | 省钱关键——缓存重算代价高的前缀。前缀匹配（如 DeepSeek）命中后直接复用，避免重复计算 |

> 不同数据的「访问形态」不同，就该放进不同类型的存储。

## 8. 关键架构决策与权衡

### 决策 1：流式输出（SSE）还是一次性返回？

| 方案 | 优势 | 代价 |
|------|------|------|
| 一次性 | 实现简单 | 用户盯着空白屏等十几秒，体验灾难 |
| 流式 SSE | 首字 <1 秒，感知延迟大幅下降 | 连接管理复杂，重试/恢复更麻烦 |

**取向**：几乎一定选流式。**感知延迟有时比真实总延迟更重要。**

### 决策 2：单请求独算还是连续批处理？

| 方案 | 优势 | 代价 |
|------|------|------|
| 单独算 | 延迟可控 | GPU 大量空转，成本爆炸 |
| 连续批处理 | 多请求拼批，GPU 利用率拉满 | 调度复杂，可能拉高尾延迟 |

**取向**：必须批处理，GPU 是头号稀缺资源。

#### 深层矛盾：Prefill vs Decode 争抢

LLM 推理分两个阶段，资源特征完全不同：

| 阶段 | 做什么 | 吃什么 |
|------|--------|--------|
| **Prefill** | 一次性算完用户的整段 prompt | 计算密集（吃算力） |
| **Decode** | 逐 token 生成 | 访存密集（吃显存带宽） |

**矛盾**：新请求的 Prefill 一旦进入 batch，会把算力全吃掉，导致同批里正在 decode 的请求卡顿（用户看到吐字卡一下）。但如果让 Prefill 排队等，新用户的首字延迟就崩了。

**解法：chunked prefill**——把一个大 Prefill 切成多个小块，与 decode 步混排在同一个 batch 里。两边都不饿死：decode 不卡顿，Prefill 也不用干等。

### 决策 3：重复提示前缀要不要缓存？（省钱关键）

每轮都把「系统提示+全部历史」重新算一遍 → 极度浪费。缓存 KV cache / prompt caching，下轮直接复用。

实现要点：
- **前缀匹配**：新请求与已缓存的 KV 状态做前缀比对，命中则复用（如 DeepSeek 的方式）
- **存储策略**：KV 缓存存在 GPU 显存（VRAM）里，显存是最贵最少的资源——缓存多了新请求进不来，少了命中率低
- **分页管理**：vLLM 的 PagedAttention 像操作系统管虚拟内存一样管显存，按需分配/回收

**取向**：规模化后必做。**把「重算昂贵前缀」变成「读缓存」是最大的成本杠杆之一。**

#### 显存满了该踢谁？驱逐优先级

判断依据不是「多久没用」，而是 **「重建成本 vs 占用空间」的性价比**：

| 优先级 | 对象 | 为什么 |
|--------|------|--------|
| ① 先踢 | 长时间不活跃的会话 KV | 占空间大，短期重用概率低 |
| ② 再踢 | 公共前缀缓存 | 虽然一份成本、几百倍收益，但它小，踢了也腾不出多少空间 |
| ③ 永不踢 | 正在生成中的请求 | 踢了等于白烧了已经花掉的 GPU 时间，请求作废 |

❗ **常见错误**：把公共前缀缓存第一个踢掉。它是几百个会话共享的，踢了就等于把 prefix caching 这个最大的省钱杠杆当场作废。

**优化**：被踢的不活跃会话不必真删，可以 offload 到 CPU 内存或磁盘，用户回来时换回显存——比从头重算便宜得多。

### 决策 4：知识从哪来？长上下文 vs RAG vs Agentic Retrieval

| 方案 | 适用场景 | 代价 |
|------|---------|------|
| 直接塞上下文 | 小（几页文档） | 几乎零成本，但窗口有限 |
| Agentic Retrieval（工具调用式检索） | 中（几十~几百页） | 轻量，模型自己决定查什么，像 coding agent 用 grep |
| RAG（切块→向量化→检索） | 大（几万页 / 持续更新） | 重基础设施，但大规模时最准 |
| 混合检索 | 大多数场景 | 向量语义 + 关键词 + 工具查询互补，比单一 RAG 更鲁棒 |

**取向**：不要一上来就上 RAG。先用最简单的方式（摘要 + 工具查询），真到了几万页文档、向量检索比 grep 更准的时候，再上 RAG。大多数场景用混合检索效果最佳。

### 决策 5：会话状态放客户端还是服务端？

**取向**：产品级 → 服务端存（多设备、长期记忆）；API 级 → 调用方自带历史（无状态、好扩展）。

### 决策 6：一个大模型通吃还是模型路由？

**取向**：规模化后引入路由。简单问题给小模型，难问题才上大模型。**把昂贵的工作交给能干它的最小工具。**

#### 路由悖论：谁来判断「难不难」？

预判难度本身就是个悖论：
- 用**大模型**判断 → 路由本身就花了大模型的钱，省钱变成多花钱
- 用**小模型**判断 → 它能力弱，怎么知道一个问题「难到自己答不了」（学渣不知道题超纲）
- 用**规则**判断 → 「用一句话证明黎曼猜想」只有 12 个字

**两种可落地的解法**：

| 方案 | 适用场景 | 机制 | 代价 |
|------|---------|------|------|
| **任务级路由** | Agent / 多步任务 | 大模型做规划时顺便拆出子任务并标难度，路由决策搭便车零额外成本 | 只适用于有规划阶段的场景 |
| **级联路由（cascade）** | 单轮对话（占 C 端 80% 流量） | 小模型先答 → Judge 评质量 → 不合格才升级大模型重答 | **尾延迟翻倍**（小模型生成 + Judge + 大模型重来） |

关键洞察：**判断「答得好不好」比预判「难不难」容易得多。** 级联路由省的是钱，付的是最慢那批请求的体验。

### 决策 7：模型装不下单卡，怎么拆到多卡？

70B 模型一张 80GB 卡装不下，必须拆。两种拆法的**通信模式完全不同**：

| 方案 | 怎么拆 | 卡间传什么 | 通信频率 | 网络要求 | 主要代价 |
|------|--------|------------|---------|---------|---------|
| **张量并行（TP）** | 每层的矩阵横切成 N 份 | 每层算完都要 all-reduce 合并 | **极高**（80 层 = 每个 token 通信 80+ 次） | **NVLink 级，只能单机内** | 通信开销巨大 |
| **流水线并行（PP）** | 按层分段（1-20 层卡1，21-40 卡2…） | 只在层边界传一次激活值 | **极低**（只在分段边界） | 以太网也能忍 | 流水线气泡（卡空转） |

❗ **最常见的认知错误**：以为张量并行「只需最后组合结果」。错——第 2 层的输入需要第 1 层的**完整**输出，所以每层都必须立刻同步。TP 是通信**最重**的方案，不是最轻的。

**取向**：单机多卡（有 NVLink）→ TP；跨机器、走以太网 → PP。大规模集群常是两者混合：机器内用 TP，机器间用 PP。

### 决策 8：用户中途跑了，GPU 还在算吗？

这是自部署模型**最容易漏掉的成本黑洞**。规模化后，被取消的请求可能占 10%+。

**两个必须 abort 的场景**：

| 场景 | 为什么要 abort |
|------|---------------|
| 用户关浏览器/断网/切 App/锁屏 | 他已经不要这个答案了 |
| 同一会话里，上一条还没答完就发了新消息 | 发新消息就说明他不要上一条了，而新消息马上就要资源 |

**不 abort 的三重代价**：
1. 纯烧钱：给一个不存在的需求算完剩下的 700 个 token
2. **占着 batch 槽位**：队列里的真实用户在等，首字延迟被僵尸请求拖长
3. **占着 KV 缓存**：显存本就不够，还被没人要的请求占着

**实现：cancellation 沿链路传播**

```
SSE 连接断开 → 网关检测到 → 通知编排层 → 通知推理引擎
                                          ↓
                          立刻从 batch 踢出 + 释放 KV 缓存槽位
```

❗ **常见陷阱**：
- 以为「加个停止按钮」就解决了——按钮只是触发方式，后面还是要走同一条 abort 链路；而且关浏览器/断网用户不会主动通知你
- 以为「算完保存结果下次给他看」很贴心——对话产品不是邮件，用户关掉就是不要了
- vLLM 等引擎都有 abort 接口，但**自建系统很容易漏接这条链路**：网关那边连接断了，推理引擎根本不知道，继续算到 max_tokens 才停

## 9. 规模化与瓶颈

| 瓶颈 | 破解 |
|------|------|
| GPU 被打满 → 排队 → 首字延迟飙升 | 连续批处理、prompt 缓存、模型路由、量化、扩 GPU |
| 上下文越长，单请求吃显存越多 | KV 缓存精细管理（paged attention）、RAG 取代长上下文、历史压缩/摘要 |
| 大批次拉高尾延迟（P99） | 批大小和延迟目标动态权衡，付费高档用户预留低延迟通道 |
| 成本本身是瓶颈 | 缓存/路由/量化从第一天就是架构议题，不优化毛利直接为负 |
| **被取消的请求白烧算力（规模化后可达 10%+）** | cancellation 沿链路传播，立刻 abort 释放 batch 槽位和 KV |
| **Prefill 抢算力导致 decode 卡顿** | chunked prefill，切碎与 decode 混排 |

## 10. 安全与合规

- **提示注入（Prompt Injection）**：AI 产品最棘手的攻击面。任何重新进入模型的外部文本（RAG 网页、工具结果、用户上传）都可能藏恶意内容 → 所有输入标记为不可信/低置信度，通过 Guard/Judge 模型评估后放行
- **Guard 模型机制**：独立的轻量模型在主模型前后做安全检查。输入侧拦截注入/违规，输出侧拦截有害内容。比硬编码规则更能识别语义级攻击
- **工具执行必须沙箱隔离**：在受限、可丢弃的隔离环境执行，绝不能碰生产系统
- **数据隐私**：对话常含个人/商业敏感信息 → 租户隔离、传输与存储加密、「是否用于训练」边界明确、可删除
- **输出安全**：输入输出两侧都要审核（越狱防护）
- **配额与滥用**：API 层防刷防薅（每个 token 都是钱）

## 11. 常见误区/反模式

| 反模式 | 正确做法 |
|--------|---------|
| 当普通 CRUD 网站设计，忽视 GPU 稀缺 | 一切先问「这对 GPU 利用率和成本意味着什么」 |
| 不做流式，憋完整答案再返回 | 默认流式，首字延迟是第一体验指标 |
| 每轮全量重算，从不缓存 | 缓存提示前缀，最大的省钱点之一 |
| 所有资料硬塞进上下文 | 按规模选策略：小→直塞，中→工具查询，大→RAG，多数→混合检索 |
| 一上来就上 RAG | RAG 是大规模知识库的解法，不是默认解法。先简单，真需要时再上 |
| 直接信任工具/检索返回的文本 | 当不可信输入，警惕提示注入 |
| 同步阻塞调工具，卡住整个流 | 工具调用异步化，Agent 循环和流式解耦 |
| 不记 token 账 | 没有计量会超窗口 + 收到吓人账单 |
| **用户跑了还继续算完** | cancellation 沿链路传播，立刻 abort 释放资源 |
| **跨机硬上张量并行** | TP 只能单机内（需 NVLink），跨机用 PP |
| **把公共前缀缓存第一个驱逐** | 它是几百个会话共享的最大省钱杠杆，先踢不活跃会话 |

## 12. 演进路线

| 阶段 | 规模 | 架构 | 该操心什么 |
|------|------|------|-----------|
| MVP | 验证想法 | 调模型提供商 API + 薄编排层；客户端带历史；简单 SSE；无 RAG、无自建 GPU | 先验证有没有人用，别一上来自建 GPU |
| 成长期 | 万~百万用户 | 会话存储、RAG、输入输出审核、限流配额、prompt 缓存；自建模型则上连续批处理 | 找成本和延迟瓶颈，把单 token 成本打下来 |
| 成熟期 | 千万~亿级 | 多区域 GPU、模型路由（大小混用）、精细缓存与显存管理、完整 Agent 生态、评测/可观测性、企业级多租户 | 成本、容灾、安全合规、模型质量持续评测 |

## 13. 可复用要点

- **围绕稀缺资源做架构**：这里是 GPU，在别的系统可能是数据库连接、带宽或人。把架构建在「让稀缺资源不空转」上。
- **感知延迟常比真实延迟更重要**：流式没让总时间变短，但让体验天差地别。任何「让用户更早看到反馈」的设计都值钱。
- **缓存「重算代价高的东西」是巨大杠杆**：这里是 KV cache / prompt 缓存，别处可能是计算结果、聚合视图、渲染页面。
- **把昂贵活交给能干它的最小工具**：模型路由 ≡ 别用重型方案解决轻量问题。
- **任何重新进入核心系统的外部数据都不可信**：提示注入只是「永远不要信任用户输入」在 AI 时代的新形态。用 Guard 模型做语义级审核，比硬规则更智能。
- **不要默认上重武器**：RAG、模型路由、多区域 GPU 都是好东西，但先问「不加会死吗」。创新代币省着花。
- **时刻问「这一秒 GPU 在为谁工作？这人还要这个结果吗？」** 成本意识不只是「省 token」，更是「立刻停掉没人要的计算」。任何涉及昂贵资源的系统都适用。
- **通信模式决定部署边界**：分布式拆分时，先算清「每步要传多少数据、传多少次」。通信重的方案（如 TP）只能单机，通信轻的（如 PP）才能跨机。
