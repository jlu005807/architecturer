# 短链接服务架构模板

> 代表产品：Bitly、TinyURL、t.co（Twitter）、各类二维码/分享短链
> 一句话定位：把一条长 URL 映射成一个极短的 key，点击短链时以最快速度重定向回原始地址。

## 1. 一句话定位

短链接服务 = 一张巨大的「短码 → 长链接」映射表 + 一条被优化到极致的重定向快路。

它看起来简单到像一行哈希表，但恰恰是**「读多写少、极致可用、全局唯一 ID」的教科书**。99.9% 的流量都是「拿短码查长链，然后 302 跳走」这一个动作——这条路必须快到几十毫秒、且几乎不能挂。

## 2. 业务本质

长链接又长又丑：短信有字数限制、二维码越长越密难扫、社交分享要好看可点。短链解决的是「把任意长的地址压缩成一个干净、可分发、可追踪的入口」。

附带的真正价值是点击分析：谁、什么时候、在哪、用什么设备点了这条链接。

**钱从哪来**：企业版的点击分析与营销报表、自定义品牌域名、批量生成 API、A/B 投放追踪。短链本体几乎不赚钱，赚钱的是背后那层「可度量的分发」。

## 3. 核心需求与约束

### 功能性需求

- 长链接 → 生成短码
- 短码 → 重定向回长链接（核心中的核心）
- 自定义别名（`/spring-sale`）、过期时间
- 点击统计（次数、来源、地域、设备）

### 质量属性（架构主战场）

| 质量属性 | 目标 | 为什么重要 |
|---------|------|-----------|
| 重定向延迟 | < 50ms | 用户点了要立刻跳，慢一点就像「这链接坏了」 |
| 可用性 | 99.99%+ | 链接已发出去/印出去了，服务挂 = 所有人点了都打不开 |
| 读写比 | 100:1 甚至 1000:1 | 创建一次，被点千万次，读写形态严重不对称 |
| 短码长度 | 尽量短 | 越短越好用，但可用空间越小，是个取舍（应由日增量×预期寿命反推，不是产品拍脑袋） |
| 域名信誉 | 不被平台封禁 | 滥用失控 → 域名被封 → 所有客户一起死，比宕机更棘手 |

### 关键约束（不可逾越的边界）

- 链接不可变：短码一旦生成并分发，就印在物料上，永远改不了——这既是约束也是红利（见「决策 4：映射缓存要不要设 TTL」）
- 短码空间有限：6 位 Base62 ≈ 568 亿，日增 1000 万约 15.5 年耗尽，耗尽后位数会默默变 7
- 读写极度不对称：架构必须围绕「读」来设计，「写」可以慢
- 域名信誉是生存红线：被微信/浏览器封禁 = 全部客户链接一起死（见安全章节）

## 4. 架构全景图

```
   创建短链(少量)                          点击短链(海量,99.9%流量)
        │                                          │
        ▼                                          ▼
┌────────────────┐                      ┌────────────────────────────┐
│   写服务         │                      │   读服务 / 重定向(快路)       │
│ • 校验长链      │                      │  ┌──────────────────────┐  │
│ • 申请唯一 ID    │◀── 发号器 ──┐        │  │ 1.查KV缓存(命中即返) │  │
│ • ID → Base62   │   (号段/雪花) │        │  └──────────┬───────────┘  │
│ • 落库          │             │        │             │ 未命中        │
└───────┬────────┘             │        │             ▼              │
        │                      │        │  ┌──────────────────────┐  │
        ▼                      │        │  │ 2.查主存储,回填缓存   │  │
┌────────────────┐            │        │  └──────────┬───────────┘  │
│  主存储(映射表) │◀───────────┘        │             ▼              │
│ short_key→long  │◀───────────────────│  3.返回301/302重定向        │
└────────────────┘                      └─────────────┬──────────────┘
                                                       │ 异步上报
                                                       ▼
                                          ┌──────────────────────┐
                                          │ 点击事件队列 → 分析存储 │
                                          └──────────────────────┘
```

**灵魂部件是重定向快路**：它要承受全部读流量，「缓存命中率」几乎等于这个系统的命运。

## 5. 组件职责

| 组件 | 职责 | 为什么需要 |
|------|------|-----------|
| 写服务 | 校验 URL、申请唯一 ID、编码短码、落库 | 创建低频但必须保证短码全局不重复 |
| 发号器/ID 生成 | 产出全局唯一、不冲突的 ID | 短码唯一性的根基；成为单点则写入卡死 |
| 读服务/重定向 | 查缓存 → 查库 → 返回重定向 | 系统 99.9% 的工作，必须独立、极简、可水平扩展 |
| KV 缓存 | 热门短码映射放内存级缓存 | 热点链接极热，缓存命中率直接决定延迟和成本 |
| 主存储 | short_key → long_url 持久化 | 真相源 |
| 点击事件管道 | 点击事件异步入队，后台聚合 | 统计绝不能挡在重定向关键路径上 |

## 6. 关键数据流

### 场景一：创建短链（低频写）

1. 用户提交长 URL → 写服务校验合法性/黑名单
2. → 发号器拿到全局唯一 ID（如 10000001）
3. 写服务：ID 用 Base62 编码 → `aUKYr`；落库 `{aUKYr → https://...}`
4. 返回 `https://sho.rt/aUKYr`

### 场景二：点击短链并重定向（海量读，系统命脉）

1. 用户点击 `https://sho.rt/aUKYr` → 读服务
2. 查 KV 缓存：
   - 命中 → 直接拿到长链（99% 走这里）
   - 未命中 → 查主存储，拿到后回填缓存
3. 返回 HTTP 302 + Location → 浏览器自动跳转
4. （旁路）把点击事件异步丢进队列，主流程立刻结束 ← **不等统计写完**

> 统计是「旁路」不是「主路」——重定向在第 3 步就结束了。这是「把非关键路径从关键路径上剥离」的典型。

## 7. 数据模型与存储选择

| 数据 | 存储类型 | 为什么 |
|------|---------|-------|
| 短码 → 长链映射 | KV / 关系型（按 short_key 分片） | 主键精确查找、海量、无复杂关联 |
| 热点映射 | 内存级 KV 缓存 | 读路径命脉，命中率决定一切 |
| 点击事件 | 时序/列存 | 海量追加、按时间和维度聚合做报表 |

> 主键点查场景（永远是拿一个 key 取一个 value），没有 JOIN、没有范围扫描——KV 形态天生最合适。

## 8. 关键架构决策与权衡

### 决策 1：短码怎么生成？

| 方案 | 优势 | 代价 |
|------|------|------|
| 自增 ID → Base62 | 短、无冲突、保证唯一 | 短码连续可枚举，能遍历全站链接 |
| 随机生成 | 不可枚举、安全 | 要查重（可能撞码），空间用满后撞码率升高 |
| 哈希长链取前几位 | 相同长链得相同短码（天然去重） | 哈希冲突要处理 |

**取向**：多数选「自增 ID + 打乱/加盐再 Base62」——既拿到唯一性，又避免明文连续可枚举。代价是发号器要可靠。

#### 短码位数：先算账，再定长度

短码几位不应该是产品拍脑袋定的，而是**算出来的**：

| 位数 | Base62 空间 | 日增 1000 万能用多久 |
|------|------------|-------------------|
| 6 位 | 62⁶ ≈ 568 亿 | ≈ 5680 天（约 15.5 年） |
| 7 位 | 62⁷ ≈ 3.5 万亿 | ≈ 960 年 |

**用完那天会发生什么？**

❗ **不是短码重复**——自增 ID 永远唯一，加盐也不改变唯一性。真正发生的是：ID 超过 62⁶ 后，Base62 编码出来变成 **7 位**。

没有报错、没有冲突、没有任何异常——短码悄无声息地从 6 位变成 7 位。这个区别很重要：误判为「会重复」会让你去设计错的防御（冲突检测），而实际需要的是**变长兼容**。

**上线前就该做的三件事**（事后再改贵一万倍）：

1. 字段用 `VARCHAR` 而不是 `CHAR(6)`
2. 路由/校验正则写 `{6,}` 而不是 `{6}`，不锁死上限
3. 前端、SDK、二维码生成器全部按最长位数预留，不假设固定长度

> **原则：任何“现在够用”的固定容量，都要在设计时算出耗尽时间，并确保耗尽时系统能平滑扩容。**

#### 自定义短码与自动生成短码的碰撞

开启自定义短码（`sho.rt/spring-sale`）后，两套机制共用同一个命名空间，会出真实事故：

1. 企业客户抢先注册了自定义短码 `aB3xY`
2. 三个月后自增 ID 走到某值，Base62 编码出来**正好是 `aB3xY`**
3. 冲突或覆盖 → 客户已印在物料上的链接指向了别人的网站

❗ **无效解法**：把自定义码「再映射成一个 Base62 字符串」。用户访问 `sho.rt/spring-sale` 时，查找的 key 依旧是 `spring-sale` 本身——只是把一次查找变成两次，碰撞一点没解决。

**正解：命名空间隔离（结构保证）**

| 方案 | 机制 | 为什么好 |
|------|------|---------|
| **长度隔离** | 自定义码强制 ≥ 8 位，自增生成的永远 ≤ 7 位 | 两个空间**数学上不相交**，零检查成本 |
| **字符集隔离** | 自定义码必须含 `-` 或 `_`（Base62 里没有） | 同上，天然不相交 |
| **路径隔离** | 自定义走 `sho.rt/c/spring-sale` | 显式分流，但 URL 变长 |

再叠加**短码字段唯一约束**作为最后一道保险（防两个客户抢同一个自定义码）。

> **能用结构保证的，不要用检查保证。** 「生成后查一下被占没占，撞了重试」是运行时检查：多一次 DB 往返、有重试循环、高并发下要靠唯一约束报错才发现。而长度/字符集隔离让碰撞在结构上不可能发生。

### 决策 2：重定向用 301 还是 302？

| 方案 | 优势 | 代价 |
|------|------|------|
| 301 永久重定向 | 浏览器/CDN 缓存，后续请求不到服务器——极快极省 | 收不到点击统计，短码换目标失效 |
| 302 临时重定向 | 每次回到服务器，统计完整，可灵活改目标 | 服务器要扛全部流量 |

**取向**：要分析数据就用 302（商业模式所在），代价是自己扛流量、靠缓存优化。精准体现了**「可缓存性 vs 可观测性」**的永恒矛盾。

### 决策 3：点击统计同步还是异步？

| 方案 | 优势 | 代价 |
|------|------|------|
| 同步 | 简单 | 慢写操作塞进最该快的路径，存储抖动 = 重定向变慢 |
| 异步 | 点击只往队列扔事件，主流程立刻返回 | 多一层队列要维护 |

**取向**：必须异步。重定向是关键路径，统计是旁路，两者绝不能耦死。

#### 异步丢数据能不能接受？——商业模式说了算

场景：返回 302 后事件还在内存缓冲区，机器掉电——用户体验零影响，但整个缓冲区的点击事件全丢。

**同一个丢失，两种完全相反的判断**：

| 商业模式 | 能接受吗 | 判断依据 | 架构对应 |
|---------|-----------|---------|---------|
| 统计仅用于报表展示 | **能** | 点击数不是钱。丢 200 条客户看不出来；而“一条不丢”要用读路径 5ms→4倍延迟换——买卖不划算 | 纯异步 + **访问日志兜底**（日志本来就要写，落盘后可离线补算，等于零成本的第二数据源） |
| **企业客户按点击量付费** | **不能** | 点击数就是钱。丢 200 条 = 少收 2 元，且审计无法解释 | 先持久化再返回；幂等 + 对账 |

**计费场景的持久化方式选择**：

| 做法 | 延迟代价 | 可靠性 |
|------|---------|--------|
| 同步写数据库计数 | +15~30ms，还有热点行竞争 | 高但太贵 |
| **同步顺序写本地 append-only 日志（WAL）**，再异步消费 | **+1~2ms**（顺序写盘极快） | 掉电只丢未 fsync 的那一点 |
| 同步等队列 ack（如 Kafka acks=all） | +3~10ms | 高，但依赖队列可用性 |

涉钱必须配套的两件事：
- **幂等**：点击事件带唯一 ID（短码+时间戳+IP+随机），重放/重试不重复计费
- **对账**：日志明细 vs 计费汇总每日比对（同支付系统：对账是兜底，不是可选项）

> **质量属性优先级从来不是技术决定的，是业务决定的。** 同一个「点击统计」，商业模式一变就从「可丢的日志」变成「不可丢的账」。

### 决策 4：映射缓存要不要设 TTL？

场景：一条短链被千万粉大 V 转发，10 秒内 50 万次点击全打同一个 key。**而这个 key 的 TTL 正好此刻到期。**

→ 50 万请求同时未命中、全部回源打数据库——这就是 **缓存击穿（hotkey miss）**。

| 做法 | 机制 | 代价 |
|------|------|------|
| 互斥锁/单飞回源 | 只放一个请求查库回填 | 剩下 49.9 万阻塞等锁，**雪崩从 DB 转移到应用层**（线程池/连接池占满） |
| **热点 key 永不过期** | 映射本来不可变，直接不设 TTL | 冷数据占内存（靠 LRU 淘汰兜底） |
| **逻辑过期** | 缓存存 `{value, expire_at}`，永不物理过期；读到逻辑过期时**返回旧值** + 后台异步刷新 | 短时返回旧值（对不可变映射零风险） |
| TTL 随机抖动 | TTL = 基础值 + random(0~10%) | 只防雪崩，不防单个热点击穿 |

**取向**：优先用后三种——让请求**根本不撞上过期**，而不是撞上了再靠锁扳住。

> 🔑 **这里有个容易错过的红利：短码→长链的映射是不可变的。那你为什么要给它设 TTL？**
>
> 给不变的数据设过期时间，是把「缓存一致性」的思维惯性套用到了一个**根本不需要一致性维护**的场景。不可变数据是架构红利，要主动用上。

### 决策 5：恶意链接怎么紧急止血？（与决策 4 的连锁反应）

采用了「热点永不过期」后，发现一个恶意短码要立刻下线——但它正是被大量传播的热点，躺在几十台机器的本地缓存里且**没有 TTL**。

❗ 一个「省钱」的缓存决策，在安全场景里变成了「无法紧急止血」。

**正解：不去失效映射缓存，而是加一条独立的封禁通道**

```
请求进来 → ① 查封禁名单（小集合，全量推送到每台机器内存）
              ↓ 不在名单
            ② 查映射缓存（永不过期）→ 重定向
```

封禁名单只有几千条，可以秒级广播到全集群。这样「映射缓存永不过期」和「10 秒内全网止血」**不再冲突**。

> **冲突的两个需求，不一定要妥协，可以拆成两条正交的通道。** 映射数据（不可变、永不过期）和封禁数据（频变、强一致、秒级下发）走两条完全独立的生命周期。

## 9. 规模化与瓶颈

| 瓶颈 | 破解 |
|------|------|
| 读流量打爆 | 多级缓存（本地+分布式KV）、热门推到 CDN/边缘节点、读服务无状态水平扩 |
| 中心发号器成为写入单点 | 号段模式（批发 ID 给各节点）或雪花算法（各节点自生成不冲突 ID） |
| 点击事件洪峰（爆款被疯转） | 消息队列削峰，后台批量聚合 |
| 映射表太大 | 按 short_key 哈希分片（纯点查，分片极其干净，无跨片查询） |
| **短码空间耗尽（位数从 6 默默变 7）** | 上线前就用 VARCHAR + 正则 `{6,}` + 全链路不假设固定长度 |
| **单一热点 key 过期瞬间被击穿** | 热点永不过期 / 逻辑过期返回旧值，不依赖锁扳住 |

## 10. 安全与合规

> ⚠️ **短链接最真实的死法不是技术崩了，是被人当武器用了。**

### 域名被封禁：最高优先级的生存风险

**典型事故现场**：微信全面封禁你的域名 / Google Safe Browsing 标记为恶意网站（Chrome 红色警告页）/ 用户投诉被骗钱。

**根因不是「没做审核」这么浅**：

1. 短链的**产品本质就是「隐藏真实目的地」**。这个特性对正常用户是便利，对诈骗犯是**免费的洗白工具**——他们用你的域名给钓鱼站背书
2. 封禁是**域名级**的。一个骗子毁掉整个域名，你所有正常客户的链接一起死

### bait-and-switch：创建时审核拦不住的攻击

创建时落地页是正常商品页，**三天后改成钓鱼页**。短码没变、映射没变，创建时审核毫无察觉。

| 防御层 | 做法 |
|--------|------|
| 创建时 | 目标 URL 验证、黑名单、威胁情报 API、域名信誉评分 |
| **定期重审**（关键） | 重扫已有链接，**优先级按流量排**——高频访问的链接优先重扫，因为它伤害面最大 |
| 访问时 | 独立封禁通道（见决策 5），不依赖映射缓存失效 |
| 风控 | 注册限流、实名/API key、异常检测（单账号批量建链） |
| 域名隔离 | 不同信任等级用不同域名；企业客户专属品牌域名——避免一颗老鼠屎坏一锅粥 |
| 可疑链接 | 不直接跳，先返回中间页展示真实目标 + 风险提示 |

### 其他安全面

- **枚举遍历**：连续短码会被爬虫顺序抓取 → 短码加盐打乱或随机化
- **滥用刷量**：刷点击伪造数据 → 限流、去重、风控
- **隐私**：点击数据含 IP/地域/设备，属个人信息 → 合规处理与脱敏

## 11. 常见误区/反模式

| 反模式 | 正确做法 |
|--------|---------|
| 同步写点击统计，拖慢重定向 | 统计走异步队列，重定向是神圣的快路 |
| 明文连续自增做短码 | 加盐打乱，避免可枚举、可猜量 |
| 不做缓存，每次打主存储 | 多级缓存，命中率是命根子 |
| 图省事用 301，丢了分析数据 | 想清楚要不要统计，再选 301/302 |
| 不校验目标 URL，沦为钓鱼帮凶 | 黑名单 + 扫描 + 风险拦截 |
| 把它当复杂系统过度设计 | 难点只在「读路径的快和稳」，别的都该极简 |
| **给不可变的映射设 TTL** | 映射永不变 → 热点永不过期 / 逻辑过期，不可变是架构红利 |
| **靠“生成后查重”防自定义码碰撞** | 长度/字符集命名空间隔离，让碰撞在结构上不可能 |
| **硬编码短码长度（CHAR(6)、正则 `{6}`）** | VARCHAR + `{6,}`，提前为位数增长留路 |
| **只在创建时审核目标 URL** | 必须定期重审（按流量排优先级），防 bait-and-switch |
| **靠失效缓存来下线恶意链接** | 独立封禁通道，与映射缓存正交 |
| **把“可丢的统计”结论套到计费场景** | 涉钱就要先持久化（WAL）+ 幂等 + 对账 |

## 12. 演进路线

| 阶段 | 规模量级 | 架构 | 该操心什么 |
|------|---------|------|-----------|
| MVP | 日点击 < 10 万 | 单体 + 一个 DB + 自增 ID 转 Base62；同步统计也无妨 | 先把「生成+重定向」跑通 |
| 成长期 | 百万~千万 | 读写服务拆开；加 KV 缓存；点击统计异步化；发号器换号段模式 | 找读路径瓶颈、把缓存命中率做上去 |
| 成熟期 | 亿级+全球 | 多区域多活、边缘/CDN 重定向、映射表分片、独立实时分析管道、封禁名单全集群广播 | 全球延迟、容灾、防滥用、分析体系、短码位数耗尽预案 |

## 13. 可复用要点

- **读多写少的系统**：把读路径优化到极致，和写路径彻底解耦。这是缓存、读写分离、CQRS 一切的出发点。
- **301 vs 302** 是「可缓存性 vs 可观测性」的微缩模型。任何「让中间层帮你缓存」的设计，几乎都要拿「我还看不看得见这次访问」来换。
- **全局唯一 ID** 是分布式系统基本功：中心发号、号段、雪花，各有取舍。
- **把非关键路径从关键路径上剥离**，是降低延迟、提升稳定性的通用手法。
- **不可变数据是架构红利，要主动用上**：不可变 → 不需 TTL、不需一致性维护、可无限制缓存/CDN。很多人把「缓存要设过期」的惯性套用到了不需要它的场景。
- **能用结构保证的，不要用检查保证**：命名空间隔离 > 生成后查重；同支付系统的「复式记账用结构保证资金守恒」。
- **冲突的两个需求不一定要妥协，可以拆成两条正交通道**：映射数据（不可变、永不过期）+ 封禁数据（频变、秒级下发）。
- **固定容量必须算耗尽时间**：短码位数、ID 位宽、分片数——任何「现在够用」的容量都要在设计时算出耗尽日期，并确保耗尽时能平滑扩容。
- **质量属性优先级由业务而非技术决定**：同一个点击统计，免费报表时可丢，按量计费时不可丢。先问商业模式，再定技术方案。
- **注意架构决策的连锁反应**：一个为成本优化做的决定（永不过期），可能在安全场景里变成致命约束（无法止血）。决策要跨场景交叉验证。
