# 实时通讯 / 群聊 IM 架构模板

> 代表产品：WhatsApp、微信、Slack、Discord、Signal、各类 IM / 群聊
> 一句话定位：让一条消息又快、又不丢、又有序地从一个人到达另一个人（或一群人）。

## 1. 一句话定位

一个实时通讯产品 = **一张「永远在线的消息投递网」**：几百万、上千万人同时挂着一条「随时能收到推送」的长连接，系统要保证任何人发出的每一条消息，都尽快、不丢、按正确顺序送到该收的人手里——对方在线就立刻送达，不在线就先存好、等他上线再补。

架构上最反直觉的三点：

1. **难点不在「发」，而在「维持海量长连接」**——一条消息很小，但「让千万条持久连接同时挂着、还能精准找到要把消息推给哪条连接」，会把架构逼向有状态连接 + 路由表。
2. **可靠与有序必须应用层自己保证**——网络随时会断，序号、确认、重试、去重这套机制无法外包。
3. **客户端不是「展示层」，它是系统的一个持久副本**——「不丢」的一半保障在用户设备上，而不是全靠服务端。

## 2. 业务本质：它在解决什么问题

用户要的是**「我发的消息，对方很快就能看到；对方发的，我立刻就收到；一条都不能丢、顺序还不能乱」**。它取代的是「打电话/发邮件」那种要么打断、要么很慢的沟通——IM 提供的是**即时、异步、有记录**的连续对话。

**价值与钱从哪来**：

- **粘性与网络效应**：关系链和历史都在这，迁移成本极高——这是最强的护城河
- **企业版 / 团队协作**（Slack、钉钉、飞书）：按席位订阅，卖的是团队沟通效率 + 集成生态
- **增值**：表情、会员、企业服务、平台生态

> **关键事实**：这类系统的负载形态是「**海量并发的持久连接 + 持续的小消息流**」，而不是「短平快的请求-响应」。普通网站的连接「来了就走」，这里的连接「来了就一直挂着」。这一条决定了为什么「长连接网关」「连接是有状态的」「怎么找到该把消息推给哪台机器上的哪条连接」会成为架构核心命题。

> ⚠️ **To C 和 To B 的架构答案不同**：To C（微信、WhatsApp）优先弱网、省电、海量在线、隐私；To B（Slack、钉钉）优先搜索、合规审计、集成 Webhook。同样是 IM，先问定位。

## 3. 核心需求与约束

### 功能性需求

- [ ] 发送 / 接收消息：一对一、一对多（群）
- [ ] 实时送达：对方在线时近乎瞬间到达
- [ ] 离线消息：对方不在线时不丢，上线后补齐
- [ ] 消息有序：同一会话内按发送顺序呈现
- [ ] 可靠投递：不丢、不重
- [ ] 在线状态（Presence）：在线/离线/正在输入
- [ ] 群组：成员管理 + 群消息扩散
- [ ] 多媒体：图片、语音、文件
- [ ] 多端同步：手机、电脑同时在线，消息与已读状态一致
- [ ] 撤回、已读回执、@提醒、历史搜索

### 非功能性需求 / 质量属性（架构主战场）

| 质量属性 | 目标 | 为什么对这类系统重要 |
|---------|------|-------------------|
| **消息时延** | 在线时 < 几百毫秒 | IM 的灵魂就是「即时」，慢了就不叫即时通讯 |
| **可靠投递** | 不丢、不重 | 丢一条重要消息 = 信任崩塌。**这是底线，优先于可用性** |
| **消息有序** | 单会话内严格有序 | 顺序乱了对话读不懂（「好啊」出现在「要不要吃饭」之前） |
| **海量并发连接** | 百万~千万级长连接 | **连接数是这类系统独有的核心规模指标**（不是 QPS） |
| 可用性 | 99.9%+ | 连不上=用不了。但**短暂不可用可被客户端待发队列兜住** |
| 多端一致 | 秒级收敛 | 手机看过的消息，电脑不该再提醒 |
| 在线状态实时性 | **最终一致即可** | 状态变化极频繁，允许短暂不准——这是宝贵的「松弛空间」 |
| 成本 | 存储随时间无限增长 | 消息只增不减，十年后存储与索引是第一大项 |

> ⚠️ 注意「消息不丢」**优先于**「可用性」——这跟短链接（可用性优先）正好相反。服务端短暂挂掉可以接受（客户端会重传），但确认收到后又丢了不能接受。

### 关键约束（不可逾越的边界）

- 🔴 **长连接是「有状态」的**：一条连接物理挂在某一台网关机器上，系统必须知道「某用户此刻连在哪台机器」才能推给他。这与无状态 Web 服务的扩展方式完全不同，是**头号约束**
- 🔴 **网络不可靠**：连接随时断、消息可能丢、可能重发。可靠与有序必须靠应用层机制（序号、确认、重试、去重）自己保证
- 🔴 **大群扩散**：一条消息发进万人群要触达每个成员——**扇出问题**，和社交信息流的大 V 同源
- 🔴 **消息不可变**：发出去就存在了。**撤回不是删除，是追加一条撤回记录（墓碑）**——审计与多端同步都要求如此
- 🔴 **群成员上限（500 vs 5000）是架构决策，不是产品参数**：它决定投递机制，投递机制决定数据模型（见决策 6）
- **消息写入量大且持续**：每条消息都要持久化以支持离线/历史/多端
- **移动端环境恶劣**：弱网、切后台被系统杀、省电限制后台连接
- **合规**：多地法规对 IM 有最短保存期限和内容审核要求

## 4. 架构全景图

```
┌──── 发送方 / 接收方客户端（也是一个持久副本，不是纯展示层）─────┐
│  本地 DB（SQLite）: 消息 + 会话 + last_synced_seq             │
│  待发队列: 未收到 ack 的消息（带客户端生成的 msg_id）           │
└────────┬────────────────────────────────────────▲────────────┘
         │ ① 发消息（长连接上行）                    │ ⑤ 推送（在线时）
         ▼                                         │
┌──────────────────────────────────────────────────────────────────────┐
│  长连接网关层（有状态：每台机器挂着一批持久连接；业务逻辑一律不放这里）    │
│  网关A          网关B          网关C   ...   (水平扩展，可挂百万级连接) │
└────┬──────────────────────────────────────────────┬──────────────────┘
     │ ② 上行消息                                     ▲ ④ "推给用户U" → 查路由
     ▼                                               │   → 找到U连在网关C → 投递
┌────────────────────┐         查询/更新              │
│  消息服务（核心）    │ ◀──── 用户↔网关 路由表 ────────┘
│  • msg_id 幂等去重  │       （用户U 此刻连在 网关C，内存级 KV）
│  • 分配会话内 seq   │              ▲
│  • 先持久化 再投递  │              │ 连接建立/断开时更新
│  • 在线/离线分流    │
└───┬──────────┬─────┘
    │          │ ③ 写入                        离线分支
    │          ▼                          ┌────────────────────┐
    │   ┌──────────────┐                  │ 离线信箱 + 推送服务  │
    │   │ 消息存储      │                  │ (唤起 APNs/FCM)    │
    │   │ 按会话分片    │                  └────────┬───────────┘
    │   │ seq 有序追加  │                           │ 上线后按游标拉取
    │   └──────┬───────┘◀──────────────────────────┘
    │          │ 冷归档
    │          ▼                    ┌──────────────────────────┐
    │   ┌─────────────┐             │ 同步服务（无状态）          │
    │   │ 对象存储归档 │             │ GET /changes?since=<seq> │
    │   └─────────────┘             └──────────────────────────┘
    │ 群消息扩散
    ▼
┌──────────────┐  ┌────────────────┐  ┌──────────────────────────────┐
│ 群组/成员服务 │  │ 在线状态服务     │  │ 媒体存储                       │
│ 小群写扩散    │  │ presence        │  │ 图/语音/文件走对象存储          │
│ 大群共享读取  │  │ 内存KV+TTL      │  │ **消息里只带引用，不塞字节**    │
│ 权限强一致    │  │ 最终一致        │  │                              │
└──────────────┘  └────────────────┘  └──────────────────────────────┘
```

**灵魂部件是两块**（少见的双核系统）：

1. **长连接网关层**——有状态地挂着海量持久连接，它是这类系统区别于普通 Web 的根本
2. **用户↔网关路由表**——要把消息推给某人时，先查到他此刻连在哪台网关

加上消息服务里的**「序号（保序）+ 先落库（不丢）+ 在线/离线分流」**，构成整套系统的核心机制。

> 🔑 架构主线：**有状态的接入层要极简，业务全放无状态层。** 网关一旦掺业务逻辑，发版就要断所有人的连接。

## 5. 组件职责

| 组件 | 职责 | 为什么需要 |
|------|------|-----------|
| **客户端本地库** | 持久化消息 + 待发队列 + 同步游标 | **不是缓存，是副本**——「不丢」的一半保障在这里；也是离线可用的基础 |
| **长连接网关层** | 维持海量持久连接、心跳保活、上行收/下行推 | 实时推送要求服务端能主动找到客户端，只能靠一直挂着的连接；轮询既慢又费。**必须极简、独立发版、支持客户端重连** |
| **用户↔网关路由表** | 记录「某用户此刻连在哪台网关」，连接建立/断开时更新 | 连接有状态，投递前必须知道 U 连在哪。**这是有状态连接得以水平扩展的关键拼图** |
| **消息服务（核心）** | msg_id 幂等去重 → 分配会话内 seq → 先持久化 → 在线/离线分流投递 | 可靠与有序不能靠网络自带，必须这一层用序号、落库、确认来保证 |
| 消息存储 | 按会话分片、seq 有序追加，支持离线补齐/历史/多端 | 消息不能只活在连接里，持久化是「不丢」和「多端一致」的基础 |
| **用户游标** | 每人存「已收到的最大 seq / 读到哪」 | 用一个数字代替 N 条状态记录；同时解决「补齐」和「去重」 |
| 离线信箱 + 推送服务 | 收方不在线时转存，并通过 APNs/FCM 唤醒 | 用户大量时间不在线，必须「人不在也不丢、回来能补上」 |
| 同步服务（无状态） | `GET /changes?since=seq` 返回增量 | 支撑离线、多端、弱网重连——**普通 CRUD 做不到** |
| 群组 / 成员服务 | 维护成员关系；群消息扇出；**权限判定强一致** | 群消息本质是扇出问题；被踢的人必须立刻读不到新消息 |
| 在线状态服务（Presence） | 在线/离线/正在输入 | 社交临场感的关键。但状态变化极频繁，**最终一致即可**——晚一两秒不致命 |
| 媒体存储 | 图/语音/文件存对象存储，消息里只带引用 | 大文件不能挤占低时延的消息通道 |
| 冷归档 | 老消息移到对象存储 | 存储与索引成本控制（决策 8） |

## 6. 关键数据流

### 场景一：一对一发消息，收方在线（最核心的实时路径）

```
1. 发送方客户端：生成 msg_id（UUID 或 设备ID+本地序号）
   → 写本地 DB + 入待发队列 → UI 显示「发送中」    ← 0ms，用户立刻有反馈
2. 经长连接上行到 网关A ── 上行 ──▶ 消息服务
3. 消息服务：
     a. msg_id 幂等检查（唯一约束）→ 已存在则直接返回原 ack（重传安全）
     b. 分配【会话内序号 seq=N】                  ← 保证顺序
     c. 持久化这条消息                            ← 先落库，保证不丢
     d. 查【路由表】：收方 U 此刻连在 网关C，在线
4. 返回 ack 给发送方 → UI 变「已发送」            ← 几十 ms，可靠性确认
5. 消息服务 ──"投递给U"──▶ 网关C ──推送──▶ 收方屏幕
6. 收方收到后回【ack(收到了 seq=N)】→ 发送方 UI 变「已送达」
7. 没收到 ack → 按策略重试；收方靠 seq/msg_id 去重（重复的丢弃）
```

**这条路径里藏着两组核心机制：**

**① 可靠投递三件套**：先落库、再投递（不丢）+ 会话内单调序号（有序）+ ack/重试/按 ID 去重（可靠且不重）。

**② 状态分级**（第 1 步和第 4 步的分离）：

| UI 状态 | 谁保证 | 耗时 |
|---------|-------|------|
| **发送中**（转圈） | 客户端本地已落库 | **0ms** ← 满足「立刻反馈」 |
| **已发送**（单勾） | 服务端已持久化并 ack | 几十 ms ← 满足「绝对不丢」 |
| 已送达（双勾） / 已读 | 对端客户端确认 | — |

> 微信、WhatsApp 的双勾号不是产品设计，是**架构决策的 UI 投影**——把「立刻反馈」和「可靠确认」拆成四个状态，**两个需求都拿到，不必妥协**。
>
> ⚠️ 但注意**哪个状态由谁盖章**：客户端只能盖「我记下了」，「已送达/已读」必须由对端确认。客户端不能宣布「对方收到了」。

### 场景二：收方离线 / 多端同步 / 弱网重连（存 + 推 + 按游标补齐）

```
1~3. 同上：幂等 → 定序 → 落库 → 查路由发现 U 不在线
4. 写入 U 的【离线信箱】
5. ──▶ 离线推送服务：通过 APNs/FCM 唤醒 U 的设备（只推「有新消息」，不推内容）
6. （一段时间后）U 打开 App、建立长连接 ──▶ 网关更新路由表（U 现在连在 网关B）
7. U 带着 last_synced_seq = 1042 拉增量：
       GET /changes?since=1042
   → 服务端只返回 1042 之后的所有变更（新消息、撤回墓碑、已读游标变化）
8. 客户端合并 → 按 seq 排序呈现 → 更新本地游标
9. 同时把待发队列里未 ack 的消息重传（msg_id 保证不重复）
```

> 🔑 **游标同时解决三件事**：断点续传式补齐（不漏）、去重（不重）、增量传输（不用全量比对）。
>
> **这个机制在三个不同系统里是同一个东西**：IM 的同步游标 = 群聊已读游标 = 短链接的日志补算位点。看到「N 条状态记录」就想想能不能换成一个游标。
>
> 由此也说明为什么「同步接口 ≠ 普通 CRUD」：普通 CRUD 是「给我第 N 条」，**同步接口是「给我第 X 号之后发生的所有事」**。后者才能支撑离线。

### 场景三：群消息扩散（扇出问题）

```
某人在群里发一条消息 ──▶ 消息服务（分配该群会话的 seq、落库一次）
   ──▶ 群组服务：取出群成员列表
   ──▶ 在线的 → 查路由表投递；离线的 → 各自离线信箱 + 推送

   小群（几十人）：直接逐个扇出，没问题
   万人大群：一条消息瞬间要触达上万人 → "扇出爆炸"（同社交流的大V问题）
      ✅ 大群优化：只存"一份共享的群消息流"，成员各自维护"读到哪了"的位点，
                  按位点来拉，而非给每人都推一份/存一份
```

**先算一笔账再决定**（估算的意义就在这里）：

日活 100 万、人均 20 条、平均群 50 人 → **发消息请求只有 200 QPS**，但推模式扇出后是 **10,000 写/秒**（峰值 3 万）。

> ❗ **注意这里的顺序：先改机制（消解），再谈扩容（硬扛）。**
>
> - ❌ 硬扛路线：3 万写/秒 → 上分片 / 换写优化存储 → **永久背上分片复杂度**
> - ✅ 消解路线：改数据模型（共享一份 + 游标）→ **写入回落到 200/秒** → 此时单体 + 缓存就够了
>
> 大多数人跳过第一步直接去分片，**为一个本来不该存在的问题付了永久的复杂度成本**。

大群扩散和社交信息流的「大 V 写扩散爆炸」是同一个问题：**一次写要触达海量接收方**。解法也同源——别给每人都拷一份，改成共享一份、各自按位点来拉。

## 7. 数据模型与存储选择

核心实体：用户；会话（一对一 / 群）；消息（带会话内 seq + 客户端生成的 msg_id）；用户↔网关路由；会话成员关系；在线状态；已读/同步位点。

| 数据 | 存储类型 | 为什么 |
|------|---------|-------|
| 消息（持久） | **有序追加存储，按 conversation_id 分片**（宽列/LSM 类） | 写多、按会话有序读、支持离线补齐与历史；LSM 顺序写适合高写入 |
| 用户↔网关 路由表 | **内存级 KV** | 极高频读写（每条消息投递都要查）、要极低延迟、连接变动频繁 |
| 在线状态（presence） | **内存级 KV（带 TTL）** | 变化极频繁、读频繁、可最终一致 |
| 离线信箱 | KV / 有序队列（按用户） | 按用户存待收消息，上线后按 seq 拉取 |
| 用户游标（synced_seq、read_cursor） | KV | 极简点查点写、超高频更新 |
| 会话 / 群成员关系 | 关系型 / 宽列 | 成员管理要一致；大群成员列表可能很长 |
| 媒体（图/语音/文件） | 对象存储 | 文件大、不可变；消息里只存引用 |
| 近期消息全文索引 | 搜索引擎，**只索引近 N 个月** | 索引是原始数据 1~3 倍且必须放贵存储（决策 8） |
| 冷历史消息 | 对象存储归档 | 访问极少，成本降一到两个数量级 |
| 用户账户 | 关系型 | 要事务、强一致（账号安全） |

**两个教学点：**

1. **消息流和路由表是两类访问形态完全不同的数据。** 消息要持久、有序、可回溯 → 有序追加存储；路由表要「每次投递极速查一下 U 连在哪」→ 内存级 KV。**把路由表放进慢速持久库，会让每条消息的投递都被拖慢。**

2. **消息表的分片键必须是 conversation_id，不能是 user_id。** 因为读取形态永远是「拉某个会话的一段消息」。**分片键选错要重导全部数据**——这是这个模板里最难改的决策。

#### ❗ 那「全局搜索我的所有消息」怎么办？

用户在 200 个群里，搜一个词——按 `conversation_id` 分片的话要**扫 200 个分片**，查询形态和分片键完全不匹配。

**❌ 错误解法：改成按 user_id 分片。** 这会毁掉主路径：
- 群里 50 人 → 一条消息要写进 **50 个不同分片**（刚消解掉的写放大又回来了）
- 拉一个会话的消息要**跨分片聚合**，而这是 99% 的读操作

> **用 1% 的搜索需求毁掉 99% 的主路径，是分片键选择的经典错误。**

**✅ 正解：两种访问形态 → 两套存储，各按自己的形态组织。**

```
消息存储（真相源）                 搜索索引（派生数据）
按 conversation_id 分片    ──→    按 user_id 组织的倒排索引
服务「拉某会话一段消息」    异步同步   服务「某用户搜关键词」
LSM/宽列，有序追加                搜索引擎（只索引近 N 个月）
```

- 主存储按主路径的形态分片 → 99% 流量最优
- 搜索索引按 `user_id` 组织 → 搜索走一个分片，不用扫 200 个
- 索引是**派生数据，可从真相源重建**，允许异步滞后

> 🔑 这就是 **CQRS 的核心思想：读和写用不同的数据模型。** 不要试图用一套存储的一种组织方式满足所有查询——那注定要么毁主路径，要么搜索烂。
>
> ⚠️ 注意区分两个不同维度的问题：**「索引放在哪、怎么组织」**（本节，架构问题）vs **「索引多少数据」**（决策 8，成本问题）。

## 8. 关键架构决策与权衡 ⭐

### 决策 1：长连接怎么维持与水平扩展？（本架构的命门）

**问题根源**：长连接是有状态的——一条连接物理挂在某台网关上。无状态 Web「随便哪台机器都能处理任意请求」的扩展方式在这里**失效了**，因为「要把消息推给 U」必须送到「U 实际连着的那台机器」。

| 方案 | 优势 | 代价 |
|------|------|------|
| A. 单机纵向 | 简单 | 连接数有物理天花板；单点故障 = 全员掉线 |
| **B. 水平扩展 + 路由表** | 可扩到千万连接 | ① 多一层路由表且要随连接变动实时更新（高频写）② 投递路径多一跳查询 ③ 网关故障时其上所有连接要能重连并刷新路由 |

**取向**：必然走 B。

**配套的四个工程问题**：

| 问题 | 解法 |
|------|------|
| 不知道用户连在哪 | `uid → 网关ID` 路由表（内存级 KV），投递前先查 |
| 网关重启/发版 = 断掉这台机器上所有连接 | **网关极简、独立发版**；客户端自动重连 + 拉增量（游标兜住） |
| 单机连接数上限 | 单机几万到几十万（受内存/FD 限制）→ **按连接数水平扩，不是按 QPS** |
| 发版/故障引发重连风暴 | 分批灰度 + 客户端**随机退避重连**（防止雪崩式同时重连） |

> 💡 **「有状态资源 + 一张『状态在哪』的路由表」是让有状态服务水平扩展的通用套路**——它把「状态绑定」与「按状态路由」显式分离。任何有状态资源（连接、会话、分片主副本、GPU 上的模型实例）都可借鉴。

### 决策 2：消息时序怎么保证？

| 方案 | 问题 |
|------|------|
| ❌ 按到达时间排序 | 网络抖动、重发让到达顺序 ≠ 发送顺序 → 乱序 |
| ❌ 按客户端时间戳排序 | 手机时间可手动改、有时区和漂移 |
| ✅ **会话内单调递增序号（服务端定序）** | 接收端按 seq 排序呈现，而非按到达顺序 |

**取向**：服务端定序（sequencer），且保序范围**限定在单个会话内**——不需要全局有序（代价极高且没必要，用户只关心「这个对话里的顺序」）。代价是要有「为某会话发号」的机制，通常按会话分片发号以免成为瓶颈。

> 💡 **「在真正需要顺序的最小范围内保序」——范围收敛是性能与复杂度的关键。**

**这属于哪一档一致性？** 既不是强一致，也不是最终一致，而是**顺序（因果）一致性**：不要求「写完立刻全网可见」，但要求「所有人看到的顺序相同」，且**不处理就永远不会自己变对**。

**关键在因果关系，不是所有消息都需要保序：**

| 情况 | 有因果吗 | 顺序要求 |
|------|---------|---------|
| 李四**读到**张三的消息后才回「好的」 | **有**（因果依赖） | 必须保序，否则语义崩坏 |
| 私聊两人**同时**发消息（谁也没看见谁） | **无**（并发消息） | 顺序随意，各端不同也无所谓 |

> 💡 这解释了一个日常现象：**微信私聊两人同时发消息，双方看到的顺序可能不同，但没人觉得有问题**——并发消息之间没有因果，顺序本就没有客观答案。群聊回复密集、因果链多，才必须靠服务端定一个所有人都认的序。

### 决策 3：可靠投递（不丢、不重）怎么做？

| 方案 | 问题 |
|------|------|
| ❌ 发出去就不管 | 网络一抖就丢，违背底线 |
| ✅ **ack + 重试 + 幂等去重（三件套）** | ① 收方回 ack ② 没收到 ack 就重试 ③ 重试导致重复，靠 seq/msg_id 去重 |

再叠加**「先持久化、再投递」**：即使投递失败，消息也没丢、可重投。

**取向**：三件套缺一不可，因为**重试和去重是一对孪生机制**——你为了「不丢」而重试，就必然引入「重复」，于是必须去重。

> 💡 **至少一次投递 + 幂等去重 = 恰好一次的效果。** 分布式下 exactly-once 不存在，这是唯一可行的组合。适用于消息、支付回调、事件投递。
>
> 💡 **先落库、再投递**——把「持久化」放在「送出」之前，是「不丢」的根基。任何要求可靠的写-投递链路都成立。

**它的真正意义不只是防崩溃，而是为「投递失败」这条最常见的路兜底：**

场景：路由表说 U 连在网关 C，但**网关 C 整台崩了**（路由表记录还没来得及清）。

| 顺序 | 投递失败那一刻，消息服务手上有什么 | 结果 |
|------|--------------------------------|------|
| ❌ 先投递、再落库 | **什么都没有**——投递指令连同消息内容一起随网关消失 | 发送方以为发出去了，收方永远收不到，**消息凭空蒸发** |
| ✅ **先落库、再投递** | 消息**已在消息存储里**，是系统里确定存在的事实 | 转存离线信箱 / 重投 / 等 U 重连后按游标拉走——**随时能重来** |

> 🔑 **因果方向要说对**：不是「因为要不丢所以先落库」，而是「**先让消息成为已确定的事实，投递才可以是一次能失败任意多次的尝试**」。不丢是这个前提带来的结果。
>
> 这也解释了网关崩溃窗口期（从 C 崩掉到路由表更新为 A）里的消息去哪了：**它们一直在消息存储里躺着**，U 重连后带 `last_synced_seq` 一拉就补齐了。**窗口期不需要特殊处理，因为先落库已经兜住了。**

**不丢的四个环节由谁保障**（注意有一半在客户端）：

| 环节 | 谁保障 |
|------|-------|
| 用户点发送 → 网络异常 | **客户端本地库 + 待发队列**（持久副本），重连后重传 |
| 服务端收到 → 未持久化就崩了 | 未返回 ack，客户端会重传（配合 msg_id 幂等） |
| 已持久化 → 接收方离线 | 消息在服务端，接收方上线后靠**游标拉增量** |
| 接收方收到 → 本地未落库就崩了 | 游标未推进，下次同步会再拿一次 |

> 🔑 **「不能丢」≠「服务端必须在返回前落盘并等多副本确认」。** 当客户端也是持久副本时，可靠性由「**两端各留一份 + 可重传**」保障，**延迟不用付代价**。这是 IM 能同时做到「0ms 反馈」和「绝对不丢」的根本原因。

### 决策 4：消息 ID 由客户端还是服务端生成？

| 方案 | 优势 | 代价 |
|------|------|------|
| 服务端生成 | ID 全局有序、可信 | **无法离线发送**；超时重传时服务端分不清「新消息」和「重传」→ **群里出现重复消息** |
| **客户端生成** | 支持离线发送；服务端用它做唯一约束 → **重传 100 次也只存一条** | ID 无全局顺序（但顺序由 seq 负责，不需要 ID 有序） |

**取向**：客户端生成（UUID 或 设备ID+本地递增）。

> 🔑 这是**用结构保证而非检查保证**——不是「先查有没有再插」，而是让唯一约束在结构上排除重复。**这一条决策同时解锁了「离线发送」和「幂等重传」两个能力**，是本模板最容易判错的架构决策（很多人以为 ID 谁生成都一样）。

### 决策 5：群消息扩散——写扩散还是共享读取？

| 方案 | 机制 | 实际写操作（上例） | 代价 |
|------|------|------------------|------|
| 写扩散（推） | 每个成员一份收件箱 | **10,000 写/秒** | 小群很自然、读时简单；**大群爆炸** |
| 读扩散（拉） | 读时聚合所有会话 | 200 写/秒 | 读慢（要聚合几十个会话） |
| **共享一份 + 每人游标** | 群内存一份消息，每人只存「读到哪」 | **200 写/秒** | 读时按游标拉取，需缓存优化 |

**取向**：**小群写扩散、大群共享读取**（和社交流「普通人推、大 V 拉」同构）。代价是系统里同时存在两套群消息处理路径。

> 更彻底的做法是**一律共享读取**——虽然读路径要做缓存优化，但换来了「群成员上限不再是架构约束」这个红利（见决策 6）。**先消解，再决定要不要保留第二条路径。**
>
> 💡 **任何「一次写触达海量接收方」的扇出问题，解法都在「各拷一份 vs 共享一份按需拉」之间权衡。** 大群扩散、社交大 V、广播通知，本质同源。

### 决策 6：群成员上限设 500 还是 5000？

**这是架构决策，不是产品参数。** 传导链条：

```
上限 → 决定投递机制（推 vs 共享读取）
     → 决定数据模型（每人一份收件箱 vs 群共享一份 + 游标）
     → 数据模型是整个系统里最难改的东西
```

**取向**：**先按决策 5 消解扇出，此时上限就不再是架构约束**，可以纯按产品需要定。

> ❌ 反面案例：先用推模式做了 500 人上限，两年后产品要 5000 人群 → 要改投递机制 + **迁移全部历史数据**。

### 决策 7：在线状态（presence）要多准？

| 方案 | 问题 |
|------|------|
| ❌ 强一致、实时精确 | 状态变化极频繁（切前后台、断网、心跳都变），强一致代价极高且没必要 |
| ✅ **最终一致 + 内存级 KV + TTL** | 允许短暂不准（对方刚下线你可能还显示在线一两秒） |

**取向**：最终一致足矣。

> 💡 **presence 是典型的「可以不那么准」的数据，把它当强一致来做是巨大的浪费。识别出「哪些数据允许短暂不准」，能省下大量成本**——这是宝贵的设计自由度。

#### ❗ 但它为什么可以不准？边界在哪？

**不是因为「用户看不出来」**（这个理由筛不掉任何东西），而是因为 **presence 只是 hint，不是判定依据**——它只影响「走哪条投递路径」，不决定「消息该不该存在」：

| 猜错情形 | 后果 | 谁兜住 |
|---------|------|-------|
| 说在线，实际刚掉线 | 投递失败 | **消息已落库** → 转存离线信箱 |
| 说离线，实际刚上线 | 多发一条推送通知（用户开着 App 却收到「你有新消息」） | 用户已看到消息，通知只是噪音；可用「等 ack，没 ack 才补推送」减少噪音 |

**两条路都通向同一个正确结果**，只是快慢和噪音不同 → 所以它可以不准。

**判断能否最终一致的第三把尺子**（前两把是「会不会赔钱」「能不能自愈」）：

| 数据角色 | 猜错的后果 | 能最终一致吗 |
|---------|-----------|-------------|
| **hint（路径优化提示）** | 走慢路或多做一次无用功，**下游有兜底** | ✅ 可以 |
| **判定依据** | 判错就错了，**没兜底、不自愈** | ❌ 必须强一致 |

对照本模板里的一致性分层（**同一个系统三档并存，各按需要选**）：

| 数据 | 档位 | 为什么 |
|------|------|-------|
| 消息顺序 | **顺序（因果）一致** | 顺序乱了语义崩坏，且不会自愈 |
| **群成员关系（用于权限判定）** | **强一致** | 判错 = 越权读到不该看的消息，不会自愈，没有下游兜底 |
| 群成员关系（用于 UI 显示成员列表） | 最终一致 | 晚一秒消失无所谓 |
| presence、已读回执 | 最终一致 | 都是 hint 或可容忍噪音 |

> 🔑 **同一份数据（群成员关系）在不同用途上分不同档**——这比「整份数据定一个档」精细得多，也是省成本的关键。

### 决策 8：历史消息永久保存 + 全文搜索 + 成本可控，怎么同时满足？

**最尖锐的冲突不是「永久保存 vs 成本」，是「全文搜索 vs 成本」**——存原始文本很便宜（压缩后一条几十字节），但**索引通常是原始数据的 1~3 倍，且必须放在能随机访问的贵存储上**。

关键事实：**99% 的搜索打在最近 5% 的数据上。**

| 方案 | 他得到什么 | 他付出什么 | 成本 |
|------|-----------|-----------|------|
| A. 全量热存 + 全量索引 | 十年消息全部秒搜 | 无 | **极高** |
| **B. 冷热分层**：近 3 月热存可秒搜，更早归档对象存储 | 成本降 80~90%，**近期体验完全不变** | 查十年前要「发起检索」，等几秒到几十秒 | 中 |
| C. 免费 3 个月 + 付费永久 | 成本与收入挂钩，自然可持续 | 需做会员体系 | 技术成本低 |

**取向**：**B + C**——技术上分层砍掉 90% 成本，商业上把「永久」做成付费权益。

### 决策 9：已读回执怎么存？

| 方案 | 存储量（50 人群 × 100 条） | 说明 |
|------|--------------------------|------|
| ❌ 每条消息记「谁读了」 | **5,000 条记录**，随消息数线性增长 | 扇出爆炸 |
| ✅ **每人一个 read_cursor** | **50 条记录**（每人一个数字） | 「读到 seq=1088」隐含「1088 之前全读过」 |

**取向**：游标。代价是无法表达「跳着读」（实际业务也不需要）。

### 决策 10：撤回和删除怎么做？

**消息不可变**，所以：

- **撤回 = 追加一条撤回记录（墓碑）**，不是物理删除
- **服务端也不能物理删除**：三设备场景下，手机撤回 → 服务端物理删 → 平板一周后联网，`GET /changes?since=X` 里**没有任何撤回痕迹** → 平板把本地那条**又传回去** → **撤回的消息复活**
- 墓碑保留一段时间（直到所有设备确认或固定期限）后再做 GC

> 🔑 **分布式同步里最难的操作是删除**——因为「不存在」这个状态没法传播，你只能用「**一条说明它不存在的记录**」来传播它。

### 决策 11：端到端加密要不要做？（IM 最硬的取舍）

E2EE 和一批服务端能力**根本冲突**——服务端拿不到明文，就做不了这些事：

| 能力 | E2EE 下还能做吗 | 能否消解 |
|------|---------------|---------|
| 服务端全文搜索 | ❌ | ✅ **能消解**：改为客户端本地建索引（Signal 的做法） |
| 多端历史漫游 | ⚠️ | ✅ 能消解：需额外的密钥同步机制 |
| **内容审核 / 合规审计** | ❌ | ❌ **无法消解**，必须选边 |

**取向**：
- **To C 隐私优先**（Signal、WhatsApp）→ 做 E2EE，搜索挪到客户端
- **To B 协作**（Slack、钉钉）→ **不做 E2EE**，企业客户明确要求审计、合规、管理员可查
- 折中：默认不加密，敏感会话可选「加密聊天」（Telegram 的做法）

> ❗ **这是「冲突能不能被消解」的一个重要反例**——搜索这一项可以消解（挪到客户端），但**合规审计无法消解**。遇到这类冲突不要硬找消解方案，**先问业务是 To C 还是 To B**，答案完全不同。

## 9. 规模化与瓶颈

和普通系统不同：这里的**头号瓶颈是「长连接数」和「连接路由」**，其次才是消息写入与大群扩散。

| # | 瓶颈 | 破解 |
|---|------|------|
| 1 | **长连接数**（单机内存/FD 上限，不是 CPU） | 网关水平扩 + 路由表 + 就近接入 + 连接负载均衡；**扩容指标是连接数，不是 QPS** |
| 2 | **大群扇出** | 共享读取（读扩散）+ 已读位点拉取，而非给每人推/存一份 |
| 3 | **消息存储写入量** | 按会话分片打散写入；冷消息归档；写入路径异步化/批量化 |
| 4 | **路由表 / presence 高频读写** | 内存级 KV、按用户分片；presence 用最终一致 + TTL 降写压 |
| 5 | 大群消息风暴（万人群刷屏） | 合并推送、限频、只推「有新消息」让客户端拉、大群降级为只读广播 |
| 6 | 历史存储与索引无限增长 | 冷热分层 + 索引只建近期 + 对象存储归档 |
| 7 | 离线推送受第三方限制（APNs/FCM 配额与延迟） | 推送去重合并、只推摘要、重要消息才推 |
| 8 | 媒体流量挤占消息通道 | 对象存储 + CDN，消息只带引用 |
| 9 | 网关发版引发重连风暴 | 分批灰度 + 客户端随机退避重连 |

## 10. 安全与合规要点

- **端到端加密（取决于产品定位）**：见决策 11。是否上 E2EE 是**产品级取舍**，不是技术优劣问题
- **元数据隐私**：即便消息内容加密，**「谁和谁在何时聊」这类元数据本身也高度敏感**，要尽量少留、严控访问
- **群与权限必须服务端强制**：谁能进群、谁能看历史，**不能只靠客户端隐藏**；被移出群的人**必须立刻读不到新消息**（权限强一致；成员列表 UI 显示可最终一致）
- **消息隐私与最小留存**：传输与存储加密、访问控制、明确的留存与删除策略
- **传输加密**：即便不做 E2EE，客户端到服务器链路也必须加密
- **内容审核**：多地法规强制。与 E2EE 冲突（决策 11）
- **保存期限**：部分地区法规要求最短保存期限，这是**约束不是可选项**
- **滥用与垃圾消息**：防骚扰、防垃圾、防批量拉群 → 风控 + 限流
- **客户端不可信**：本地数据可被改（root/越狱/改包/改时间）；权限、成员关系、seq 一律**服务端裁决**

## 11. 常见误区 / 反模式

| 反模式 | 正确做法 |
|--------|---------|
| ❌ 用轮询代替长连接 | 轮询要么慢（间隔长）要么费（间隔短狂打服务器），做不到真正实时 |
| ❌ 不分配序号，按到达顺序展示 | 网络抖动/重发必然乱序，用**会话内单调序号**保序 |
| ❌ 按客户端时间戳排序 | 手机时间可手动改，有时区和漂移 |
| ❌ 不做去重，重试导致消息重复 | 为「不丢」而重试必然带来重复，必须靠 seq/msg_id 幂等去重 |
| ❌ 发出去就不管，不做 ack/重试 | ack + 重试 + **先落库再投递**才能不丢 |
| ❌ **服务端生成消息 ID** | 客户端生成，才能离线发送 + 幂等重传 |
| ❌ 大群同步写扩散 | 万人群一条消息瞬间上万次投递 → 共享读取 + 位点拉取 |
| ❌ 把连接当无状态、随意路由 | 连接有状态，必须有路由表知道用户连在哪 |
| ❌ **长连接网关里写业务逻辑** | 有状态层要极简，发版才不会断所有人连接 |
| ❌ **用 QPS 做扩容指标** | 长连接系统的核心指标是**连接数**和**扇出量** |
| ❌ presence 当强一致来做 | 状态变化极频繁，最终一致足够，强一致是巨大浪费 |
| ❌ 把媒体字节塞进消息流 | 大文件挤占低时延通道，应存对象存储、消息只带引用 |
| ❌ **把客户端本地存储当缓存** | 它是**持久副本**，是「不丢」保障的一半，也是 0ms 反馈的来源 |
| ❌ **物理删除消息 / 撤回即删** | 墓碑：撤回是追加记录，两端都不物理删，否则撤回会失效复活 |
| ❌ **给十年历史全量建索引** | 索引只建近期；99% 的搜索打在最近 5% 的数据上 |
| ❌ **每条消息存「谁读了」** | 每人一个 read_cursor，扇出从 N 降到 1 |
| ❌ **追求 exactly-once 投递** | at-least-once + 幂等去重，分布式下 exactly-once 不存在 |
| ❌ **客户端宣布「对方已收到」** | 客户端只能盖「我发出了」，送达/已读必须对端确认 |
| ❌ **消息表按 user_id 分片** | 必须按 conversation_id——读取形态永远是「拉某会话的一段」 |
| ❌ **遇到写瓶颈直接分片** | 先问「为什么有这么多写」，改机制消解往往能降两个数量级 |
| ❌ **先投递、再落库** | 投递失败时消息凭空蒸发；先落库让它成为事实，投递才能失败重来 |
| ❌ **为支持全局搜索而改按 user_id 分片** | 会毁掉主路径（群 50 人 = 写 50 个分片，拉会话要跨片聚合）。应建**独立的搜索存储按 user_id 组织**，异步同步、可重建 |
| ❌ **把 presence 不准的理由说成「用户看不出来」** | 真正原因是它只是 **hint 有兜底**；判定类数据（如群权限）即使用户也看不出来，照样必须强一致 |

## 12. 演进路线：MVP → 成长期 → 成熟期

| 阶段 | 规模量级 | 架构长什么样 | 此时该操心什么 |
|------|---------|------------|-------------|
| **MVP** | 几万用户，千级同时在线 | 单机长连接 + 单一消息存储；**seq / ack / 客户端 msg_id / 离线信箱 / 游标这几个机制从第一天就要有**；无大群优化 | 先把「实时、不丢、有序」的基本盘做对；连接都在一台机器上还撑得住 |
| **成长期** | 百万级连接 | 分布式长连接网关 + 路由表；离线存储 + 推送；消息存储按 conversation_id 分片；presence 用内存 KV；已读用游标 | 长连接水平扩展、连接路由可靠性、可靠投递在分布式下依然成立；盯住第一批大群 |
| **成熟期** | 千万级连接 / 海量消息 | 大群共享读取 + 位点；多活多区域 + 就近接入；冷热分层归档；独立搜索集群（只索引近期）；完善多端同步；（按定位）E2EE + 风控合规 | 大群扇出、连接规模、容灾多活、存储与索引成本、隐私与合规 |

> ⚠️ **唯一不能等到成长期再做的是数据模型**：消息表分片键（conversation_id）、消息 ID 由客户端生成、共享一份 + 游标——这三个决策改起来要**重导全部历史数据**。其他都可以后加。

## 13. 可复用要点

- 💡 **有状态服务靠「状态绑定 + 路由表」来水平扩展。** 长连接挂在某台机器上，就用一张「状态在哪」的路由表来定位它。任何有状态资源（连接、会话、分片主副本、GPU 上的模型实例）的扩展，都可借鉴这种「把状态绑定与按状态路由显式分离」的套路。
- 💡 **有状态层要压到最薄，业务全放无状态层。** 这样两者才能各自按自己的方式扩展、独立发版——网关发版只影响连接（客户端自动重连恢复），逻辑层发版不断连。
- 💡 **在「真正需要顺序的最小范围」内保序，别追求全局有序。** 单会话内用序号保序就够，全局有序代价高且无意义。**范围收敛是性能与复杂度的关键。**
- 💡 **至少一次投递 + 幂等去重 = 恰好一次的效果。** 重试（防丢）与去重（防重）是一对孪生机制——任何「不可靠信道上要可靠送达」的场景都适用，从消息到支付回调到事件投递。
- 💡 **先落库、再投递。** 把「持久化」放在「送出」之前，是「不丢」的根基——这条次序原则在任何要求可靠的写-投递链路里都成立。
- 💡 **客户端/边缘也是一个副本，不是缓存。** 「不能丢」≠「服务端返回前必须落盘」——两端各留一份 + 可重传，能同时拿到 0ms 反馈和绝对不丢。适用于 IM、协同编辑、离线优先 App、文件同步。
- 💡 **状态分级可以消解「立刻」与「可靠」的冲突。** 拆成发送中→已发送→已送达→已读，两个需求都拿到。**但要注意哪个状态由谁盖章**：客户端只能盖「我记下了」，不能盖「事情成了」。
- 💡 **游标模式：用一个「读到哪」的数字代替 N 条状态记录。** 同一个模式在三个场景出现——群聊已读、离线增量同步、短链接日志补算。看到「N 条状态记录」就想想能不能换成一个游标。
- 💡 **「一次写触达海量接收方」永远是扇出问题**，解法在「各拷一份 vs 共享一份按需拉」之间。大群扩散、社交大 V、广播通知，本质同源。
- 💡 **先改机制（消解），再谈扩容（硬扛）。** 算出 3 万写/秒时先问「为什么有这么多写」。改数据模型让它回落到 200/秒，比扛住 3 万便宜一万倍。
- 💡 **识别「允许不那么准/不那么实时」的数据，把它降级处理。** presence 用最终一致省下大量成本。**哪里能松弛，哪里就能换来弹性与省钱。**
- 💡 **一个系统里可以三档一致性并存**：消息顺序要顺序（因果）一致、群权限要强一致、presence 和已读可最终一致。别用一档打天下。
- 💡 **用结构保证而非检查保证**：客户端生成 ID + 唯一约束，而不是「先查再插」。
- 💡 **扇出比 QPS 更早压垮系统**：看到「一人发多人收」的业务关系，就要算写放大，而不是只算请求数。**长连接系统的扩容指标是连接数，不是 QPS。**
- 💡 **有些冲突无法消解，必须选边。** E2EE vs 合规审计就是——搜索能挪到客户端，审计不能。这时先问「业务是 To C 还是 To B」。
- �� **判断能否最终一致的第三把尺子：这份数据是 hint 还是判定依据。** hint 猜错有下游兜底（presence 猜错 → 投递失败 → 落库兜住），判定猜错就错了（群权限判错 → 越权读取，不会自愈）。**同一份数据不同用途可分不同档。**
- 💡 **「是副本」和「不可信」分管两件事**：前者管数据在哪（可持有、可先写），后者管谁说了算（判定权在服务端）。**客户端可以是仓库，但不能是法官。**
- 💡 **读写形态冲突时用两套存储（CQRS）**：主存储按主路径形态分片，派生存储（搜索/报表）按各自形态组织，异步同步、可重建。**不要为 1% 的查询需求毁掉 99% 的主路径。**

## 🎯 随堂检验

**Q1：在不可靠网络上做到消息「不丢、不重」，通常的组合是？**

- A. 只重试
- B. **至少一次投递 + 幂等去重** ✓
- C. 只去重

> 重试（防丢）与去重（防重）是一对孪生机制，合起来达到「恰好一次」的效果——任何不可靠信道上的可靠送达都适用。

**Q2：消息 ID 由客户端生成，主要解锁了什么能力？**

- A. ID 全局有序
- B. **离线发送 + 幂等重传** ✓
- C. 减少服务端计算

> 服务端生成 ID 时，超时重传会被当成新消息 → 群里出现重复；且离线时拿不到 ID 就无法先写本地。

**Q3：算出群消息扇出后是 3 万写/秒，第一步该做什么？**

- A. 上分库分表
- B. 加读写分离
- C. **先问「为什么有这么多写」，改数据模型消解** ✓

> 复制/读写分离只扩读，对写瓶颈无效。改成「群共享一份 + 每人游标」能让写入回落到 200/秒，此时根本不需要分片。
