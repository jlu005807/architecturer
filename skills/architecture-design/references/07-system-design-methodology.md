# 07 · 从 0 到 1 设计一个系统：实战方法论

> 参考章节：把前六章工具拧成一条流水线，从需求到架构方案完整走一遍。

## 核心论点

**架构不是画出来的，是从约束里逼出来的。** 接到需求后的前几分钟，一个框都不画，只问问题。

## 八步流程

不是一条直线，而是会反复回头的循环：

```
                  ┌─────────────────────────────────────────────┐
                  │                                             │
                  ▼                                             │
   ① 澄清需求与范围 ──▶ ② 估算规模 ──▶ ③ 定义用例/API 边界       │
                                              │                 │
                                              ▼                 │
   ⑤ 画高层架构 ◀────────────────── ④ 设计数据模型             │
        │                                                       │
        ▼                                                       │
   ⑥ 逐个深入关键组件 ──▶ ⑦ 找瓶颈,针对性扩展                  │
                                              │                 │
                                              ▼                 │
                              ⑧ 回顾取舍/列风险/列未决问题 ────┘
                                   发现问题就回到任意一步重来
```

| 步骤 | 你在干什么 | 对应哪章 |

## 步骤① 澄清需求与范围

要问的问题分三类：

- **功能边界**：MVP 到底做什么、不做什么？把不做的明确划出去比列要做的更重要
- **用户与规模**：谁用？多少人？增长多快？→ 喂给步骤②
- **质量与约束**：多快？能不能短暂不可用？数据能不能丢？合规/成本红线？

**关键心法**：目标不是满足所有需求，而是确认哪些需求其实不重要。范围每砍掉一块，架构就简单一个量级。新手什么都想做，高手拼命做减法。

## 步骤② 信封背面估算

不追求精确，只求数量级对不对。因为 1 万用户和 1 亿用户是两个完全不同的系统。

### 值得背下来的锚点数字

- 一天 ≈ 86,400 秒，估算用 10⁵ 秒
- 1000 万日活 × 每人每天 10 次 = 1 亿次/天 ÷ 10⁵ ≈ 1,000 QPS（平均）
- 峰值通常是平均值的 2~5 倍，按 ×3 备容
- 社交/内容类读写比常 10:1 起步
- 一条文本 ~ 数百字节；一张图 ~ 数百 KB ~ 几 MB

### 估算示例：发帖应用（1000 万日活，人均发 1 条刷 50 条）

- 写 QPS：1000 万/天 ÷ 10⁵ ≈ 100/秒，峰值 ×3 ≈ 300
- 读 QPS：1000 万 × 50 = 5 亿/天 ÷ 10⁵ ≈ 5,000/秒，峰值 ≈ 15,000
- 读写比 50:1 → 典型读多写少，缓存和读扩展是重点
- 存储：1 KB/帖 × 1000 万/天 × 365 ≈ 3.6 TB/年（纯文本）；带图均摊 500 KB → 1.8 PB/年

**估算的价值不在精确，而在逼你想清楚系统会被什么压垮。** 读爆？写爆？存储爆？答案不同，后面七步全跟着变。

### ❗ 估算的第一用途：证伪复杂度，不是论证复杂度

很多人算完 QPS 的下一句话是「那我该上什么方案」——**这是工程师惯性，不是架构师思维**。

看一个具体例子：朋友圈式信息流，1000 万日活，人均发 1 条、刷 20 次→ 写 100 QPS、读 2000 QPS、峰值 6000 QPS。

> **6000 QPS 大吗？一台 8 核机器 + Redis 就能扛，还有很大余量。**
>
> 正确的第一个架构结论是：**这个规模用单体 + 一个数据库 + 一层缓存就够了。不要上微服务、不要分库分表、不要读写分离。**

估算最大的价值，往往不是告诉你「要上什么」，而是 **证明你「不需要上什么」**——它是对抗过度设计最有力的武器（参见 [09 章](09-architecture-taste.md)：克制是小团队的默认审美）。

看到一个数字后，先问：**这真的是个问题吗？** 而不是：我该优化什么？

### ❗ QPS 看不见的维度：写放大与扇出

QPS 算的是**请求数**，不是**实际操作数**。一个请求可能在系统内部放大成千万个操作：

> 上例里写 QPS 只有 100，看起来毫无压力。但一个大 V 有 **1000 万粉丝**，他发 1 条内容：
> - 推模式下要写入 1000 万个粉丝的收件箱 = **1000 万次写操作**
> - 这一点在「写 QPS = 100」里完全看不到

| 模式 | 机制 | 代价 |
|------|------|------|
| 推（写扩散） | 发布时写入所有粉丝收件箱 | 大 V 一条 = 千万次写，写爆 |
| 拉（读扩散） | 读时聚合所有关注者的内容 | 读慢，关注 2000 人要聚合 2000 个源 |
| **推拉结合** | 普通用户推，大 V 拉 | 工业界标准解（Twitter 的做法） |

**估算时要额外算三个量**（它们常比 QPS 更早把系统压垮）：

| 量 | 怎么算 | 典型陷阱场景 |
|----|--------|-------------|
| **扇出 / 写放大** | 单请求触发的实际写入次数 × QPS | 信息流推模式、群聊消息扩散、通知广播 |
| **数据总量与增速** | 单条大小 × 日增量 × 保存年限 | 日志/图片/视频类，存储先爆 |
| **热点集中度** | 最热单个 key 占总流量比例 | 大 V/爆款商品/首页，平均 QPS 很低但单点被打穿 |

> 一句话：**看到「一对多」的业务关系（一人发多人收），就要算扇出，而不是只算 QPS。**

### ❗ 结论必须配上「数字的性质」，否则会变成教条

同一个数量级，**是读还是写，结论完全相反**：

| 场景 | 数字 | 性质 | 结论 |
|------|------|------|------|
| 信息流浏览 | 6,000 QPS | **读** | 一台机器 + 缓存就够，别上复杂架构 |
| 群聊扇出后 | 30,000/秒 | **写** | 缓存和复制都无效；先消解扇出，不行才分片 |

「6000 QPS 不用优化」是**读**场景的结论。把它背下来套到写场景，就从「反过度设计」变成了「漏掉真实瓶颈」。

> **套结论前先问一句：这次的数字和性质，和上次一样吗？**（读/写、可变/不可变、并发/因果、限量/非限量）

### ❗ 顺序铁律：先改机制（消解），再谈扩容（硬扛）

算出瓶颈后，**先问「为什么会有这么多」，再问「怎么扛住这么多」**。

群聊例子：扇出后 10,000 写/秒。
- ❌ 直接分片 → 扛住了，但永久背上分片复杂度
- ✅ 先消解：群里只存一份消息 + 每人存一个读游标 → **写入回落到 200/秒**，此时单体+缓存就够（代价转移到读时聚合）

> 大多数人跳过第一步，**为一个本来不该存在的问题付了永久的复杂度成本**。详见 [05 章](05-data-and-state.md)。

## 步骤③ 定义核心用例/API 边界

把系统当黑盒，列动作清单。挑出 1~2 个**主航道**（用户最高频、最能体现系统特点的动作）。

边界清楚后，内部实现就有了靶子：服务不了任何用例的模块 = 过度设计。

## 步骤④ 设计数据模型

用例清楚后立刻设计数据，而不是先设计服务。

1. 画概念模型：核心实体 + 关系
2. 给每类数据选存储形态（[05 章](05-data-and-state.md)原则：不同访问形态 → 不同存储）

## 步骤⑤ 画高层架构

按 [C4 模型](03-c4-model-architecture-diagrams.md)顺序：先 Context（系统当黑盒 + 外部关系）→ 再 Container（切开一层看大块）。

**铁律：先粗后细。** 第一张图五六个框加箭头，丑一点没关系，讲清数据流就行。一上来画二十个框 = 用画图勤奋掩盖没想清楚的偷懒。

## 步骤⑥ 深入关键组件

挑 1~2 个灵魂部件往里钻。怎么判断？**被规模压垮的那个就是它。**

套 [04 章](04-ten-core-architecture-patterns.md)的模式：要解耦 → 事件驱动；读写差太大 → CQRS；要扛突发 → 消息队列削峰。

## 步骤⑦ 找瓶颈针对性扩展

问：用户涨 100 倍，第一个撑不住的地方在哪？然后第二个、第三个。

**对着具体的瓶颈打，不要泛泛地说「加缓存上分片」。** 瓶颈在读就别优化写，瓶颈在带宽就别抠 CPU。

## 步骤⑧ 回顾取舍与风险

最显功力的一步：

- **取舍**：选了 A 放弃了 B，代价是什么
- **风险**：哪个假设如果错了，整个设计就崩
- **未决问题**：哪些还没想清楚，标记留待以后

能主动说出方案的弱点，恰恰证明你真的想清楚了。

## 贯穿主线：架构是迭代出来的

没有人能一次把架构画对。好架构是先画个粗的，再在压力下一轮轮长出来的。

```
   第一版:粗          第二版:细           第 N 版:实战打磨
   ┌────────┐  发现瓶颈  ┌────────┐  真实流量   ┌────────┐
   │ 五六个框 │ ───────▶ │ 加缓存  │ ─────────▶ │ 分片/CDN │ ─▶ …
   │ 能讲通即可│         │ 拆服务  │            │ 多活/降级│
   └────────┘          └────────┘            └────────┘
```

别拿成熟期的图去套 MVP。过度设计和想不到一样有害。

## 实战案例：短链接服务（完整模板见 [templates/01](../templates/01-url-shortener.md)）

完整八步推演见章节原文。关键示范：

- **步骤②**：读写比 100:1 直接定出架构重心在读路径，短码 7 位是从估算里算出来的
- **步骤④**：纯 key-value 查找 → KV 存储，不用关系型
- **步骤⑤**：创建和跳转拆成两条路，因为流量差 100 倍
- **步骤⑦**：每个瓶颈的破解都在兑现前面某步埋下的伏笔
- **步骤⑧**：列出未决问题（热点击穿、短码耗尽、过期回收）是设计成熟的标志

## 常见陷阱

- **一上来就画框**：没搞清楚约束，画什么都是瞎画
- **跳过估算**：不算 QPS/读写比就定组件 = 不知道盖平房还是摩天楼就浇地基
- **算完估算却忘了证伪**：算出 6000 QPS 后不是问「该上什么」，而是先问「这真的是个问题吗」
- **只算 QPS 不算扇出**：写 QPS=100 看着很小，但大 V 一条可能放大成千万次写
- **结论不配数字性质**：「6000 QPS 不用优化」是读的结论，套到写场景就会漏掉真实瓶颈
- **跳过消解直接硬扛**：先问「为什么有这么多写」，再问「怎么扛住」
- **什么都想做**：范围不砍，架构复杂度指数级上升
- **先画细节**：二十个框 = 用勤奋掩盖没想清楚
- **不列未决问题**：号称没问题 = 还没想到那么深
