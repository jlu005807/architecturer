# 09 · 架构品味：框架之外，什么在拉开差距

> 参考章节：品味是什么、怎么养——框架从 0 到 70 分，品味决定 70 到 90 分。

## 核心论点

**框架能教，品味只能养。** 品味是在框架给出的几个合理选项里，选得又准、又美、又适合此时此地的判断力。

| 框架 / 模式 / 流程 | 品味 / 判断力 |
|-------------------|-------------|
| 可以教、可以背 | 只能养、靠见识 |
| 让你少犯致命错误 | 让你做得漂亮 |
| 收敛出几个合理选项 | 在合理选项里选对、知道何时破例 |
| 有可验证答案 | 没有唯一答案，只有更合适 |

## 真相一：没有唯一正确答案

- **Fowler vs Tilkov**：《MonolithFirst》建议先做单体；《Don't start with a monolith》建议别从单体开始。两个世界级架构师公开唱反调——答案取决于约束。
- **Stack Overflow vs Netflix**：前者单体+十几台服务器扛 2 亿日请求；后者数百个[微服务](04-ten-core-architecture-patterns.md)全球分布式。两个相反选择都成功，因为约束截然不同。

> **架构的个性，来自约束的个性。** 抄别人的架构而不抄它的约束，是灾难。

## 真相二：品味的五个面向

### 面向 1 · 对简单的执着，对复杂度的痛感

Rich Hickey《Simple Made Easy》：Simple（结构无缠绕）≠ Easy（就在手边、我很熟）。品味高的人追求 simple，哪怕一开始不 easy。

DHH《The Majestic Monolith》：小团队就该把单体做到极致，而不是用微服务凭空制造分布式的苦难。

### 面向 2 · 不盲从潮流

真实反转案例：
- **Amazon Prime Video**：从微服务+Serverless 改回单体，成本直降 90%
- **Segment**：140+ 微服务合并回单体，从平均每天半次宕机变成几分钟部署

教训不是微服务错了（Netflix 用得很好），真正错的是**跟风**。

> 品味就是能抵抗「显得先进」的诱惑。不问潮不潮，只问适不适合我的约束。

### 面向 3 · 把创新省着用在刀刃上

Dan McKinley《Choose Boring Technology》：每个公司只有有限的几枚**创新代币**。每用一个不成熟的新技术就花掉一枚。别把代币浪费在换时髦数据库上，省下来花在真正的核心竞争力上。

### 面向 4 · 知道何时该破例

- 「不要过早优化」是好规则；但明知道读路径上线就会爆，提前留缓存口子——这是有依据的破例
- 「数据库不要冗余」是好规则；但为了读性能主动[反范式](05-data-and-state.md)——这也是破例

> **危险的不是破例，是没搞懂规则就破例。** 先成为规则的主人，再做规则的叛徒。

### 面向 5 · 审美：认得出丑，也认得出流派

常见的丑：
- 过度设计：五人团队十几个微服务
- 抽象泄漏：号称封装好了，用的人必须懂内部才能用对
- 不一致：同一系统三种命名风格、三种错误处理
- 聪明过头：谁都看不懂的精巧设计，半年后连作者都不敢动

## 真相三：大公司的架构审美

| 公司 | 审美内核 | 标志性事实 | 适用前提 |
|------|---------|-----------|---------|
| Amazon | 服务自治，接口划清边界 | 2002 Bezos API 命令，催生 AWS | 超大组织 |
| Netflix | 拥抱失败，为弹性而生 | Chaos Monkey / 混沌工程 | 超大规模 + 高可用是生命线 |
| Google | 工程严谨，planet-scale 统一基建 | Borg/K8s、Spanner、Bigtable | 极重，非 Google 量级硬学是邯郸学步 |
| Shopify | 单体的简单 + 模块的纪律 | 280 万行 Ruby 模块化单体 | 靠纪律守住边界 |
| 37signals/Basecamp | 极致克制，少即是多 | Majestic Monolith + 下云自建机房省 $10M+ | 小团队效率与成本极致优化 |
| Stack Overflow | 性能极客，最少机器做最多事 | 2 亿日请求只跑十几台 Web 服务器 | 对性能的极致较真 |

### 你该选哪种审美？

**绝大多数个人开发者和小团队，应该向 37signals / Stack Overflow / Shopify 这一端靠拢。**

原因：你的约束长得像 Basecamp，不像 Netflix。人少、要快、预算有限、负载远没到全球弹性。

**小团队默认审美五条**：
1. **单体优先**，先做模块化单体。除非组织真的大到互相阻塞，否则别碰[微服务](04-ten-core-architecture-patterns.md)
2. **选无聊技术**。把创新代币省下来，只花在真正的差异化上
3. **对复杂度有洁癖**。每加一个组件/服务/抽象层，先问：不加会死吗（见[附录 · 升级信号](appendix-signals.md)）
4. **垂直扩展优先**。加配置比加机器再搞分布式更便宜更简单
5. **简单永远压过「显得先进」**

> 先学会 Basecamp 的克制，才有资格谈 Netflix 的复杂。

## 怎么练品味：五件可操作的事

1. **大量读真实架构**：先读模板当地图，再读一手工程博客（Netflix TechBlog、Shopify Engineering、Stack Overflow/Nick Craver、Martin Fowler、InfoQ）
2. **刻意对比同类系统**：挑两个做同类事的产品，列出架构不同，回答「差异来自什么约束的不同」
3. **给每个决策做事后复盘**：三个月后回看取舍，对吗？哪个假设错了？代价如我所料吗？
4. **培养对复杂度的痛感**：每次想加组件，先逼自己回答「不加它，会死吗」
5. **专门读反转故事**：微服务回单体的案例，是校准潮流免疫力的最好疫苗

## 常见陷阱

- **抄架构不抄约束**：看到大厂用某套架构就照搬，忽略团队/流量/成本差异
- **追求标准答案**：架构没有标准答案，只有在这组约束下最合适的
- **盲从潮流**：前几年微服务，这两年 AI 架构——不问适不适合，只问潮不潮
- **创新代币乱花**：通篇新潮技术的系统不是先进，是没想清楚什么才值得冒险
- **没搞懂规则就破例**：蛮干不是品味，搞懂为什么再破才是
