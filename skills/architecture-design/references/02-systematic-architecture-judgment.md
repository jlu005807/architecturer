# 02 · 做架构判断是有章法的

> 参考章节：架构判断的系统化流程，从需求到决策的完整框架。

## 核心论点

架构判断不是玄学，是一套可拆解的流程：**需求 → 约束 → 质量属性 → 候选方案 → 取舍 → 决策**。业务/规模变化时，回到起点重走一遍。

## 六步框架

```
需求 → 约束 → 质量属性 → 候选方案 → 取舍 → 决策
 │                                          │
 └───── 业务/规模变化时，回到起点重走 ◀──────┘
```

### Step 1 · 需求：分清两种需求

| 类型 | 回答的问题 | 特点 |
|------|-----------|------|
| 功能性需求 | 系统要**做**什么 | 显性的，写在文档里 |
| 质量属性（非功能性需求） | 系统要做得**多好** | 隐性的，得自己问出来 |

**核心区分**：功能性需求决定系统能不能用；质量属性决定系统该怎么搭。

举例——图片分享服务：
- 功能：上传图片、获取链接、分享查看、删除图片
- 质量：200ms 内显示（性能）、10 亿用户（可扩展）、全年宕机不超几分钟（可用性）、十一个九（持久性）

### Step 2 · 约束：你不是在真空里做设计

约束 ≠ 质量属性。质量属性是你想达到的目标（越好越好）；约束是你绕不开的限制（就这条件）。

| 约束类型 | 它怎么逼你 |
|---------|-----------|
| 团队规模 | 3 人硬上几十个微服务？运维就累垮 |
| 时间 | 下周上线 vs 有一年 → 完全不同的方案 |
| 预算 | 决定能用多少机器、多贵的服务 |
| 合规/法规 | 红线，不是「尽量」而是「必须」 |
| 已有系统 | 得迁就祖传系统的接口和脾气 |
| 第三方依赖 | 外部 API 的能力上限和故障就是你的约束 |

**关键认知**：约束不是来添堵的，是来帮你砍选项的。约束越清晰，决策越容易。

### Step 3 · [质量属性](06-quality-attributes-and-tradeoffs.md)：检查清单

| 质量属性 | 一句话解释 |
|---------|-----------|
| 性能 | 反应多快（延迟 + 吞吐） |
| 可用性 | 多大比例时间能用（几个九） |
| 可靠性/持久性 | 数据会不会丢、操作会不会出错 |
| 可扩展性 | 涨上来能不能靠加机器应对 |
| [一致性](05-data-and-state.md) | 多处看到的数据是否一致 |
| 安全性 | 能不能挡住攻击、防住越权 |
| 成本 | 建设和运营要花多少钱 |
| 可维护性 | 好不好改、好不好懂 |
| 可观测性 | 出了问题能不能快速看出哪里坏了 |
| 可演进性 | 业务变化时架构能不能跟着长大 |

用法：拿到系统逐项过一遍，对每项问「对我重要吗？目标是多少？」

### Step 4 · 候选方案

带着质量目标表，列出可行的搭建方式。

### Step 5 · 取舍

**没有银弹，只有取舍。任何架构决策，本质都是用 A 换 B。**

| 想加强 | 往往要牺牲 |
|-------|-----------|
| 性能 | 成本 / 一致性 |
| 一致性 | 性能 / 可用性 |
| 可扩展性 | 简单性 / 成本 |
| 安全性 | 便利性 / 性能 |
| 上线速度 | 可维护性 / [技术债](08-architecture-decision-records.md) |

**试金石**：如果一个方案哪儿都好、没有缺点 → 不是完美，是没想清楚。想清楚的人一定能说清：好在哪、牺牲了什么、为什么值得。

### Step 6 · 决策

选一个，并写下为什么。把这些「为什么」记下来 = [ADR（架构决策记录）](08-architecture-decision-records.md)。

## 灵魂六问

适用于任何系统的核心提问，每个都直接锚定一类架构决策：

| 问题 | 锚定什么 |
|------|---------|
| 1. 规模多大？现在多少用户/数据？峰值？ | 要不要/何时为扩展做准备 |
| 2. 读写比？读多写少还是写多读少？ | 往读优化还是写优化倾斜 |
| 3. 一致性要求？刚写的必须立刻能读到？ | 一致性 vs 性能/可用性的取舍 |
| 4. 增长预期？一年后涨到多少？ | 扩展的节奏和时机 |
| 5. 失败的代价？挂了/数据丢了后果多严重？ | 可靠性、可用性的投入程度 |
| 6. 有什么约束？团队/时间/预算/合规？ | 砍掉不可行选项 |

**心法**：没有最好的架构，只有在这组答案下最合适的架构。答案变了，最优解就变了。

## 案例：短链接服务（完整模板见 [templates/01](../templates/01-url-shortener.md)）

**需求**：长 URL → short.ly/x7Kp9，点击跳转原网址。

### 灵魂六问答案

| 问题 | 答案 |
|------|------|
| 规模 | 每天新建 1000 万条 |
| 读写比 | 100:1 甚至 1000:1（生成一次，点击无数次） |
| 一致性 | 可以最终一致（晚一两秒能忍） |
| 增长 | 链接只增不减，数据无限累积 |
| 失败代价 | 跳转挂了体验差但不致命；数据丢了已分享链接全废 = 灾难 |
| 约束 | 小团队、尽快上线、预算有限 |

### 推导出的质量目标

| 质量属性 | 目标 | 来源 |
|---------|------|------|
| 读性能 | 跳转 < 50ms | 读远多于写 |
| 可扩展性（读） | 扛住海量读 | 读写比 100:1+ |
| 持久性 | 短链绝不能丢 | 丢了 = 已分享链接全废 |
| 一致性 | 可以最终一致 | 晚一两秒用户能忍 |
| 成本 | 存储要省 | 数据无限累积 + 预算有限 |

### 关键取舍

- **短码生成**：哈希取前几位（简单但要处理冲突） vs 全局递增计数器（干净但引入发号器）
- **扛读**：缓存热门短链映射 → 读飞快 + 省数据库压力，代价是多一层维护 + 旧数据（但能容忍最终一致，代价承受得起）
- **存储**：简单键值按 key 查 → 天然适合 KV 存储而非关系型

## 常见陷阱

- **跳过质量属性**：功能需求是显性的，质量属性是隐性的，得自己问出来
- **无视约束**：急着画方案而非先摸约束，最后发现方案不可行
- **寻找银弹**：没有哪儿都好的方案，看到取舍才是想清楚的标志
- **跳过六问直接选型**：「微服务 + Kafka + Redis」不是答案，六问答案才是
