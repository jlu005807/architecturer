# 06 · 质量属性与取舍

> 参考章节：七大质量属性的度量、实现与冲突，以及怎么和业务方谈取舍。

## 核心论点

**质量属性几乎全是取舍，不可能全都要。** 架构的本质就是按业务排好优先级，然后清醒地做取舍。

## 七大质量属性速查

| 属性 | 怎么度量 | 怎么实现 | 主要和谁冲突 |
|------|---------|---------|-------------|
| 性能 | 延迟（P99）+ 吞吐（QPS） | 缓存、读写分离、异步、CDN | 成本、一致性、简单性 |
| 可用性 | 几个 9（停机时间） | 冗余、消灭单点、故障域隔离、优雅降级 | 成本、一致性、简单性 |
| 可扩展性 | 负载增 N 倍能否加资源平滑撑住 | 无状态设计、水平扩展、分片 | 一致性、简单性、成本 |
| 一致性 | 强一致 ←→ 最终一致谱系位置（详见 [05](05-data-and-state.md)） | 事务/协调（强）vs 异步同步（最终） | 扩展性、可用性、性能 |
| 安全性 | 攻击面、最坏后果 | 不信任输入、最小权限、纵深防御、数据分级 | 性能、便利性、成本 |
| 可维护性 | 改功能/加特性要多久、新人多久上手 | 清晰边界、低耦合、高内聚、可观测性、[ADR](08-architecture-decision-records.md) | 性能、短期交付速度 |
| 成本 | 单位成本（每用户/请求/token） | 效率优化、资源合理配置 | **几乎所有其他属性** |

## 性能：延迟 vs 吞吐

**延迟** = 单次操作多久（一辆车北京到上海多久）
**吞吐** = 单位时间处理多少（高速每小时通过多少辆车）

两者常常对立：赛道限速 200 但单车道（低延迟低吞吐）vs 限速 80 但十车道（高延迟高吞吐）。

**看 P99 别看平均**：平均 100ms 可能 99% 的人 50ms，1% 的人卡了 5 秒。尾延迟才是体验杀手。

**感知延迟常比真实延迟更重要**：流式输出没让总时间变短，但让体验天差地别。骨架屏、乐观更新、进度提示都在改善感知延迟。

## 可用性：几个 9 值多少钱

| 可用性 | 每年停机 | 每月停机 | 体感 |
|--------|---------|---------|------|
| 99%（两个 9） | ≈ 3.65 天 | ≈ 7.2 小时 | 玩具/内部工具 |
| 99.9%（三个 9） | ≈ 8.76 小时 | ≈ 43 分钟 | 一般在线服务及格线 |
| 99.99%（四个 9） | ≈ 52.6 分钟 | ≈ 4.3 分钟 | 严肃商业服务 |
| 99.999%（五个 9） | ≈ 5.26 分钟 | ≈ 26 秒 | 电信/支付级，极其昂贵 |

**每多一个 9，成本和复杂度往往数量级上涨。** 别张口就要五个 9，先问：挂一小时损失多少？

核心实现思想：**消灭单点故障（SPOF）**，用冗余兜底。
- 冗余：关键组件至少有备份
- 故障域隔离：鸡蛋放不同篮子（多机器/机架/可用区/区域）
- 优雅降级：扛不住时关掉次要功能保核心

## 可扩展性：垂直 vs 水平

| | 垂直扩展（Scale Up） | 水平扩展（Scale Out） |
|---|---------------------|---------------------|
| 方式 | 给单台机器升级配置 | 增加更多台机器 |
| 优点 | 简单，代码不用改 | 理论可无限扩，顺带冗余 |
| 缺点 | 有物理天花板、单点 | 架构必须支持，前提是无状态 |

**关键洞察**：垂直扩展治标有天花板；水平扩展治本但要求无状态。见 05 章第一性原理。

## 安全性：特殊的质量属性

安全平时是看不见的成本，出事时是致命的代价。不能用 ROI 不高为由省掉。

四个贯穿原则：
1. **永远不信任输入**：所有外部数据当有毒处理（提示注入只是老规矩的新形态）
2. **最小权限**：每个组件只拿干活必需的权限
3. **纵深防御**：层层设防，攻破一层还有下一层
4. **数据分级保护**：敏感数据传输和存储都加密

## 成本：最常被忽视的真正约束

成本是你为每个质量属性买单的最终账单。冗余要钱、缓存要钱、多副本要钱、强一致要钱、低延迟也要钱。

**反直觉之处**：低效设计在 1 万用户时月多花几百没人 care，到 1 亿用户就是月多烧几百万——同一设计缺陷被规模放大成天文数字。

## 经典冲突矩阵

| 冲突对 | 具体表现 |
|--------|---------|
| 一致性 vs 可用性 | CAP：网络分区时鱼与熊掌不可兼得 |
| 性能 vs 成本 | 要更快几乎总要砸更多/更贵的资源 |
| 灵活/可扩展 vs 简单 | 微服务灵活但复杂度爆炸；单体简单但难独立扩 |
| 安全 vs 便利/性能 | 每道防线增加摩擦和开销 |
| 上线速度 vs 可维护性 | 赶工 = 借技术债，迟早连本带利还 |

**不可能三角**：一致性、可用性、低延迟——你很难同时把三个角都拉满，优化任何一个往往在另外两个上让步。

## 和业务方谈取舍

### 翻译公式：别讲技术参数，讲业务后果

```
❌ "用强一致会导致写吞吐下降，得加分片，还会牺牲可用性。"

✅ "方案 A（强一致）：保证一分钱不会错，但大促可能排队、每月多花 X 万。
    方案 B（最终一致）：又快又便宜，但极端情况余额可能几秒显示不准。
    我的建议是 A，因为这是钱，出一次错赔的比省的多。您怎么看？"
```

### 沟通心法

1. **永远给选项 + 代价，而不是结论**：摆清楚各路的得到和放弃，让业务方在知情下选择
2. **用三种货币报价：钱、风险、时间**：任何技术取舍都能折算成这三样
3. **把质量属性绑到业务指标**：别说要四个 9，要说挂一小时损失 Y 万，所以值得投入 Z
4. **区分底线和优化项**：安全合规/资金正确不可谈判；200ms 优化到 100ms 可能只是锦上添花

❗ **绝不能说的一句话：「技术上做不到」。**

这句话把你从「参谋」变成了「障碍」，而且它通常不准确——真相是「做得到，但要付 X 代价」。**架构师的活不是说不行，是把选择权交回去，但把代价标清楚。**

### ❗ 最容易做错的一步：报价 ≠ 菜单

被要求「给选项」时，绝大多数人给的是**每条需求分别多贵**，而不是**有哪几条完整的路可走**。

场景：老板要求「聊天记录永久保存 + 全文搜索秒出 + 成本压一压」。

| ❌ 报价（汇报视角） | ✅ 菜单（参谋视角） |
|------------------|------------------|
| 「永久保存要花很多存储钱；全量索引成本是原始数据几倍；成本要压就得牺牲速度」 | 方案 A 全量热存全量索引 / 方案 B 冷热分层 / 方案 C 免费 3 个月+付费永久，各标得失与成本 |
| 老板听完还是不知道该选什么 | 老板可以直接拍板 |

**区别在于**：报价是「这事有多难」，菜单是「有这几条路，各自的代价，你拍」。

> **写不出三个方案，说明你还没想清楚。** 一个方案 = 你在推销；两个方案 = 一个是陪衬；三个方案 = 真的在做取舍。

### 带价签的选项表：标准输出格式

以「在线协同文档」为例——产品提三个要求：实时光标（<100ms）、绝不丢内容、可用性 99.99%。写法应该是：

| 方案 | 他得到什么 | 他付出什么 | 开发成本 |
|------|-----------|-----------|---------|
| A. 服务端强持久化后再广播 | 数据零丢失，逻辑简单 | **协作延迟 300ms+**，打字有粘滞感 | 低 |
| B. 纯内存广播，定期快照 | 极致流畅 | 服务器崩溃丢最近 30 秒编辑 | 低 |
| C. 客户端副本 + 操作日志（推荐） | 流畅**且**不丢 | 需要 CRDT/OT，**复杂度高 2~3 倍** | 高，多 2 个月 |

> 「A 和 B 各让一步，C 两个都要但要多花 2 个月。**你选。**」

### ❗ 取舍之前先问：这个冲突能不能被消解？

**不是所有冲突都必须妥协。换个架构视角，有时两个需求可以拆成两条正交的通道，都拿到。**

上例的 C 方案就是消解：关键洞察是**客户端浏览器里就有一份完整副本**。

```
用户敲字
  ├─→ ① 本地立刻应用（0ms）
  ├─→ ② 广播给协作者（内存快路，<100ms）← 满足要求①
  └─→ ③ 追加到本地未确认队列 + 异步发服务器落盘

服务端落盘的是「操作日志」（append-only）而非文档快照
  → 顺序写盘极快；崩溃后重放日志恢复
  → 客户端手里有未确认队列，重连后重传 ← 满足要求②
```

> **「不能丢」不等于「服务器必须在返回前落盘」。** 当客户端也是一个持久副本时，可靠性可以由「两端各留一份 + 可重传」保障，而不是牺牲延迟。这就是 Figma / Google Docs 的做法。

类似的消解例子：短链接服务里「映射缓存永不过期（省钱）」与「10 秒内下线恶意链接（安全）」看似冲突，拆成**封禁通道 + 映射通道**两条独立生命周期后两者兼得（见 [templates/01](../templates/01-url-shortener.md)）。

> 好架构师一半功夫在白板上，另一半在会议室里。

## 常见陷阱

- **全都要心态**：不存在又高一致又高可用又便宜又简单的系统
- **张口就要五个 9**：每多一个 9 成本数量级涨，先问业务到底需要多少
- **只看平均延迟**：P99 和尾延迟才是体验杀手
- **技术语言沟通**：跟业务方讲术语而非讲钱/风险/时间
- **说「技术上做不到」**：把自己从参谋变成障碍；真相通常是「做得到，但要付 X 代价」
- **遇冲突就直接妥协**：先问能不能拆成两条正交通道把冲突消解掉
- **把「报价」当成「给选项」**：列每条需求多贵 ≠ 列几条可选的完整路径
- **把成本当成底线**：成本是**约束**（六步框架 Step 2），底线是安全/合规/资金正确这类不可谈判项
- **忽视成本复利**：低效设计被规模放大成天文数字
