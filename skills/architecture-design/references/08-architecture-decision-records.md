# 08 · 架构决策记录与演进

> 参考章节：怎么让架构活得久、长得好——ADR、演进式架构、技术债管理、康威定律。

## 核心论点

**最先丢失的永远是为什么。** 代码和图能说清系统是什么，但讲不清为什么这么选、放弃了什么——而后者才是后人最需要、最易蒸发的东西。

## 一、ADR：给架构决策建一本为什么的账

ADR（Architecture Decision Record）= 架构决策记录。一份轻量文档，每做一个重要架构决策就写一份。

**精髓**：
- 足够轻：一个决策一份，通常一页纸
- 追加不修改：决策变了写新的，把旧的标记为「被取代」——保留历史
- 和代码放在一起：如 `docs/adr/` 目录，随代码一起版本管理

### ADR 模板（六块）

| 字段 | 写什么 | 为什么不能省 |
|------|--------|-------------|
| 标题 | 一句话说清这个决策是什么 | 方便日后检索 |
| 状态 | 草稿 / 已采纳 / 已废弃 / 被某 ADR 取代 | 让读者知道这条还算不算数 |
| 背景/上下文 | 当时面临什么问题、什么约束 | 后人最缺的就是当时的处境 |
| 决策 | 我们最终决定怎么做 | 系统是什么，代码里也能看到 |
| 考虑过的其它选项 | 还想过哪些方案，为什么没选 | **放弃了什么，是 ADR 独有的价值** |
| 取舍与后果 | 好处、代价、已知债务 | 让后人清楚地继承这份有意的取舍 |

### ADR 示例

```
ADR-007：订单流水采用「主库 + 不可篡改日志」双写

状态：已采纳
日期：2026-05-23    决策者：架构组 + 合规

── 背景 ──────────────────────────────────
监管要求订单流水必须落入「写后不可改」的存储以备审计；
但业务又要求订单可被高频修改。单一存储无法同时满足。

── 决策 ──────────────────────────────────
主库存可变订单状态；同时把每次变更追加写入不可篡改日志；
以日志为准做定期对账。

── 考虑过的其它选项 ─────────────────────
A. 只用主库 + 软删除 → 否决：软删除仍可被改，过不了审计
B. 只用不可篡改存储 → 否决：无法支持改单
C. 双写（本方案） → 采纳

── 取舍与后果 ───────────────────────────
+ 同时满足合规与业务两个硬约束
− 引入双写，需要对账逻辑兜底不一致
− 后人会觉得「多此一举」——本 ADR 就是写给你看的，别删！
```

## 二、强观点：记为什么比记是什么重要一百倍

- **系统是什么样会自我证明，为什么这么做不会。** 看代码就知道系统什么样；但代码永远不会告诉你团队本来想用方案 B，只因某个约束才忍痛上了方案 C。
- **没有为什么，后人只能二选一**：不敢动（系统僵化）或乱动（直接踩雷）。
- **为什么是可迁移的智慧**，是什么只是一次性的结果。

> 好的文档不重复解释代码做了什么（代码自己会说）；好的文档解释代码为什么这么做（代码永远不会说）。

## 三、演进式架构：留好接缝

核心思想：既然你注定无法一次设计对，那就把架构设计成**容易改对**的样子。

**接缝（Seam）**：清晰的模块边界和接口。想换掉某个模块时，只要接口不变，其它模块毫无感觉。

- 短码生成做成独立模块 → 将来换生成策略只换这一块
- 缓存藏在接口背后 → 从进程内缓存换 CDN 对调用方透明
- AI 产品调模型 API 收在清晰边界后 → MVP 调外部 API，成长期换自建推理

> 设计时多问一句：**这一块将来最可能被换掉吗？** 最可能变的地方，就要用最干净的接口包起来。好的接缝，让演进从重写变成替换。

## 四、技术债：关键是记账

技术债 = 为了现在更快拿到价值，而有意识选的将来需要偿还的权宜方案。

| 有意识的债（健康） | 无意识的债（危险） |
|-------------------|-------------------|
| 「为赶发布先用最简单方案，记 TODO，下季度重构」 | 「我也不知道为什么这里这么写，反正能跑」 |
| 理性的商业权衡 | 失控，你甚至不知道欠了债 |
| 写进 ADR/backlog，排期还 | 哪天突然爆雷 |

**处理纪律三条**：
1. 有意识地借，明确是权宜之计
2. 记下来——技术债就该写 ADR，背景说明为什么暂时这样做
3. 安排偿还时机——挂进 backlog，定「当 X 发生时就还」的触发条件

## 五、康威定律

**系统的架构，会不可避免地长得像设计它的那个组织的沟通结构。**

两条启示：
1. **拆服务之前，先看团队结构**：团队还是一锅粥，拆出来的微服务照样紧耦合。想要松耦合的服务，先有边界清晰的团队。
2. **逆康威操作**：想要什么架构，就先组织成什么团队。组织设计本身就是一种架构设计。

> 架构问题，常常是组织问题伪装的。两个模块怎么解耦都解不干净时，先看看背后那两拨人是不是本就分不开。

## 六、何时升级架构：用判断，不用感觉

靠两把尺子量，而不是拍脑袋：

| 尺子 | 判断标准 |
|------|---------|
| 瓶颈（[06](06-quality-attributes-and-tradeoffs.md)+[07](07-system-design-methodology.md)） | 某个质量属性已被架构卡住？数据库读到冒烟？模块改动连累一片？ |
| 质量属性变化（[06](06-quality-attributes-and-tradeoffs.md)） | 业务要求上了台阶？可用性从 99% 到 99.99%？用户量进入下一量级？ |

**原则**：不是旧了、丑了、别人上了就升级，而是某个真正在乎的质量属性被真实瓶颈卡住了才升级（见[附录 · 升级信号](appendix-signals.md)）。每次升级本身也该写 ADR。

## 常见陷阱

- **不记为什么**：代码/图说清了什么，但为什么随风而逝
- **无意识的技术债**：不知道自己欠了债，最危险
- **凭感觉升级**：「代码看着丑」不是升级理由，要量出真实瓶颈
- **跟风大厂**：别人的瓶颈不是你的瓶颈，照搬成熟期架构套自己成长期 = 头号过度设计
- **忽视康威定律**：团队边界不清就去拆服务，拆了也白拆（见 [04 · 微服务](04-ten-core-architecture-patterns.md)）

## 整章贯穿：判断 + 记录的循环

```
做出一个架构判断 ──▶ 把「为什么」记成 ADR
（用 01–17 的方法）         │
                            ▼
            业务长大 / 出现新瓶颈
            （用 06 的尺子重新判断，回到顶端）
                  ↑
            判断力在每一圈里复利增长
```
