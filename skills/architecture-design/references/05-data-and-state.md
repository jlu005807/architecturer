# 05 · 数据与状态：系统真正的难点

> 参考章节：数据建模、存储选型、一致性、扩展手段——架构的真正功夫在管好状态。

## 核心论点

**逻辑好改，数据和状态难改。** 代码写错改几行重新部署；但当几亿条数据已按某种结构躺在库里，想改它是要命的。架构的真正难点，从来不在逻辑，而在数据与状态。

## 无状态 vs 有状态

| 类型 | 特点 | 扩容难度 |
|------|------|---------|
| 无状态 | 不记得任何事，给输入算输出，算完就忘 | 直接复制，流量随便分 |
| 有状态 | 记得事情，且记忆随时间变化 | 复制就有同步问题，一切麻烦的根源 |

**反复出现的架构动作**：把状态从计算里挤出去，集中放进少数专门管理状态的地方（数据库、缓存），让其余组件尽量无状态。

## 一、存储选型：为访问形态选存储

核心原则：先看数据长什么样、怎么被访问，再选最适合的存储。

| 存储类型 | 最适合的数据/访问 | 一句话直觉 |
|---------|-----------------|-----------|
| 关系型 | 结构清晰、关系复杂、需要事务和强一致 | 钱、账、关系的默认家 |
| 文档型 | 结构灵活、自包含、按 ID 整取整存 | 半结构化 JSON，字段常变就用它 |
| 键值 KV | 极简按 key 取 value，要求极快 | 超大字典，闪电般读写 |
| 列存 | 海量数据分析聚合（报表、统计） | 按列存，扫大片算总和 |
| 图 | 关系网络（社交、推荐、风控） | 谁认识谁、谁连着谁 |
| 向量 | 语义相似度检索（RAG、推荐） | 找意思最像的内容 |
| 对象存储 | 大块不可变文件（图片、视频、模型权重） | 海量大文件仓库 |
| 搜索引擎 | 全文检索/复杂条件过滤排序 | 输入关键词，模糊找出 |
| 时序 | 带时间戳、只追加、按时间聚合 | 不断增长的时间轴 |

**三个判断问题**：
1. 读写形态是什么？高频小读写（KV）/ 整存整取（文档/对象）/ 大范围聚合（列存）/ 按关系语义找（图/向量/搜索）
2. 需要多强的一致性？一分钱不能错（关系型）vs 差一点没关系（KV/搜索）
3. 会长到多大？访问多频繁？决定要不要复制/分片

> 复杂系统天然多种存储混用（多语言持久化 polyglot persistence）。

## 二、一致性谱系

```
强一致 ◀─────────────────────────────────────────▶ 最终一致
写完立刻任何人读到最新值                    过一会儿大家才看到最新值
严谨但贵、难扩、易拖慢                    宽松、好扩、高可用但有短暂不一致窗口
```

### CAP 定理（人话版）

网络分区（P）不是你能选的，分布式系统迟早会遇到。分区发生时只能二选一：

- **CP（一致性优先）**：宁可不服务，也不给错数据 → 适合钱、账、库存
- **AP（可用性优先）**：宁可给旧数据，也得继续服务 → 适合点赞数、动态流

### 哪些要强一致，哪些可最终一致？

判断标准：**这份数据短暂不一致，会造成多大真实后果？**

**必须强一致**（后果严重，错了要赔钱/出事）：
- 账户余额、支付：多扣一分、双花一笔都是事故
- 库存扣减：超卖 = 卖了不存在的货
- 唯一性约束：用户名不能注册两次

**可以最终一致**（短暂不一致没人真的在意）：
- 点赞数、浏览量：1024 vs 1025 谁会受损
- 社交动态流：晚几秒刷到完全可以接受
- 通知、已读状态：迟到一会儿无伤大雅

> 强一致很贵，别到处滥用。把配额花在真正会出事的地方。

## 三、事务：ACID vs BASE

| | ACID（严谨派） | BASE（务实派） |
|---|---------------|---------------|
| 核心 | 每一步必须绝对正确 | 允许暂时不完美，保证最终对上 |
| 一致性 | 强一致 | 最终一致 |
| 代价 | 难扩、可能拖慢/拒服 | 要容忍中间态，逻辑更难写 |
| 适合 | 钱、订单核心 | 大规模、可容忍延迟场景 |

成熟系统混用：核心交易走 ACID，周边统计/通知走 BASE。

## 四、扩展数据三张牌

| 手段 | 主要目的 | 解决什么 | 核心代价 |
|------|---------|---------|---------|
| 复制（主从） | 扩读 | 读多写少压力分摊 | 主从延迟（最终一致）、写仍是单点 |
| 分片 | 扩写 | 写能力和存储容量扩展 | 跨分片操作极难、分片键选错是灾难、再分片很痛 |
| 缓存 | 降延迟+扩读 | 热点数据快速响应 | 一致性问题、穿透/击穿/雪崩 |

**一句话区分**：复制扩读、分片扩写、缓存降延迟并扩读。三者都靠制造副本换扩展性，代价都是一致性变难。

## 五、缓存三大经典难题

### 1. 缓存失效与一致性
数据库变了，缓存还是旧的。没有完美解，只有[取舍](06-quality-attributes-and-tradeoffs.md)：给缓存设 TTL，把不一致窗口控制在业务能接受的范围。

### 2. 穿透/击穿/雪崩

| 问题 | 原因 | 对策 |
|------|------|------|
| 穿透 | 大量请求查不存在的数据，穿过缓存打 DB | 空值缓存 / 布隆过滤器 |
| 击穿 | 热点 key 过期瞬间，海量请求涌向 DB | 重建时加锁，只让一个请求查库 |
| 雪崩 | 大量 key 同时过期或缓存宕机 | 过期时间加随机抖动、缓存高可用 |

### 3. 缓存与数据库一致性
缓存是第二份副本，只要有副本就有对不上的风险。这与主从延迟、分片不一致是同一类问题。

## 六、数据模型是最难改的决策

```
改代码: 旧代码 ──删除──▶ 新代码          (干净、可逆、几分钟)
改数据: 几亿条旧数据 ──?──▶ 新结构
        ① 兼容方案 ② 迁移脚本 ③ 期间正常服务 ④ 出错能回滚
        (痛苦、危险、以周/月计)
```

**建议**：数据模型与状态管理要慎重、要尽早想清楚。在[六步框架](02-systematic-architecture-judgment.md)里，数据怎么建模、放哪、要多强一致、怎么扩，应该是最早最认真思考的一部分。

## 常见陷阱

- **一种存储装一切**：不管什么都用同一个数据库，必然别扭
- **到处强一致**：把点赞数也做成全网强一致，为不需要的严谨付高昂代价
- **分片太早/分片键选错**：尽量晚做、想清楚再做
- **忽视缓存一致性**：用了缓存就主动选择了某种不一致，要控制窗口
- **数据模型草率**：逻辑可以先糙后精，数据模型要尽早想透
