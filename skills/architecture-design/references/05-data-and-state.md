# 05 · 数据与状态：系统真正的难点

> 参考章节：数据建模、存储选型、一致性、扩展手段——架构的真正功夫在管好状态。

## 核心论点

**逻辑好改，数据和状态难改。** 代码写错改几行重新部署；但当几亿条数据已按某种结构躺在库里，想改它是要命的。架构的真正难点，从来不在逻辑，而在数据与状态。

## 无状态 vs 有状态

| 类型 | 特点 | 扩容难度 |
|------|------|---------|
| 无状态 | 不记得任何事，给输入算输出，算完就忘 | 直接复制，流量随便分 |
| 有状态 | 记得事情，且记忆随时间变化 | 复制就有同步问题，一切麻烦的根源 |

**反复出现的架构动作**：把状态从计算里挤出去，集中放进少数专门管理状态的地方（数据库、缓存），让其余组件尽量无状态。

## 一、存储选型：为访问形态选存储

核心原则：先看数据长什么样、怎么被访问，再选最适合的存储。

| 存储类型 | 最适合的数据/访问 | 一句话直觉 |
|---------|-----------------|-----------|
| 关系型 | 结构清晰、关系复杂、需要事务和强一致 | 钱、账、关系的默认家 |
| 文档型 | 结构灵活、自包含、按 ID 整取整存 | 半结构化 JSON，字段常变就用它 |
| 键值 KV | 极简按 key 取 value，要求极快 | 超大字典，闪电般读写 |
| 列存 | 海量数据分析聚合（报表、统计） | 按列存，扫大片算总和 |
| 图 | 关系网络（社交、推荐、风控） | 谁认识谁、谁连着谁 |
| 向量 | 语义相似度检索（RAG、推荐） | 找意思最像的内容 |
| 对象存储 | 大块不可变文件（图片、视频、模型权重） | 海量大文件仓库 |
| 搜索引擎 | 全文检索/复杂条件过滤排序 | 输入关键词，模糊找出 |
| 时序 | 带时间戳、只追加、按时间聚合 | 不断增长的时间轴 |

**三个判断问题**：
1. 读写形态是什么？高频小读写（KV）/ 整存整取（文档/对象）/ 大范围聚合（列存）/ 按关系语义找（图/向量/搜索）
2. 需要多强的一致性？一分钱不能错（关系型）vs 差一点没关系（KV/搜索）
3. 会长到多大？访问多频繁？决定要不要复制/分片

> 复杂系统天然多种存储混用（多语言持久化 polyglot persistence）。

## 二、一致性谱系

```
强一致 ◀─────────────────────────────────────────▶ 最终一致
写完立刻任何人读到最新值                    过一会儿大家才看到最新值
严谨但贵、难扩、易拖慢                    宽松、好扩、高可用但有短暂不一致窗口
```

### ❗ 一致性不只有两档：别漏了顺序（因果）一致性

强一致 / 最终一致这个二分法**不够用**。有一类需求两头都不属于：

> 群聊里张三先发「明天别来了」，李四接着回「好的」。
> 甲的网络先收到张三，乙的网络先收到李四 → **同一个群，两人看到的对话顺序不同**，「好的」跑到了问题前面，语义全乱。

它不要求「写完立刻全网可见」（不是强一致），但要求「**所有人看到的顺序一致**」，而且**不处理就永远不会自己变对**（不是最终一致）。

| 档位 | 要求 | 实现手段 | 典型场景 |
|------|------|---------|---------|
| 强一致 | 写完任何人立刻读到最新值 | 事务、共识、原子操作 | 钱、库存、限量名额 |
| **顺序 / 因果一致** | **不要求实时，但所有人看到的顺序相同** | **服务端定序（sequencer）**：消息到达时盖一个会话内单调递增 seq，客户端按 seq 排 | 群聊消息、事件流、操作日志 |
| 最终一致 | 过一会大家都能看到 | 异步复制、消息队列 | 点赞数、已读状态、搜索索引 |

**关键在于「因果关系」——不是所有消息都需要保序：**

| 情况 | 有因果吗 | 顺序要求 |
|------|---------|---------|
| 李四**读到**张三的消息后才回「好的」 | **有**（因果依赖） | 必须保序，否则语义崩坏 |
| 私聊两人**同时**发消息（谁也没看见谁） | **无**（并发消息） | 顺序随意，各端不同也没关系 |

> 💡 这解释了一个日常现象：**微信私聊两人同时发消息，双方看到的顺序可能不同，但没人觉得有问题**——因为并发消息之间没有因果，顺序本就没有客观答案。而群聊回复密集、因果链多，就必须靠服务端定一个所有人都认的序。

### CAP 定理（人话版）

网络分区（P）不是你能选的，分布式系统迟早会遇到。分区发生时只能二选一：

- **CP（一致性优先）**：宁可不服务，也不给错数据 → 适合钱、账、库存
- **AP（可用性优先）**：宁可给旧数据，也得继续服务 → 适合点赞数、动态流

### 哪些要强一致，哪些可最终一致？

判断标准：**这份数据短暂不一致，会造成多大真实后果？**

#### 一把能一刀切开的尺子

「会不会影响用户/功能」这种尺子**筛不掉任何东西**（点赞数也影响用户，但它显然不需强一致）。用下面两个等价问法，才能一刀切开：

| 版本 | 那句话 | 如何判 |
|------|--------|--------|
| **钱的版本** | 「不一致会不会赔钱 / 需要人工介入补偿？」 | 会 → 强一致；不会 → 最终一致 |
| **自愈的版本** | 「不一致能不能自己好？」 | 等一会就对了 → 最终一致；等一辈子也不会对，必须人来查 → 强一致 |

> 💡 **需要对账的数据，就是错了不会自愈的数据。** 这两句是同一把尺子的两面。

**第三把尺子（前两把判不出时用）：这份数据是「提示」还是「判定依据」？**

| 角色 | 猜错的后果 | 能最终一致吗 |
|------|-----------|-------------|
| **hint（路径/性能优化的提示）** | 走了慢路或多做一次无用功，**下游有兜底** | ✅ 可以 |
| **判定依据（决定某事该不该发生）** | 判错就错了，**没有兜底、不会自愈** | ❌ 必须强一致 |

以 IM 的在线状态（presence）为例，它能最终一致的真正原因**不是「用户看不出来」，而是它只是 hint**：

| 猜错情形 | 后果 | 谁兜住 |
|---------|------|-------|
| 说在线，实际刚掉线 | 投递失败 | 消息已落库 → 转存离线信箱 |
| 说离线，实际刚上线 | 多发一条推送通知 | 用户已看到消息，通知只是噪音 |

**两条路都通向同一个正确结果**，只是快慢和噪音不同 → 所以它可以不准。

❗ **同一份数据，不同用途可以分不同档**：

| 数据 | 用途 | 一致性要求 |
|------|------|-----------|
| 群成员关系 | **权限判定**（U 还能不能读新消息） | **强一致**——判错就是越权读取，不会自愈，没有下游兜底 |
| 群成员关系 | UI 显示成员列表 | 最终一致——晚一秒消失无所谓 |
| 订单状态 | 是否允许再次支付 | 强一致 |
| 订单状态 | 报表统计 | 最终一致 |

> 判断时先问：**这份数据在这个位置上，是在「提示走哪条路」，还是在「裁决某事成立与否」？**

**必须强一致**（后果严重，错了要赔钱/出事）：
- 账户余额、支付：多扣一分、双花一笔都是事故
- 库存扣减：超卖 = 卖了不存在的货
- 唯一性约束：用户名不能注册两次
- **订单状态（易错点）**：用户付款成功但页面还显「待付款」→ 他再付一次 → **重复收款**。注意拆分：订单自身状态转换必须强一致 + 幂等，而下游通知（发货/短信/报表）可最终一致

**可以最终一致**（短暂不一致没人真的在意，且会自愈）：
- 点赞数、浏览量、已售件数：1024 vs 1025 谁会受损
- 社交动态流、搜索索引：晚几秒刷到/搜到完全可以接受
- 通知、已读状态：迟到一会儿无伤大雅

#### 限量发放族：一个容易漏判的同类项

下面这些看上去很不一样，但**本质上是同一个问题，全部需要强一致 + 防超发**：

| 东西 | 超发的后果 |
|------|-----------|
| 商品库存 | 超卖 → 道歉/赔付 |
| **优惠券剩余张数** | 多发 20 张都是有效券，用户来兑现你必须认 → 真金白银损失 |
| 秒杀名额 | 超额下单 → 取消订单 → 口碑崩盘 |
| 抽奖奖品 | 超发奖品 → 兑付成本失控 |
| 会议室/座位预订 | 双订 → 现场冲突 |
| 积分/虚拟币（可兑换） | 凭空多出余额 → 等同于印钱 |

> ❗ **识别口诀：任何「限量发放」的东西都是库存的变体。** 看到「剩余 N 个」就要警觉：这是强一致 + 原子扣减的场景，不是个普通计数器。
>
> （注意区分：页面上展示的「仅剩 100 张」可以是最终一致的近似值；但**领取时的实际扣减**必须强一致。展示和扣减是两回事。）

> 强一致很贵，别到处滥用。把配额花在真正会出事的地方。

## 三、事务：ACID vs BASE

| | ACID（严谨派） | BASE（务实派） |
|---|---------------|---------------|
| 核心 | 每一步必须绝对正确 | 允许暂时不完美，保证最终对上 |
| 一致性 | 强一致 | 最终一致 |
| 代价 | 难扩、可能拖慢/拒服 | 要容忍中间态，逻辑更难写 |
| 适合 | 钱、订单核心 | 大规模、可容忍延迟场景 |

成熟系统混用：核心交易走 ACID，周边统计/通知走 BASE。

## 四、扩展数据三张牌

| 手段 | 主要目的 | 解决什么 | 核心代价 |
|------|---------|---------|---------|
| 复制（主从） | 扩读 | 读多写少压力分摊 | 主从延迟（最终一致）、写仍是单点 |
| 分片 | 扩写 | 写能力和存储容量扩展 | 跨分片操作极难、分片键选错是灾难、再分片很痛、倾斜不均需再平衡 |
| 缓存 | 降延迟+扩读 | 热点数据快速响应 | 一致性问题、穿透/击穿/雪崩 |

**一句话区分**：复制扩读、分片扩写、缓存降延迟并扩读。三者都靠制造副本换扩展性，代价都是一致性变难。

> ❗ **最常见的误用：拿复制去解决写瓶颈。** 主从/读写分离加十个从库，**写入依然全部打在主库**。看到写瓶颈时，复制和缓存两张牌直接出局——只剩分片，或者更好的选择：**改机制消解写放大**（见下）。

### ❗ 先改机制（消解），再谈扩容（硬扛）

遇到写瓶颈的顺序铁律：**先问「为什么会有这么多写」，再问「怎么扛住这么多写」**。

以群聊为例：日活 100 万、人均 20 条、平均群 50 人 → 发消息请求只有 200 QPS，但**推模式（每人一份收件箱）扇出后是 10,000 写/秒**，峰值 3 万。

| 思路 | 做法 | 结果 |
|------|------|------|
| ❌ 硬扛 | 直接上分片、换写优化存储 | 扛住了 3 万写/秒，但永久背上分片的复杂度 |
| ✅ **先消解** | **群里只存一份消息，每人只存一个「读到哪」的游标** | 写入回落到 **200/秒**，代价转移到读（读时按游标聚合）——**此时单体+缓存就够了** |

消解后的附加红利：500 人群和 5000 人群**不再有本质区别**（不用为大群单独设计推拉结合）。

> 大多数人跳过第一步直接去分片，**为一个本来不该存在的问题付了永久的复杂度成本**。

## 五、客户端 / 边缘也是一个副本（离线优先）

一个常被忽略的视角：**客户端本地存储不是缓存，它是参与可靠性保障的持久副本。**

| | 缓存 | 持久副本 |
|---|------|---------|
| 目的 | 加速 | **保障可靠性** |
| 丢了 | 没事，回源重取 | **不能丢，它就是数据本身** |
| 例子 | 内存里的最近消息 | **本地 SQLite + 未确认操作队列** |

由此得到一条重要推论：

> **「不能丢」≠「服务端必须在返回前落盘」。** 当客户端也是持久副本时，可靠性可以由「**两端各留一份 + 可重传**」保障，而不必牺牲延迟。

IM 的落地形态就是 **UI 状态分级**：

| 状态 | 谁保证 | 耗时 |
|------|-------|------|
| 发送中（转圈） | 客户端本地已落库 | **0ms** ← 满足「立刻反馈」 |
| 已发送（单勾） | 服务端已持久化并 ack | 几十 ms ← 满足「绝对不丢」 |
| 已送达 / 已读 | 对方客户端已收到 / 已看 | — |

> 微信、WhatsApp 的双勾号不是产品设计，是**架构决策的 UI 投影**——把「立刻」和「可靠」拆成四个状态，两个都拿到，不需妥协。
>
> 配套前提：**消息 ID 必须由客户端生成**。否则超时重传时服务端无法分辨「新消息」和「重传」，群里会出现重复消息。客户端生成 ID + 服务端唯一约束 = 重传 100 次也只存一条（又一次「用结构保证而非检查保证」）。

同类系统：协同编辑（CRDT/OT + 操作日志）、离线优先笔记、文件同步。

#### 落地机制一：增量同步靠「同步游标」

离线操作攒了一堆，联网时不可能全量比对（十年数据每次开网都比一遍？）。必须只传增量：

```
服务端：每个变更分配一个单调递增序号（seq）
客户端：记住 last_synced_seq = 1042

联网时：
  ① 上传：POST /changes  { 本地未同步的操作日志，每条带客户端生成的操作 ID }
  ② 下载：GET /changes?since=1042  → 服务端只返回 1042 之后的变更
  ③ 合并后更新本地游标
```

> 💡 **和群聊「每人存一个读到哪的游标」是同一个机制**，也和短链接的「日志 + 游标补算」同源。**一个模式，三个场景。**
>
> 由此得到一条接口设计差异：普通 CRUD 是「给我第 N 条」，**同步接口是「给我第 X 号之后发生的所有事」**。后者才能支撑离线。

#### 落地机制二：删除必须用「墓碑」，而且服务端也不能物理删

分布式同步里**最难的操作是删除**——因为「不存在」这个状态没法传播，你只能用「**一条说明它不存在的记录**」来传播它。

| 做法 | 会发生什么 |
|------|-----------|
| ❌ 客户端物理删除本地记录 | 同步时服务端看到「客户端没有这条」，无法分辨是**用户删了**还是**还没同步到** |
| ❌ 服务端收到删除后物理删除 | 三台设备场景：手机删 → 服务端物理删 → 平板一周后联网，`GET /changes?since=X` 里**没有任何删除痕迹** → 平板把本地那条**又传回去** → **删除的数据复活** |
| ✅ 两端都写墓碑（tombstone） | 删除本身作为一条变更被传播；保留一段时间（直到所有设备确认或固定 30 天）后再做 tombstone GC |

#### 落地机制三：冲突处理——先看数据性质，再选策略

同一条记录，手机改成 100、网页改成 200，都在离线状态下改的。

**最简单的 LWW（谁晚谁赢）有三个坑**：

1. **静默丢失**：用户在手机上明明改成了 100，同步后变成 200，**没有任何提示**——他以为自己改成功了
2. **客户端时钟不可信**：手机时间可手动改、有时区和漂移问题
3. **服务端时间也不完美**：离线三小时后才上传的操作会被打上更晚的时间戳，反而赢过期间在线做的修改——**真实的因果顺序丢了**。严格解法是**版本向量 / 逻辑时钟**（记录「谁在看到什么之后做的」）

**能不能用 LWW，取决于数据性质**：

| 数据性质 | 例子 | 能 LWW 吗 |
|---------|------|----------|
| **累加 / 集合型** | 余额、计数、标签集合、待办列表 | ❌ **每个操作都携带信息，丢一个就错一个** |
| **覆盖型** | 账目备注、文档标题、设置项 | ✅ 后写覆盖前写符合语义（或保留双版本让用户选） |

> 🔑 **但注意：如果你按前面说的「存操作日志而非最终状态」，累加型的冲突根本不存在。**
>
> 手机的「+100」和网页的「+200」是两个独立操作，两边都保留、都执行 → 结果自然是 +300，**不需要问「谁赢」**。这就是 **CRDT（无冲突复制数据类型）** 的核心思想：让数据结构本身具备「无论以什么顺序合并都得到相同结果」的性质。

### ❗ 这个视角的边界：什么绝对不能让客户端先写

拿到这把锤子后最危险的事，是拿它去敲不该敲的钉子。

**反例**：把「客户端是副本 + 离线优先」用到电商——用户离线也能下单、也能付款，联网后同步。

| 问题 | 后果 |
|------|------|
| 离线下单 5 件，联网发现只剩 2 件 | 操作日志**不能无脑重放**，必须服务端裁决 |
| 离线点「支付」，客户端显示**支付成功页** | **这不是技术问题，是产品灾难**：用户认为买到了，三小时后被告知「刚才那个成功是假的」——比一开始就说「没网不能买」糟糕一百倍 |

#### 两把判断尺子

**尺子一：这个操作的「决定权」在谁手里？**

| 决定权 | 例子 | 能离线先写吗 |
|-------|------|-------------|
| **用户自己是唯一决定者** | 记账、笔记、待办、文档草稿、发消息、点赞 | ✅ 没人跟他抢 |
| **需要争抢共享资源** | 库存、秒杀名额、座位、限量优惠券 | ❌ 客户端看不到全局，不知道别人抢没抢 |
| **需要第三方确认** | 银行支付、实名认证、风控放行 | ❌ 决定权在外部系统 |

> IM 的「发送中→已发送」之所以成立，是因为**发消息的决定权在用户自己**。换成「下单成功」就不成立——那个「成功」必须服务端盖章。
>
> **同一个状态分级手法，关键在于「哪个状态由谁盖章」：客户端只能盖「我记下了」，不能盖「事情成了」。**

**尺子二：客户端是不可信的。** 本地数据用户能改（root / 越狱 / 改包 / 改时间）。**涉及钱和权限的判定绝不能采信客户端的结论**——这是「所有外部输入都视为不可信」在客户端上的应用，客户端就是外部输入。

#### 「客户端是副本」和「客户端不可信」怎么共存？

这两条看似矛盾，其实**分管两件不同的事**：

| 原则 | 管什么 | 客户端可以 | 客户端不可以 |
|------|-------|-----------|-------------|
| **客户端是副本** | **数据在哪** | 持有数据、保存操作、先写后传 | — |
| **客户端不可信** | **谁说了算** | — | 判定权限、宣布结果、决定自己该拿到什么 |

> 🔑 一句话：**客户端可以是仓库，但不能是法官。**

具体场景验证——用户被踢出群，但离线三天，本地还留着完整群消息：

| 问题 | 答案 | 依据 |
|------|------|------|
| 服务端要返回他离线期间的 200 条消息吗？ | **不返回** | 他请求了 `since=1042`，但**服务端自己查权限、自己决定给什么**（不可信原则） |
| 他本地已有的旧消息要不要删？ | **不删** | 那些消息他当时有权限看，是合法持有的数据；且他可能重新加群（副本原则） |
| 他改了本地数据说自己还在群里？ | **无效** | 成员关系由服务端裁决，客户端改了也拿不到新消息 |

#### ❗ 易漏陷阱：「自己的数据」≠「能独立决定」

判据的真正关键不是**数据属于谁**，而是：**这个操作的成功，是否依赖其他人的状态？**

| 操作 | 看起来 | 实际 |
|------|-------|------|
| 修改自己的昵称（**昵称全局唯一**） | 「我自己的数据」 | ❌ 成功取决于「别人有没有占用」→ **争抢共享资源**。两个用户离线都改成同一个昵称，联网后必有一个失败 |
| 修改自己的昵称（昵称可重复） | 「我自己的数据」 | ✅ 真的可以离线先写 |

> **一旦加了全局唯一约束，私有数据就变成了争抢资源**——这和「限量发放族」同源（见前文「唯一性约束：用户名不能注册两次」）。
>
> 正确做法：可离线**编辑**，但 UI 显示「待生效」，服务端裁决后才确认；或干脆把「唯一 ID」和「可重复的显示名」拆开。

#### 离线能力分类速查

| 操作 | 能离线先写 | 依据 |
|------|-----------|------|
| 给笔记加标签 / 待办打勾 / 编辑文档草稿 | ✅ | 自己独占，无人争抢 |
| 给动态点赞 | ✅ | 决定权在自己，且可撤销；点赞数是可合并的计数器 |
| 协同文档编辑一段文字 | ✅ | 需配 CRDT/OT 处理合并 |
| 修改昵称 | ⚠️ | 取决于是否全局唯一 |
| 领限量优惠券 / 下单 / 支付 | ❌ | 争抢资源或需第三方确认 |

## 六、缓存三大经典难题

### 1. 缓存失效与一致性
数据库变了，缓存还是旧的。没有完美解，只有[取舍](06-quality-attributes-and-tradeoffs.md)：给缓存设 TTL，把不一致窗口控制在业务能接受的范围。

### 2. 穿透/击穿/雪崩

| 问题 | 原因 | 对策 |
|------|------|------|
| 穿透 | 大量请求查不存在的数据，穿过缓存打 DB | 空值缓存 / 布隆过滤器 |
| 击穿 | 热点 key 过期瞬间，海量请求涌向 DB | 重建时加锁，只让一个请求查库 |
| 雪崩 | 大量 key 同时过期或缓存宕机 | 过期时间加随机抖动、缓存高可用 |

### 3. 缓存与数据库一致性
缓存是第二份副本，只要有副本就有对不上的风险。这与主从延迟、分片不一致是同一类问题。

## 七、数据模型是最难改的决策

```
改代码: 旧代码 ──删除──▶ 新代码          (干净、可逆、几分钟)
改数据: 几亿条旧数据 ──?──▶ 新结构
        ① 兼容方案 ② 迁移脚本 ③ 期间正常服务 ④ 出错能回滚
        (痛苦、危险、以周/月计)
```

**建议**：数据模型与状态管理要慎重、要尽早想清楚。在[六步框架](02-systematic-architecture-judgment.md)里，数据怎么建模、放哪、要多强一致、怎么扩，应该是最早最认真思考的一部分。

## 常见陷阱

- **一种存储装一切**：不管什么都用同一个数据库，必然别扭
- **到处强一致**：把点赞数也做成全网强一致，为不需要的严谨付高昂代价
- **分片太早/分片键选错**：尽量晚做、想清楚再做
- **忽视缓存一致性**：用了缓存就主动选择了某种不一致，要控制窗口
- **数据模型草率**：逻辑可以先糙后精，数据模型要尽早想透
- **拿复制去扩写**：主从/读写分离只扩读，写瓶颈时它和缓存都无效
- **跳过消解直接硬扛**：先问「为什么有这么多写」，再问「怎么扛住」
- **把客户端本地存储当缓存**：它是参与可靠性保障的持久副本，能省掉「返回前必须落盘」的延迟代价
- **离线同步物理删除记录**：必须用墓碑，两端都不能物理删，否则删除会复活
- **对累加型数据用 LWW**：余额/计数/集合丢一个操作就错一个，要合并操作而非覆盖
- **让客户端宣布「成功」**：客户端只能盖「我记下了」，涉及争抢资源或第三方确认的「成功」必须服务端盖章
