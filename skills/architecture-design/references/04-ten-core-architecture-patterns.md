# 04 · 十大核心架构模式

> 参考章节：前人踩坑后留下的成熟解法。学模式是为了手里有牌，不是炫技。

## 核心论点

**模式是工具，不是目标。** 没有高级模式与低级模式之分，只有合不合适。一个用对了的单体，远比一个用错了的微服务高级。

## 模式速查表

| # | 模式 | 解决什么问题 | 核心代价 |
|---|------|-------------|---------|
| 1 | 分层架构 | 关注点分离，改一处不崩一片 | 穿透成本，样板传递代码 |
| 2 | 单体 | 最低协作/运维成本先做出来 | 不能单独扩容/部署，模块崩拖全局 |
| 3 | 微服务 | 多团队协作扩展性 | 分布式复杂度大山，运维爆炸 |
| 4 | 事件驱动 | 解耦 + 可扩展业务流程 | 流程看不见，排查像破案 |
| 5 | 消息队列/异步 | 削峰填谷、异步解耦、可靠投递 | 异步 UX、幂等处理、队列监控 |
| 6 | CQRS | 读写诉求严重不对称 | 复杂度翻倍，最终一致 |
| 7 | Pub/Sub | 一对多广播通知 | 投递语义、扇出成本、流程追踪难 |
| 8 | 客户端-服务端/BFF | 多端各端数据裁剪 | 多一层维护，BFF 间重复代码 |
| 9 | 管道-过滤器 | 线性数据加工流程拆分 | 木桶效应、链路回滚/重试 |
| 10 | 微内核/插件化 | 核心稳定 + 外围多变 | 契约设计极难改、插件隔离 |

## 各模式详解

### 1. 分层架构 Layered

把系统按关注点横向切成几层，每层只跟相邻层打交道。

```
┌─────────────────────────────┐
│  表现层:Presentation          │  界面 / API
├─────────────────────────────┤
│  业务层:Business Logic        │  核心规则
├─────────────────────────────┤
│  数据访问层:Data Access       │  存取逻辑
├─────────────────────────────┤
│  数据库 / 外部存储             │
└─────────────────────────────┘
        每层只调用下一层,不越级、不反向
```

**代价**：穿透成本，简单查询可能老实穿过每一层。
**注意**：分层是底座不是全部，后面很多模式在分层基础上针对某个质量问题做专门处理。

### 2. 单体 Monolith — 被严重低估的正确起点

整个应用作为一个可部署单元，所有模块在同一进程里。

```
┌───────────────────────────────────────────┐
│              单 体 应 用:一个进程            │
│   ┌────────┐ ┌────────┐ ┌────────┐         │
│   │ 用户模块 │ │ 订单模块 │ │ 支付模块 │  …    │
│   └────────┘ └────────┘ └────────┘         │
└──────────────────────┬──────────────────────┘
                   ┌────▼────┐
                   │ 数据库   │
                   └─────────┘
```

**关键认知**：单体内部可以且应该分模块（模块化单体）。单体 ≠ 一团乱麻。
**硬建议**：默认从模块化单体开始。等真的痛了、痛在明确的某处，再针对那一处拆。

### 3. 微服务 Microservices — 被严重滥用的成熟期解药

把大应用拆成多个可独立开发/部署/扩容的小服务。

**核心问题不是技术问题，而是组织问题**：多团队互相踩脚时的解药。

> 微服务首先解决人的扩展性，其次才是机器的扩展性。

**使用前提（最好同时满足）**：
1. 组织规模够大，多团队互相阻塞
2. 有明确的独立部署需求
3. 已有承接复杂度的平台能力（监控、追踪、CI/CD、编排）

**代价**：网络失败/延迟/乱序、跨服务事务几乎不可能、运维复杂度爆炸、本地调试变难。

> 微服务常常用来解决你还没遇到的问题，代价是制造一堆你本来不会有的问题。

### 4. 事件驱动 Event-Driven

组件通过「发生了什么事」协作，而非「你去帮我做什么」命令。

```
                    订单已支付事件
   ┌────────┐  发布   ┌─────────────┐  分发
   │ 订单服务 │ ──────▶ │  事件总线    │ ──────┬────────┬────────┐
   └────────┘         └─────────────┘       │        │        │
   发布者不关心                              ▼        ▼        ▼
   谁在消费                             ┌──────┐ ┌──────┐ ┌──────┐
                                        │发短信 │ │加积分 │ │通知物流│
                                        └──────┘ └──────┘ └──────┘
```

**代价**：整体流程看不见，排查像破案。要处理事件重复、乱序、丢失、最终一致。

### 5. 消息队列 / 异步处理

生产者扔进去就走，消费者按自己节奏捞出来处理。

**三个经典问题**：削峰填谷、异步解耦、可靠投递。

**代价**：引入必须维护的关键基础设施、异步 UX（处理中状态）、必须做幂等（重复消费）、消息会丢（丢时无报错）、队列堆积成为新监控对象、流程看不见排查像破案。

### 6. CQRS 读写模型分离

写和读拆成两套独立模型/路径，各自优化。

```
   写请求:Command                       读请求:Query
       │                                     │
       ▼                                     ▼
  ┌─────────┐    数据同步/事件     ┌────────────────┐
  │ 写模型   │ ─────────────────▶ │ 读模型:可多个     │
  │ 规则严谨 │   常常异步,         │ 为查询预先优化好  │
  │ 强一致   │   最终一致          │ 反范式、可缓存    │
  └────┬────┘                     └───────┬────────┘
       ▼                                  ▼
   写库:为正确性优化                读库/视图:为读取速度优化
```

**代价**：复杂度翻倍，两套模型 + 同步通道 + 最终一致。
**绝大多数系统不需要 CQRS。** 它是读写严重不对称且常规手段已压榨干净后的重武器（详见 [05 · 数据与状态](05-data-and-state.md)）。

### 7. Pub/Sub 发布-订阅

一条消息被所有订阅者各收一份（广播），vs 队列一条消息只给一个消费者（分摊）。

**代价**：全局流程难追踪、扇出成本、可靠性语义要想清楚。

### 8. 客户端-服务端 / BFF

为每种前端做一个贴身后端，把后端数据裁剪/聚合成该端最顺手的形状。

**代价**：多一层维护、BFF 间重复代码。
**适用条件**：多端 + 各端差异大 + 后端是多个服务。

### 9. 管道-过滤器 Pipeline

数据像流水线一站一站加工，每个过滤器只干一件小事。

**代价**：木桶效应（最慢站拖累全线）、链路回滚/重试、不适合来回交互的逻辑。

### 10. 微内核 / 插件化

稳定内核 + 可插拔插件。内核提供基础能力和接入规则，功能做成插件。

**代价**：契约/接口一旦定下来极难改、插件质量参差需沙箱隔离、内核扩展点设计难度高。

## 选型决策流程

```
Step 0: 能不用模式就先别用 → 分层单体能解决？能就这样
    │
    ▼ 解决不了
问 1: 我遇到的到底是什么问题？对症，别对时髦
    │
    │  代码搅成一团 ────────▶ 分层 / 模块化
    │  一件事扇出通知多方 ──▶ 事件驱动 / Pub/Sub
    │  耗时任务 / 削峰 ─────▶ 消息队列 / 异步
    │  读写严重不对称 ───────▶ CQRS
    │  多端差异大 ───────────▶ BFF
    │  线性数据加工 ─────────▶ 管道-过滤器
    │  核心稳定 + 外人扩展 ──▶ 微内核 / 插件
    │  多团队互相阻塞 ───────▶ 慎重考虑微服务
    │
    ▼
问 2: 这个模式的代价我现在付得起、也愿意付吗？
    │  付不起 / 问题还没真出现 → 先别上，记一笔
```

## 三条心法

1. **从简单开始，被痛驱动地演进**：不预支未来的复杂度
2. **模式可以组合**：真实系统常是分层单体打底 + 局部事件驱动/异步/缓存
3. **永远能说出代价**：说不清换走了什么 = 大概率在跟风

## 常见陷阱

- **集邮心态**：不是模式用得越多越好
- **跟风微服务**：三人团队十几个微服务 = 给自己上刑（详见 [09 · 架构品味](09-architecture-taste.md)）
- **无视代价**：看不到代价 = 没学会这个模式
- **预支复杂度**：产品还没验证就先搭一套分布式基础设施
