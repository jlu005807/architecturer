# 01 · 为什么先有架构思维

> 参考章节：架构设计技能的背景知识库，供深度分析时引用。

## 核心论点

写代码正在贬值，架构判断正在升值。AI 让「怎么写」变廉价，于是「写什么」「为什么这么写」成了真正稀缺的能力。

## 实现能力 vs 架构判断

| 维度 | 实现能力 | 架构判断 |
|------|---------|---------|
| 回答的问题 | 这个功能怎么写出来？ | 系统该长什么样？哪里会先出问题？拿什么换什么？ |
| 关注点 | 语法、库、性能技巧 | 边界、数据流、取舍、失败模式 |
| 出错代价 | 改一个函数 | 可能要重写整个系统 |
| 反馈速度 | 跑一下就知道对不对 | 几个月后才暴露 |
| AI 替代性 | AI 越来越能替你做 | AI 只能当参谋，拍板的还是你 |

**核心区分**：实现的错误，代码会告诉你；架构的错误，时间才会告诉你。

## 架构的定义与三个特征

架构 = 系统里那些重要决策的集合。「重要」= 同时满足以下三点：

### 特征一：难以更改
- 判断标准：如果反悔的代价大到只能忍着，就是架构决策
- 例：单体拆微服务、分库分表 → 架构；改个变量名 → 不是

### 特征二：影响全局
- 影响蔓延到系统很多角落，而非局限在一个模块
- 例：同步调用 vs 异步消息 → 影响每个功能写法、故障传播、延迟和复杂度

### 特征三：关乎[质量属性](06-quality-attributes-and-tradeoffs.md)
- 架构关心的不是功能能不能实现，而是系统做得好不好
- 质量属性（非功能性需求）：快不快、稳不稳、扛不扛得住、改不改得动、贵不贵、安不安全

## 案例：两个团队，同一个需求

**需求**：团队任务协作工具（建任务、分配、评论、通知）

### A 团队：先跑起来再说
- 任务/评论/通知全塞一张大表
- 通知靠刷新页面轮询
- 所有逻辑写在一个服务里
- 结果：用户增多后系统变慢、改推送要伤筋动骨、多人改同一文件天天冲突

### B 团队：先看地图再上路
花两天问关键问题：
1. **规模预期**：现在几百，一年内可能几十万 → 可扩展性从一开始就得想
2. **读写比例**：读远多于写 → 读写形态不同，不该挤在一起
3. **实时性要求**：通知延迟几分钟就被骂 → 实时推送是现在就得留的位置
4. **一致性分级**（详见 [05 · 数据与状态](05-data-and-state.md)）：任务数据丢了是灾难（强一致），通知晚到几秒可以忍（最终一致）

架构决定：核心数据与通知分开处理；推送通道独立预留；各部分可独立演进。

**教训**：有些坑，写代码前花两天想想就能绕开；掉进去要花两个月才爬出来。

## 开发者成长路径

```
会写 → 写得好 → 会做系统 → 会判断
(能实现)  (优雅健壮)  (拆得清连得顺)  (知道为什么、算得清代价)
                                        ↑ 只能靠你，AI 给不了
```

## 练习方法

对每个技术选择，强迫自己回答：
1. **为什么是它？** 是真有理由，还是只是大家都这么用？
2. **代价是什么？** 选了它，同时放弃了什么？将来在哪里付代价？

## 真实案例：Knight Capital (2012)

- 部署新代码时 8 台服务器只更新了 7 台
- 漏掉的那台跑着 2003 年遗留的死代码
- 45 分钟发出 400 多万笔错误订单，亏损约 4.4 亿美元
- 失守层面：部署一致性、死代码治理、风险隔离 — 都是架构问题

## 常见陷阱

- **过度设计**：想三个月再动手是另一个极端
- **正确配比**：在最难改、最致命的几个决定上，提前投入一点点思考
- **漂亮代码救不了歪地基**：每个函数都优雅，但数据该强一致的地方最终一致了，该解耦的地方死死耦在一起
