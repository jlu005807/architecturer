# 附录 · 何时该升级架构：量化触发信号

> [08 章](08-architecture-decision-records.md)说过：别凭「感觉旧了/丑了」或「大厂都上了」就升级架构，要看「某个你在乎的质量属性，是不是被真实瓶颈卡住了」。
> 这份速查，把那句话落成可观测的量化信号——当你看到这些信号，才是该动手的时候。

⚠️ **重要**：下面的数字是「经验数量级」，不是铁律。真实阈值取决于你的硬件、数据形态、业务容忍度。把它们当「该警惕了」的提示，而不是「到这个数就必须改」的命令。真正的依据永远是：某个质量属性被真实瓶颈卡住（且你量出来了）。

## 读 / 写 / 存储：数据层的信号

| 你观测到的信号（经验区间） | 大概率的瓶颈 | 常见破解（见 05） |
|--------------------------|-------------|-----------------|
| 主库 CPU 持续 > 70%、读请求排队 | 读打满了 | 加读副本（复制扩读）+ 缓存（见 [05](05-data-and-state.md)） |
| 缓存命中率掉到 < 90%、回源压力大 | 缓存不够 / 失效策略差 | 调缓存粒度、TTL、预热；防穿透击穿雪崩 |
| 单表行数过千万 ~ 上亿，或单库容量过几百 GB | 单库装不下 / 写变慢 | 考虑分片（扩写），但要慎选分片键（见 [05](05-data-and-state.md)） |
| 写 QPS 接近单库上限、主库成为写瓶颈 | 写打满了（复制救不了） | 分片；或拆出独立写服务 |
| 同一份数据被多种查询形态折磨（又要事务又要全文又要聚合） | 一种存储扛了不该扛的活 | 按访问形态拆存储（多语言持久化，见 [05](05-data-and-state.md)） |

## 延迟 / 性能：体验层的信号

| 信号 | 瓶颈 | 破解 |
|------|------|------|
| P99 延迟持续超标（而 P50 还好） | 尾延迟——某条慢路径 / 资源争抢 | 找最慢那一跳针对性优化，别动 P50 |
| 某个耗时操作让用户干等 > 几秒 | 同步阻塞了不该同步的活 | 异步化 + 队列削峰（[04](04-ten-core-architecture-patterns.md)） |
| 流量出现规律性尖峰（开售/大促/早晚高峰） | 按峰值堆机器太贵、按均值又被冲垮 | 削峰填谷 + 弹性扩缩 +（极端）排队 |

## 可用性 / 可靠性：稳定性的信号

| 信号 | 瓶颈 | 破解 |
|------|------|------|
| 业务要求可用性上一个台阶（99% → 99.9% → 99.99%） | 单点 / 无冗余撑不住更高的 9 | 消灭单点、加冗余、故障域隔离、多活 |
| 某组件一挂全系统瘫（SPOF） | 存在单点故障 | 冗余 + 自动故障转移 |
| 一次故障波及面过大、恢复慢 | 故障域没隔离 | 隔离爆炸半径、限流降级、熔断 |

## 组织 / 研发效率：最容易被忽视的信号

| 信号 | 瓶颈 | 破解（注意：常是组织问题） |
|------|------|------------------------|
| 改一处牵动一片、发布越来越慢、谁都不敢动 | 模块边界烂 / 耦合过紧 | 先理清模块边界（模块化单体）；未必要拆服务 |
| 多团队在一个代码库里互相阻塞、上线排队 | 「人」的扩展性到顶了 | 这才是微服务的真正信号——但先看团队边界（[康威定律](08-architecture-decision-records.md)，见 [08](08-architecture-decision-records.md)） |
| 新人上手要好几周、改个功能要动很多地方 | 可维护性差 | 重构边界、补文档/ADR，而非堆新功能 |

### 拆分判据的可量化阈值

上面三条是定性描述。但你去说服 CTO / 团队时，**形容词没有说服力——必须给数字**。以下是行业常用参考阈值：

| 维度 | 可观测指标 | 参考阈值 | 为什么是这个数 |
|------|-----------|---------|-------------|
| **发布阻塞** | 单次发布需协调的人数 / 发布频率 | 协调 > 3 人，或发布频率被迫降到 < 1 次/周 | 发布变成「仪式」而非日常动作，就是耦合在收税 |
| **团队规模** | 同一 repo 高频改动的贡献者数 | > 10~15 人 | 两个披萨团队上限；超过后沟通成本呈平方增长 |
| **反馈环时长** | 构建 + 测试总时长 | > 15 分钟 | 超过这个时长开发者就会去干其他事，上下文切换成本失控 |
| **故障耦合** | 月度事故中「A 模块拖挂 B 模块」的占比 | > 30% | 说明故障域没隔离，但**先试进程内隔离/限流**再谈拆服务 |
| **资源不对称** | 单模块占整体 CPU/内存比例 vs 它的业务价值比例 | 吃掉 > 50% 资源但只占 10% 业务价值 | 该模块需要独立扩容节奏，这是最硬的拆分理由 |

❗ **最关键的一条：真正的微服务信号是「人」而不是「机器」。**

性能问题几乎都能用「加机器 + 缓存 + 读写分离 + 分片」解决，而这些手段都比微服务便宜得多。**只有当多团队在同一代码库互相阻塞、上线排队时，微服务才是那个唯一的解**——这正是康威定律的意义。

### 拆服务前要先付的隐藏成本

单体里 `userService.getUser(id)` 是一次函数调用——**永不失败、微秒级、在同一个事务里**。拆成服务后它变成网络调用：

| 新增问题 | 你必须额外养的东西 |
|---------|-----------------|
| 会失败（超时/网络抖动） | 超时、重试、熔断、幂等 |
| 会慢（延迟叠加） | 一个请求串 4 个服务，P99 叠加放大 |
| **事务没了** | 原本一个 `@Transactional` 搞定的事，变成 Saga / 补偿逻辑 |
| 调试变难 | 必须上分布式追踪（trace）才知道请求死在哪 |
| 本地开发变重 | 新人第一天要启动 4 个服务才能跑起来 |

> 一句话：**微服务把「编译期能发现的问题」变成了「运行时才炸的问题」。** 估算你的团队养不养得起这套基础设施，再谈拆。

## AI 层（LLM / RAG / Agent 专属）

> 以下综合自各 AI 模板的演进信号（见 [ai-native.md](domains/ai-native.md)），仅供 AI 系统参考。

| 信号 | 瓶颈 | 破解 |
|------|------|------|
| GPU 打满致首字延迟飙升、单 token 成本压不下去 | 推理资源不足 | 上连续批处理、prompt / KV 缓存、模型路由 |
| 上下文频繁撞窗口、压缩后丢关键信息 | 上下文管理失控 | 上 RAG / 外置记忆 / 分层上下文管理 |
| 召回 / 准确率不足、检索质量瓶颈 | 检索策略不当 | 混合检索 + 重排、语义切块、上下文增强 |
| eval 指标退化、人审积压、工具误操作增多 | 质量/安全失控 | 加评测门禁、human-in-the-loop、权限沙箱收紧 |

## 怎么用这张表

1. **先量，再判断。** 没有监控数据（QPS、P99、命中率、CPU、容量）就谈升级，都是拍脑袋。先把这些指标盯起来。
2. **一次只解一个瓶颈。** 升级架构有巨大成本和风险，它必须是为了换取某个当下被卡住的质量属性——别一次重构全家桶。
3. **每次升级都写一条 ADR**：什么信号触发了它、升成什么、放弃了什么。
4. **没触发，就别动。** 没有信号还要升级，十有八九是过度设计或跟风——记住 [09 章](09-architecture-taste.md)：个人/小团队的默认审美是「克制」。

> 一句话：架构升级是「被真实信号触发的、有据可查的决策」，不是「定期重构的仪式」，也不是「追新的冲动」。
